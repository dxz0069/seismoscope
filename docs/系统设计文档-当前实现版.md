# 嫘祖鉴丝 Vibe Sec Platform：面向 Vibe Coding 的 Skill 化安全审查验证平台系统设计与实验报告（当前实现版）

> 阅读说明：全文沿用原设计文档的七个顶层部分和原有编号顺序。每个部分开头的“当前实现核对”是对本地仓库事实、实现边界和未交付能力的勘误说明；其后的编号小节负责完整展开设计、场景、创新或实验论证。两类内容不是新增顶层章节，历史实验数字统一标注为上一版基线。

## 一、目标问题与意义价值

### 当前实现核对：当前产品定位与工程边界

#### 产品定位的重新收束

嫘祖鉴丝 Vibe Sec Platform 的核心定位不是一个远程漏洞扫描器，也不是把若干安全规则和大语言模型拼接起来的报告生成器。它是面向 Vibe Coding 工作流的本地安全审查与验证平台：编码 Agent 负责快速生成和修改代码，平台负责把代码、运行面、提示词、工具、外部上下文、权限和部署边界组织成可审查对象，再将证据绑定的风险、可执行的整改约束和复测计划回送给编码 Agent。

“Vibe Coding”改变了安全问题出现的方式。传统应用往往由开发者先设计控制边界，再实现功能；Vibe Coding 中，页面、API、数据库、模型提示词、MCP 工具、文件操作和部署配置可能在一个会话中连续生成。功能演示可以很快成功，但安全属性不一定被显式表达。平台因此将安全审查放在编码会话的循环中，而不是只在发布前运行一次：

```text
编码 Agent 生成或修改代码
        │
        ▼
Skill 触发并建立 RunSession
        │
        ▼
项目画像与 VRTM 运行面建模
        │
        ▼
静态审查 + 规则/语义工具 + LLM 多轮证据审查
        │
        ▼
风险链、验证谓词与受控验证计划
        │
        ▼
Harness 授权验证 / 浏览器或服务证据
        │
        ▼
整改包、修补约束、验收标准与复测计划
        │
        ▼
编码 Agent 受控修改 → 人工确认门 → 复测 → 关闭或保留风险
```

平台的价值不在于让模型“多说一些安全建议”，而在于把每个结论放回一条可以追溯的事实链：哪个入口可达、哪一个输入被谁控制、经过了什么数据流、跨越了哪个权限边界、到达了什么危险能力、验证工具观察到了什么、修复后哪个谓词发生了变化。

#### 面向对象与角色

平台面向四类主要角色。第一类是使用 AI 编程助手的开发者，他们希望在代码生成和修改过程中得到短、准、可执行的安全反馈。第二类是安全工程师，他们需要查看运行面、风险链、证据包、验证状态和复测差异，而不是只查看一张漏洞列表。第三类是团队负责人或审核人，他们需要批准高权限 Agent 的修改范围、外部服务启动和动态验证。第四类是编码 Agent 本身，它通过 Skill 接收结构化结果，把整改包作为下一轮修改的输入。

平台的主要对象如下：

| 对象 | 定义 | 持久化内容 | 主要消费者 |
| --- | --- | --- | --- |
| Project | 一个本地源码项目及其审查范围 | 名称、路径、审查范围、更新时间 | Web UI、CLI、API |
| RunSession | 一次可恢复、可审计的 Skill/审查/验证会话 | 任务、状态、事件、检查点、权限上下文 | Agent、Harness、复测 |
| Runtime Surface | 项目的运行面节点和关系 | 入口、数据、指令、权限、能力、外部边界 | VRTM、风险图、LLM |
| VRTM Snapshot | 某次运行面和威胁假设的不可变快照 | 图指纹、风险假设、覆盖诊断、变化分析 | 审查、复测、前端 |
| Candidate Finding | 静态或语义工具提出的候选 | 类型、位置、严重度、置信度、证据 | 审查队列、LLM |
| Evidence Bundle | 与结论绑定的证据集合 | 工具记录、代码片段、验证谓词、差异 | 报告、整改、复测 |
| Remediation Package | 面向 Agent 的整改回送 | 修改提示、约束、验收标准、复测计划 | 编码 Agent、审核人 |
| Validation Session | Harness 受控验证过程 | 授权、控制、观测、清理、结果 | Finding、VRTM、报告 |

#### 解决的问题与不解决的问题

平台明确解决五个连续问题：

1. 解决“看不见”：把 Web/API、模型、提示词、MCP、文件、外部内容、权限和部署关系放到同一运行面。
2. 解决“排不出优先级”：用漏洞类型、严重度、置信度、可达性、权限跨度、能力到达和证据缺口排序，而不是按文件扫描顺序展示。
3. 解决“讲不清”：将候选组织为入口、前提、转换、边界、触发、影响和证据条件组成的风险链。
4. 解决“证不实”：把 LLM 结论限制在静态证据和 Harness 结果内，动态验证采用漏洞态、修复态、合法控制三态。
5. 解决“改不顺”：输出带有文件范围、修改约束、验收条件、负向控制和复测计划的整改包，供编码 Agent 继续工作。

平台不把以下内容伪装成已解决能力：没有授权时的生产环境渗透、没有目标控制权的远程利用、没有 Ground Truth 时的检测率宣称、没有运行证据时的漏洞确认、没有审批时的高权限自动修改，以及没有完整依赖信息时的 CVE 版本结论。

#### 结论状态的语义

系统使用保守的状态机来防止自然语言和证据等级混淆：

| 状态 | 含义 | 可以对外表述 | 不能对外表述 |
| --- | --- | --- | --- |
| potential | 静态或语义证据支持风险可能存在 | “潜在风险，需要验证” | “漏洞已确认” |
| needs_evidence | 证据不足、LLM 会话中断或动态验证未授权 | “保留为待证实项” | “已修复”或“已利用” |
| not_reviewed | 候选超出当前 LLM/验证预算 | “尚未审查” | “没有问题” |
| rejected | 有足够反证或验证控制否定该候选 | “当前证据不支持该风险” | “代码绝对安全” |
| verified | Harness 通过授权、正/负控制和验证谓词确认 | “在限定范围内已验证” | “整个产品无此风险” |
| closed | 修复、反向控制、回归和 VRTM 变化均通过 | “该整改包在当前基线关闭” | “同类问题永久消失” |

这些状态既出现在 API 的 `verification_status` 字段，也出现在报告、前端队列、RunSession 事件和整改回送中。任何跨状态升级都必须有新增证据或可信审批记录。

状态字段需要分层理解：`potential`、`needs_evidence`、`not_reviewed`、`rejected`、`verified` 是 Finding/验证结论语义；`static_only`、`candidate_confirmed`、`unverified` 是审计器或兼容层的内部标记，不能直接当作漏洞确认；`open`、`draft`、`returned`、`in_progress`、`completed`、`closed` 属于整改包或整改工单状态。不同层的状态不能互相直接转换，必须经过证据绑定、授权和复测条件。




### 1.1 作品背景

**页面、工作流和轻量智能体正在被 AI 批量生成，安全边界却没有被同等速度地证明。** 这是 vibe coding 场景下最值得警惕的结构性失衡：功能从自然语言到可运行页面只需要几分钟，认证、权限、提示词、工具和浏览器执行边界仍然需要按工程事实逐项确认。

一个典型开发现场已经很清楚。开发者让 AI 先生成课程主页和登录页，再补“教师查看学生进度”的后台接口；随后又在页面里加入 AI 助手，让它读取课程资料、外部网页和学习状态；为了方便运营，再接入表单、文件上传、审批流、MCP 工具或第三方 API。页面打开正常，接口返回正常，模型也能回答问题，项目看起来已经接近交付。真正的风险埋在连接处：学号字段是否被后端当作身份事实，富文本内容是否进入浏览器执行点，外部网页是否被助手当成高优先级指令，工具描述是否放大了执行权限，修补后合法业务路径是否仍然保留。

这类风险的危险之处，在于它们通常不会以“页面崩溃”的形式暴露。一个 AI 生成的报名系统可以顺利提交表单，却把身份字段留给前端控制；一个智能体页面可以正常回答问题，却把外部网页中的隐藏指令带入上下文；一个工作流节点可以完成文件处理，却让用户输入接近读写文件、网络请求或代码执行能力。vibe coding 将“能跑起来”的速度大幅提前，也把安全审查从上线前的一次检查，推到了每一轮生成、修改和复测之中。嫘祖鉴丝面向的正是这种“功能已经成形、边界尚未证明”的真实交付现场。

开发效率提升的同时，网页应用的安全边界也在发生变化。对于 AI 网页与轻量智能体应用，安全对象已经从前端代码和后端接口，扩展到页面提示词、页面助手职责、工具/能力调用权限、浏览器状态以及模型输出的信任方式。页面、模型、工具和业务接口不再是彼此孤立的几个部分，并在运行时共同组成一个 **复合运行面**。

这意味着 **传统网页漏洞与智能体风险会在同一页面内叠加出现**。

一方面，旧问题并未消失。前端业务逻辑漏洞、校验绕过、越权入口暴露、敏感信息泄露、客户端关键字段可控，以及前端对价格、权限、角色或状态的错误信任，仍然会进入 AI 辅助开发场景。不同的是，由于生成速度快、模板复用多、人工复核不足，这些常见缺陷更容易在短周期内被批量带入真实业务环境——以前写一个有漏洞的页面需要几天，现在几分钟就能生成并部署。

另一方面，AI 引入了全新的风险维度。页面助手和轻量智能体把提示词、外部上下文和工具调用引入了同一条页面链路。OWASP 已将提示词注入（Prompt Injection）与不安全输出处理列为大模型应用的首要风险[1]；OpenAI 关于浏览器智能体和提示词注入的系统卡与防御研究也表明，当模型可以读取网页、访问上下文、调用工具并代用户执行操作时，外部不可信内容可能沿着提示词、工具链和权限链逐级放大影响[3][4][12]。更关键的是，这些风险已经不再停留在实验室。来自真实网络遥测的研究表明，网页型间接提示注入已经从概念验证走向在野利用，攻击者会利用隐藏页面结构、样式欺骗、运行时拼装和社会工程等方式影响智能体决策[5]；面向间接提示注入的基准与防御研究也表明，外部内容、检索结果和网页上下文会显著改变模型执行路径[11]。与此同时，以模型上下文协议（MCP）为代表的开放协议正在把外部资源、提示模板和工具调用标准化接入智能体系统，安全边界也随之延伸到资源暴露、工具描述、授权和追踪等多个层面[6][7]。

2026 年 5 月的 Pwn2Own Berlin 把这个变化推到了更醒目的位置。赛事现场累计挖出并攻破 `47` 个唯一零日漏洞，总奖金达到 `1298250` 美元；更值得注意的是，AI 产品从边缘类别进入核心攻击靶标，OpenAI Codex、LiteLLM、LM Studio、Ollama、Cursor、NVIDIA Megatron Bridge、Chroma 等产品或组件均被列入攻击面[34][35]。这类事件传递出的信号很直接：AI 产品的安全问题已从“模型回答是否可靠”扩展到“代理、插件、工具、协议、数据库、本地推理环境和主机执行边界是否可靠”。其中多起成功利用都围绕信任边界展开，攻击者并不需要从零发明新的漏洞类型，只要找到 AI 系统连接外部工具、SDK、网络、文件或执行环境时的边界缝隙，就可能把普通输入转化为代码执行、越权访问或敏感数据泄露。

Skill 生态的公开审计同样说明了问题的另一面。腾讯云安全团队对 SkillHub 平台超过 `30000` 个第三方技能开展安全审计后发现，技能市场的风险已经从传统依赖投毒扩展到自然语言指令劫持、权限配置劫持、模式绕过、远程下载执行和静默数据外传[36]。在 `35` 个确认恶意技能中，`74.3%` 涉及提示词注入或指令劫持，`60.0%` 涉及自动命令执行，`42.9%` 涉及恶意下载或远程执行；可疑技能中，供应链风险、网络请求、代码执行、数据外传和文件系统风险也大量并存。这个案例与 vibe coding 场景高度相似：开发者以为自己只是在调用一个辅助能力，实际引入的是一段能够影响智能体行为、权限和工具调用链的外部输入。

上述两个案例共同指向一个现实判断：AI 应用的安全边界已经从“代码有没有漏洞”变成“页面、提示词、技能、工具、权限、浏览器动作和后端接口如何共同形成运行面”。嫘祖鉴丝的命名正来自这一判断。“鉴丝”强调从一缕线索中辨别整条关系链：一个本地字段、一段提示词、一项工具权限、一条外部请求或一次浏览器动作，单独看可能只是普通实现细节，连起来就可能成为风险链。平台要做的，是把这些分散线索织成可审查、可验证、可整改的安全证据链。

这两个案例也把作品的现实价值推到了台前。Pwn2Own Berlin 2026 显示，AI 产品已经成为高水平攻击者集中研究的靶标；SkillHub 审计显示，技能生态正在形成新的供应链与指令链风险。二者夹在一起，正好覆盖 vibe coding 的两端：一端是开发者用 AI 更快地产生页面、接口和工具调用链，另一端是攻击者同样借助 AI 更快地寻找信任边界裂缝。安全能力如果仍停留在“人工读代码、事后写报告”的节奏，就会被生成式开发速度甩开。嫘祖鉴丝要解决的核心问题，是让安全审查也具备可调用、可验证、可回送、可复测的工作流形态。

进入 2026 年 4 月，头部大模型厂商已经把网络安全视为高能力模型受控落地的重要场景。Anthropic 于 2026 年 4 月 7 日发布 Project Glasswing，面向关键软件防御场景开放 Claude Mythos Preview 试用入口；OpenAI 于 2026 年 4 月 14 日扩展 Trusted Access for Cyber（TAC），并推出面向防御任务更宽松的 GPT-5.4-Cyber，同时强调身份验证、信任信号、分层授权与审计问责[13][14]。这表明行业关注点正在从“模型是否更强”进一步转向“高风险安全能力如何在可信访问和受控部署条件下进入真实工作流”。

回到网页生成这一具体应用层面，相关风险已经不再停留在概念讨论，并在多种真实场景中持续出现。教师、课程团队和外包开发者开始用 AI 生成课程页面、实验平台、作业管理页和对话助手；开发者和中小团队也越来越多地直接使用 AI 生成前端页面、连接后端服务并对外发布。AI 生成网页带来的安全问题，已经随着这些实际使用方式进入日常教学系统和面向用户的产品交付链。

以教学场景为例，OpenAI 已面向教师推出专门工作区，明确提出教师已经成为最活跃的 AI 使用群体之一；SparkLearn 等产品也已经支持上传 PDF、Word、PPT 后由 AI 自动生成课程内容与文章[15][16]。这意味着教师、课程团队和外包开发者可以在很短时间内生成带有页面入口、课程路由、文件上传、对话助手和角色页面的教学系统。例如在真实课程实践中所接触到的一套 AI 教材系统里，首页之外还并列存在 AI 助理、智能体对话、教员主页、学员列表、学员详情等入口，页面状态、本地存储和学习进度接口直接在同一套前端中联动；这类系统一旦边界处理不足，问题就会很快从课程内容页延伸到真实业务状态。

这一类应用上的公开研究已经给出了令人警醒的数据。SAFECOMP 2024 的一项研究以 GPT-4 零样本生成的 `2500` 个 PHP 网站为对象，结合主动扫描、静态分析与人工复核开展系统评估，结果触目惊心：共存在 `2440` 个脆弱参数，**`26%` 的站点至少存在一个可通过 Web 交互利用的漏洞，文件上传场景的不安全比例更高达 `78%`**[17]。该研究对象虽然面向通用 PHP 网站，但其暴露的问题类型与课程网站、教学实验平台、作业管理页常见功能高度重合，尤其集中在参数处理、上传约束和输出环节。这说明，这类场景中的风险既来自开发者自身疏漏，也来自 AI 生成过程把关键缺陷一起带入系统。因此，面向这类教学应用的安全复核，必须从传统代码检查扩展到对 AI 生成页面、接口和运行状态的联合审查。

类似问题在面向公众交付的生成式建站和智能表单产品中也已出现公开事件，且已进入国家漏洞数据库。NVD 收录的 `CVE-2025-48757`（记录中带有 disputed 标记）显示，围绕 Lovable 生成站点的数据访问边界已经出现公开安全争议：在部分部署方式下，generated sites 关联的数据接口可能因数据库行级安全策略不足而暴露未授权读取与写入风险[18]。**这类问题暴露出的核心矛盾，是“快速生成前端界面 + 默认连接后端服务 + 直接发布为可访问应用”这一交付链会把权限边界错误批量带入真实项目。** 类似地，NVD 记录的 `CVE-2026-0996` 显示，Fluent Forms 的 AI Form Builder 组件曾因权限与输入处理不足引入存储型 XSS 风险[19]。从研究讨论到公开漏洞披露，AI 生成网页的安全问题正在跨过”假设性风险”的门槛。

对开发者而言，这一变化会直接改写开发流程本身。OpenAI 在 2026 年 3 月发布 Codex Security 研究预览时，已经明确把”项目级威胁建模—漏洞发现—隔离验证—补丁建议”组织为一条面向开发流程的安全协同链路[22]。然而，一个常见误解是”AI 会写代码”等同于”AI 会主动把代码写安全”。事实恰恰相反：Sajadi 等人在 2025 年的研究中发现，**Claude 3、GPT-4、Llama 3 在面对包含脆弱代码的编程问题时，主动识别并警告漏洞的比例仅为 12.6% 至 40%**[20]；Wang 等人提出的 CodeSecEval 也显示，当前模型在安全代码生成与修复任务中仍会频繁遗漏关键安全问题[21]。这意味着，AI 帮你写得更快，但不会帮你写得更安全。

更深层的变化已经出现：**安全正在从”上线前审计”前移为”开发时常驻”**。在新的开发方式下，完成功能实现之外，还必须同步考虑提示词约束、工具权限、页面状态和接口信任边界；开发者也需要具备基本的安全意识和工程常识，并能够借助 AI 完成代码审查、漏洞分析和风险定位。更现实的问题也随之转向：**在能够发现并证实风险的前提下，安全结果能不能在同一条 AI 工作流里继续驱动下一轮修改。** 这也意味着，**更具竞争力的开发者，必须既写得快，又能借助 AI 把系统写得更稳、更难被滥用。**

归结起来，AI 网页安全问题已经同时具备三个不可回避的特征：**风险边界确实变了——审查对象从代码扩展到提示词、工具和信任链；真实案例已经出现——从公开研究到 CVE 披露，从教学系统到公开建站产品；开发方式也已经被改写——安全必须嵌入生成式修改的每一轮循环。** 因而，真正需要回答的是一条完整链路能否成立：**能不能在复合运行面中发现并证实高价值风险；又能不能把确认结果继续送回正在运行的 AI 开发现场。**

表 1-1 对比了传统网页应用与 AI 网页及轻量智能体应用在风险维度上的主要差异：

| 风险维度 | 传统网页应用 | AI 网页与轻量智能体应用 |
|:---|:---|:---|
| 审查对象 | 前端代码 + 后端接口 | 前端代码 + 后端接口 + 提示词 + 工具/能力权限 + 页面助手行为 |
| 输入来源 | 用户表单、URL 参数 | 用户输入 + 外部网页/文档 + 第三方上下文 + MCP 资源 |
| 信任边界 | 前后端校验边界 | 前后端校验 + 提示词角色约束 + 工具权限范围 + 模型输出信任 |
| 风险传播 | 单点漏洞 → 局部影响 | 链式风险：提示注入 → 工具调用 → 权限放大 → 业务影响 |
| 典型新增风险 | — | 提示词注入/泄露、危险输出渲染、工具滥用、外部内容操纵 |

从表 1-1 可以看出，AI 网页场景的变化并不只体现在输入来源增多，更体现在审查对象、信任边界与风险传播路径整体外扩。

### 1.2 目标问题

围绕 AI 网页与轻量智能体应用的上线前安全复核，当前真正的难点在于：**既要把复合运行面里的高价值风险找出来、讲清楚、验证实，也要把已确认风险重新接回开发者正在使用的 AI 编程工作流。** 具体到实践层面，这一难点表现为四类环环相扣的断点：**看不全、讲不清、证不实、改不顺。** 它们彼此牵连，构成一条因果链：对象看不全，就难以把风险讲清；风险讲不清，就更难把验证做实；验证做不实，就难以形成足以进入开发流程的整改交付。

**（1）看不全：审查对象不完整。** 传统前端安全工具擅长发现代码级缺陷和部分业务逻辑问题，但缺乏将提示词规则、页面助手行为、工具/能力权限纳入同一次检查的能力；通用智能体安全测试工具又往往脱离真实网页页面和业务语境，无法还原页面、提示词与工具共同作用后的实际运行状态。两类工具之间因此形成系统性盲区。举例来说，一个前端扫描器可以发现某个接口缺少参数校验，却未必意识到该接口参数值实际来自页面智能体的模型输出，而该输出又可能受到外部提示注入的影响。只看代码或只看提示词，都会遗漏这类跨层耦合形成的风险入口。

**（2）讲不清：风险分析缺少统一主线。** AI 网页中的高价值问题往往由页面逻辑、角色约束、工具能力和输出传播共同构成链式风险。以实测某高校 AI 教材系统中出现的请求篡改问题为例，一个“学号字段可篡改”本身未必足够严重，但当该字段继续被页面带入 `get_progress.php` 接口，而服务端又直接信任这一前端传值并返回对应学习进度时，风险就从“前端参数可改”演化为“真实业务状态可被任意读取和冒用”。再以提示词注入问题为例，一段外部恶意提示本身并不直接构成泄露，只有当它进入页面智能体上下文、被高权限角色误认为有效指令，并进一步影响回答或触发工具调用时，才会升级为真实风险。现有方法通常只能分别发现代码问题或提示词问题，难以解释这些问题在同一业务链路中如何叠加形成可达风险。

**（3）证不实：结果验证不足。** 大量分析结论停留在“疑似风险”层面，缺少真实页面中的受控验证、过程证据和结论回写。一个典型场景是：安全工具报告了多个“可能存在的问题”，但开发团队无从判断哪些是真实可达的，哪些只是理论上的可能性。阅读者看到的往往是一份缺少证据支撑的“可能性清单”，既难以直接进入缺陷流转，也难以服务于项目验收、整改优先级排序以及后续版本复核。

**（4）改不顺：结果难进入开发流程。** 即便少数工具已经能够给出风险条目，这些结果也常常停留在报告层，难以进一步整理为开发者或 AI 编程助手可继续使用的整改输入。对于 AI 生成页面、接口和页面助手逻辑的场景而言，这个问题会更加突出，因为问题发现之后，下一轮修改动作本身往往仍由 AI 参与完成。现实开发中，团队往往需要在“AI 编程助手会话、源码工程、安全报告、测试记录”几套界面之间来回切换，手工摘取问题描述、重写修补要求、再补一份复测说明；这个过程不仅耗时，也极易丢失上下文，使安全结论重新退化成一段需要人工转述的备注。更关键的是，现有结果通常缺少一种能被 AI 编程工作流直接消费的整改输出，开发者很难把一条确认风险直接变成下一轮可执行的修改动作。实际需要的是一组可回送开发现场的整改输入，包括修补约束、复测要求和验收依据。只有这样，安全审查才能不再停在工作流外部，并自然衔接后续修改。

因此，本作品解决的是一条从 **发现、证实到整改回送** 的完整链路：既要在复合运行面中把高价值风险发现出来并给出可信证据，也要让确认后的风险立刻进入下一轮修改。具体而言，需要把页面代码、提示词配置、页面助手行为、工具/能力接口、权限边界和浏览器真实交互统一纳入同一条审查链路，把高价值问题推进到真实浏览器中的受控验证阶段，并将已确认结果整理为可直接进入后续修改、复测与回归流程的整改交付。对 AI 编程场景而言，这组交付不仅要”能看懂”，更要 **”能直接被 AI 编程助手继续执行”**——这正是本作品提出安全审查技能机制的出发点（详见 1.3）。前述公开研究和公开漏洞事件共同表明，AI 生成开发带来的风险已经不再是概念层面的推测，并进入了可部署、可利用、需要上线前复核的现实阶段。

### 1.3 作品概述

针对上述四类断点，本作品设计并实现了 **嫘祖鉴丝-面向 vibe coding 范式的Web与智能体安全审查验证平台**。平台面向“网页前端 + 提示词 + 页面助手/轻量智能体 + 工具/能力调用 + 浏览器真实交互”这一复合对象，采用端到端流程化方式组织目标接入、运行面重建、联合审查、真实验证、整改交付与回归复核，服务于 AI 网页上线前安全复核，也服务于生成式开发场景中的问题修补与复核。

与将代码检查、提示词测试、验证取证分散开展的常见做法相比，本平台把页面结构、提示词配置、工具能力和真实浏览器交互统一纳入同一条可追踪的安全审查链。这样，平台既能识别问题，也能在真实页面中补齐证据，并把确认结果整理成研发、测试和项目沟通都能继续使用的整改交付。原本分散在扫描结果、测试记录和人工备注里的信息，也因此被收束为一条可连续阅读、可继续执行的安全链路。

平台的关键价值，在于把确认后的风险组织为可回送开发现场的结构化整改输入。开发者拿到的是一组能继续推动修改的内容：风险为什么成立、失败边界在哪里、应从什么位置修改、修改时要守住哪些约束、修完以后怎样复测。平台输出的 `RemediationBundle`、修补提示词和复测计划，可以被开发者直接阅读，也可以回到 AI 编程会话中，作为下一轮修改的输入。

在实现上，平台以任务编号 `task_id` 串联全过程：先重建运行面对象 `RuntimeSurface`，形成结构化发现项 `Finding`，再对高价值问题建立 `ValidationSession` 并采集证据，最后由审计/整改输出模块生成统一中文报告材料和 `RemediationBundle`。`UnifiedReport`、`RemediationTicket`、`RetestRun` 和 `RegressionCase` 在本文中是交付语义名称；当前源码没有为它们分别提供独立服务类，整改、复测和回归主要通过 API 模型、CLI/Python 和目录材料表达。

平台核心特点可以归纳为三个关键词——**统一、证实、回送**：

1. **统一运行面（解决”看不全”）。** 平台把网页代码、提示词、工具权限和页面状态统一纳入 `RuntimeSurface` 对象，为后续分析提供完整的审查基底。
2. **会话化验证（解决”证不实”）。** 平台将高价值风险推进到真实浏览器中的 `ValidationSession`，用截图、网络日志、状态差异和输出痕迹做证据收口，让结论建立在可复核证据之上。
3. **整改结果可回送开发工作流（解决”改不顺”）。** 平台把整改包、修补提示词和定向复测要求组织为可执行输入；在需要时，这些结果还可以直接回到当前开发会话，使已确认问题衔接下一轮生成、修改与复测。

**平台工作链：**

> **目标接入 → 运行面重建 → 联合审查 → 风险分级 → 自动/人工联合验证 → 证据归档 → 报告输出 / 整改交付 → 定向复测 → 多靶场回归**

上述工作链描述的是平台内部的执行顺序。从开发者视角看，安全审查技能是嵌在 AI 编程会话里的 **“送检入口 + 结果回传口”**。开发者提供目标页面、源码位置、提示词配置、工具说明和验证范围，技能把这些信息整理为审查任务并提交给平台；平台完成运行面重建、联合审查、受控验证、证据归档和整改生成；任务结束后，技能把整改包、修补提示词和复测要求带回原会话，使 AI 编程助手可以在原上下文中继续修改。

> 图 1-1（文字流程）：项目/Skill 接入 → VRTM 运行面 → 静态与 LLM 审查 → 授权 Harness 验证 → 整改包 → CLI/Python 复测。原报告引用的 SVG 资产未随当前仓库交付，以文字流程为准。

这种接入方式直接对应 1.2 中“改不顺”的核心断点。开发者不需要在“AI 编程助手、源码工程、安全报告、测试记录”之间来回切换，平台把“问题发现 → 问题解释 → 修补指导 → 复测要求”压缩为一次调用后的结构化返回。AI 编程助手可以据此继续生成补丁代码，开发者审阅修改结果后触发定向复测；复测通过后，相关风险路径再进入回归基线。

在实际包装上，平台当前只提供一个 `vibe-sec` Skill 接入开发会话。它负责把当前会话中的目标地址、工作区路径、源码范围、提示词说明、工具说明、权限说明和业务背景整理为平台任务，并把整改摘要、修补提示词、复测计划和验收条件作为命令输出返回。整改回送目前不是独立 Skill，也没有外部桥接服务；开发者或 Agent 通过 CLI/API 或前端本地状态读取这些结果。

因此，面向开发者的使用体验可以被包装为一句话：**“把当前 AI 生成页面送检，返回可直接交给 AI 编程助手执行的修补与复测要求。”** 在背后，单一 Skill 把自然语言会话中的上下文规范化成平台任务，平台完成运行面重建、风险链解释、受控验证和证据归并；结果通过 CLI/API 或前端展示返回，开发者再决定是否交给当前 Agent 执行。这使安全审查前移为 vibe coding 工作流中的质量门禁，同时不虚构外部自动回调。

技能层的边界也很明确：它不直接重建运行面，不直接生成风险结论，不直接替代验证执行器。它只解决“开发会话如何进入平台”和“平台结果如何回到开发会话”这两个连接问题。真正的安全判断、受控验证、证据归档和报告生成仍由平台主体完成。这样的边界避免把复杂状态机塞进会话脚本，同时保留了一句话调用的易用性。

从实际使用方式看，平台面向三类典型场景。第一类是研发自测，开发人员在页面上线前接入网址、源码包、提示词和工具说明，完成运行面识别与高价值风险初筛，使安全工作前移到研发阶段。第二类是测试复核，测试人员围绕重点问题查看验证会话、网络证据和页面截图，判断哪些结论可以直接进入缺陷流转。第三类是项目交付，项目负责人、测试负责人或验收人员能够在同一个任务编号 `task_id` 下连续查看运行面、发现项、验证样例和报告，减少跨系统、多格式材料的人工汇聚成本。平台既服务于“发现问题”，也服务于“解释问题、证明问题和推动修补”。

从交付形态看，平台输出一组可直接进入验证、整改与复测流程的结构化结果；在需要接入 AI 编程工作流时，这组结果也可以直接回送到当前开发会话：

1. **统一运行面对象** `RuntimeSurface`，回答“目标系统的关键边界由哪些要素构成”；
2. **统一发现项主表** `Finding`，回答“当前目标中哪些问题值得优先关注”；
3. **验证会话与证据对象** `ValidationSession / EvidenceBundle`，回答“哪些高价值问题已在真实页面中得到验证、证据位于何处”；
4. **统一中文报告与整改输出**（报告材料 / `RemediationBundle`），回答“哪些问题已确认、应从何处修改、修补后应如何复测”。`UnifiedReport` 是本文的报告语义名称，不表示当前源码存在同名服务类。

这四类资产共同构成平台的最小交付单元，也为多靶场回归、误报校准和版本复核提供稳定基础。归结起来，平台把扫描结果、验证记录和修复建议压缩到同一条任务链中，使其以可验证、可整改、可复测的方式被连续交付；当需要贴近 AI 开发流程时，这组交付结果还可以自然回到当前开发会话，继续驱动下一轮修改与复测。

AI 网页的安全对象已由“前后端代码”扩展为覆盖页面入口、提示词、工具权限、浏览器状态与业务接口的复合运行面。系统围绕这一复合运行面建立任务对象、风险链、验证会话、证据包、整改包和回归基线，使安全结果能够在真实开发场景中继续流转。

### 1.4 作品价值

本作品的价值，体现在围绕 AI 网页从上线前复核到持续修补形成的一条层层递进的价值链路：**直接价值——让安全结果进入 AI 修改；落地价值——让复核、整改与复测一体化；方法价值——为复合运行面提供统一视角；长期价值——把一次审查验证沉淀为可复用资产。** 对于这类新型系统，真正稀缺的是能否把复杂风险转化为研发、测试和项目沟通都能直接使用、并能继续推动后续修改的统一结果。

**（1）直接价值：让安全结果真正进入下一轮 AI 修改**  
当前大量团队已经习惯在 AI 编程助手中完成页面生成、接口改写和组件调整，但安全工具给出的仍常常是一份停留在工作流外部的报告。开发者需要自己把问题翻译成下一轮提示词，再补一份复测说明，既慢也容易漏掉关键约束。平台补上的，是安全发现进入 AI 修改链路的关键衔接点：确认风险后，平台直接返回 `RemediationBundle + ai_patch_prompt + retest_plan`；在需要时，这组输出还可以继续回到当前开发会话。这样，整改动作天然带上修补约束、复测计划和验收边界。

**（2）落地价值：让复核、整改与复测处于同一任务链**  
在直接进入修改之后，平台进一步补足了 AI 网页上线前安全复核与整改支持的实际缺口。当前常见做法要么偏向代码检查，要么偏向提示词测试，缺少一套能够把页面、提示词、工具权限和页面助手行为放在同一次复核中的方法，也缺少一套能够把已确认问题继续转化为整改输入的统一出口。本作品面向开发团队、测试团队和项目验收环节，提供了一套贴近实际交付流程的安全审查验证方案，使风险条目、成因定位、验证过程、整改建议和复测要求能够在同一任务链上被连续查看和使用。

**（3）方法价值：为复合运行面提供统一分析与验证视角**  
之所以能够把前述流程真正串起来，关键在于平台为复合运行面提供了统一分析与验证视角。AI 网页的风险会同时分布在页面结构、业务状态、提示词装配、工具调用和浏览器交互的组合关系里。本作品的意义，在于把原本分散的代码问题、提示词问题和交互问题放回同一上下文中理解，并进一步把高价值问题推进到真实浏览器中的受控验证阶段，从而更接近真实系统中的风险形成方式。

**（4）长期价值：把一次审查验证沉淀为可复用资产**  
在流程打通和方法稳定之后，平台进一步把一次审查验证沉淀为可持续复用的工程资产。传统安全测试结果往往停留在一次性报告或临时截图中，后续版本很难直接复用。本作品将运行面对象、发现项、验证会话、整改输出和回归基线统一挂接到任务对象链之下，使同一类问题能够在不同版本和不同目标场景中持续复核。随着样本和任务不断积累，平台能够逐步沉淀形成风险条目库、验证证据库、整改模板库和回归基线库，为后续整改验收、版本复测和工作流复用提供稳定参照。

从协同角度看，上述四层价值汇聚为一个核心转变：**将安全讨论从”经验判断”拉回到”对象、过程和证据”**。研发可以基于运行面理解问题落点，测试可以基于验证会话复核问题可达性，项目负责人或验收人员可以基于统一中文报告判断风险边界和整改优先级；开发者和 AI 编程助手则可以基于整改输出继续完成修补、复测与回归。

对开发者个人而言，这也对应着一种更现实的能力升级路径：在 AI 可以帮你写得更快的时代，真正的竞争力不只在于”会写功能”，还在于 **”会借助 AI 把系统写得更稳、更难被滥用”**。本作品所提供的，正是支撑这种能力升级的基础设施。

## 二、设计思路与系统架构

### 当前实现核对：Skill 化接入设计

#### Skill 的定位

Skill 是编码 Agent 与平台之间的安全工作协议，不是一个模型提示词集合。`skill/SKILL.md` 定义什么时候触发平台、如何识别项目根、如何处理证据缺口、如何返回整改包和如何运行复测；CLI、REST API 和 Harness 负责真正的状态、权限和证据。

#### 安装与发现

仓库提供跨平台安装器：

```powershell
scripts/install-agent-skill.ps1 -Agent codex
scripts/install-agent-skill.ps1 -Agent claude-code
scripts/install-agent-skill.ps1 -Agent project
```

```bash
sh scripts/install-agent-skill.sh codex
sh scripts/install-agent-skill.sh claude-code
sh scripts/install-agent-skill.sh project
```

安装器默认不覆盖已经存在的 Skill。`-Force` 或 `--force` 是显式更新确认。Skill 目录包括 `SKILL.md`、`metadata.json`、`agents/openai.yaml` 和渐进式 references；安装器不把 API Key、项目内容或当前 RunSession 复制到 Agent 目录。

#### Skill 输入合同

Skill 接收的输入不是一句“帮我找漏洞”，而是一组可以进入审计的结构化字段：

```json
{
  "entrypoint": "skill-audit",
  "project_path": "/workspace/demo",
  "changed_files": ["src/auth.py", "package.json"],
  "scope": {"web_vulns": true, "agent_vulns": true, "secret_leaks": true},
  "use_llm": true,
  "container_tools": false,
  "dependency_network": false,
  "authorization": {"allow_service_start": false, "allow_poc_execution": false}
}
```

`changed_files` 是审查种子，不是审查边界的唯一来源。平台会沿调用者、被调用者、配置、路由、工具注册和数据流扩展上下文；同时保留原始变更范围，防止扩展后的审查被误写成“用户要求修改所有文件”。

#### Skill 输出合同

`skill-audit` 输出 `vibe-sec.skill-result.v2`。主要字段包括 `trigger_decision`、`scope`、`audit_executed`、`audit_summary`、`returned_packages`、`session`、`full_result_ref`、`vrtm_snapshot`、`runtime_graph_observations` 和 `vrtm_evolution`。

如果 `audit_executed=false`，结果只说明触发建议，不得显示为“审查通过”。如果 `returned_packages` 中存在 `needs_evidence`，Agent 必须在上下文中保留证据缺口，不能将其改写为确认或修复。

#### RunSession 设计

RunSession 是 Skill、审查、验证和整改之间的连接对象。它不是普通日志，而是可恢复的工作状态和证据索引：

```json
{
  "schema": "vibe-sec.skill-session.v1",
  "run_id": "run-<stable-id>",
  "project_id": "project-<id>",
  "phase": "audit",
  "status": "running",
  "scope": {"mode": "project", "changed_files": []},
  "authorization": {"allow_service_start": false, "allow_poc_execution": false},
  "events": [],
  "checkpoints": [],
  "artifact_refs": [],
  "parent_session_id": null
}
```

事件包括 `session_started`、`project_resolved`、`vrtm_built`、`candidate_registered`、`review_started`、`tool_completed`、`verification_authorized`、`remediation_returned`、`retest_completed` 和 `session_closed`。检查点保存状态机状态、待处理工具调用、已消费证据、任务计数和上下文窗口摘要。凭据、供应商原始错误和未经脱敏的模型异常不进入持久化事件。

#### 高权限编码 Agent 接入

高权限 Agent 可能拥有写文件、执行命令、启动服务、访问密钥或修改部署配置的能力。平台将修复权限拆成四个门：范围门、语义门、审批门和复测门。整改包列出允许修改的文件、符号、配置键和测试目录；修改必须满足 Finding 的修复谓词；高风险包必须由本地操作者批准；修改后必须通过正向安全控制、负向攻击控制、项目测试和 VRTM 变化分析。

Agent 可以生成 patch，也可以根据 `ai_patch_prompt` 选择修复方式，但不可以修改 `verification_status`、伪造 Harness 记录、扩展授权目标、删除负向控制或把失败任务标记为 completed。








### 当前实现核对：当前系统总体架构

#### 逻辑分层

当前实现由八个逻辑层组成。层之间通过结构化对象和事件通信，模型输出不能越过控制层直接改变执行权限。

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Agent 接入层                                                        │
│ Codex / Claude Code / 项目级 Agent / REST API / Web UI               │
├─────────────────────────────────────────────────────────────────────┤
│ Skill Contract 层                                                   │
│ trigger_decision / RunSession / returned_packages / retest          │
├─────────────────────────────────────────────────────────────────────┤
│ 编排与状态机层                                                      │
│ Orchestrator / AgentTaskLoop / StateTransition / Checkpoint          │
├──────────────────────┬──────────────────────┬───────────────────────┤
│ 静态与语义审查层      │ VRTM / RuntimeSurface │ LLM ReAct 层          │
│ AST / patterns /      │ 图构建、威胁假设、   │ 多轮证据、工具调用、    │
│ framework semantics   │ 变化分析、投影视图   │ 终态合同与失败降级      │
├──────────────────────┴──────────────────────┴───────────────────────┤
│ Harness 验证层                                                       │
│ 授权、服务/浏览器/沙箱验证、正负控制、清理与证据抽取                  │
├─────────────────────────────────────────────────────────────────────┤
│ Tool Fabric 与权限策略层                                             │
│ read_source / trace_flow / scanner / browser / network allowlist     │
├─────────────────────────────────────────────────────────────────────┤
│ 持久化与报告层                                                       │
│ SQLite API state / RunSession / ArtifactStore / JSON / Markdown / UI  │
└─────────────────────────────────────────────────────────────────────┘
```

#### 控制面、执行面、证据面

控制面决定“允许做什么”，执行面执行已经被允许的动作，证据面记录“做了什么和观察到什么”。三者不能合并，否则 LLM 或被测项目文本可能通过提示注入改变权限。

控制面包括 Project 范围、ToolSpec 风险级别、PermissionPolicy、Harness authorization、approval gate、LLM review budget、verification count 和 RunSession 状态转移。控制面是平台信任根的一部分。

执行面包括源码读取、Python/JavaScript/TypeScript 数据流追踪、VRTM 图构建、静态扫描器、浏览器验证器、服务验证器和清理动作。每一个执行动作通过 ToolGateway 注册、策略检查、记录和结果规范化。

证据面包括代码位置、输入输出摘要、工具执行审计、HTTP/浏览器观察、验证谓词、正向控制、负向控制、修复前后差异、artifact ref 和时间戳。证据面可以被报告读取，但不能反向修改控制面。

#### 组件与代码边界

| 组件 | 当前实现位置 | 核心职责 | 可信度边界 |
| --- | --- | --- | --- |
| CLI | `main.py` | setup、doctor、audit、skill-audit、model、retest | 用户调用入口，不能绕过 Harness |
| REST API | `api/server.py` | 项目、任务、Finding、模型、整改、验证接口 | API 状态持久化，验证写入需要 token |
| API State Store | `api/state_store.py` | SQLite 持久化任务、Finding、配置 | 不存储模型原始错误；凭据只作为内部配置 |
| Orchestrator | `core/orchestrator`、`agents` | 阶段编排、候选合并、验证和整改 | 维护流程状态和任务关系 |
| ReAct Runtime | `core/agent_runtime` | LLM 消息、工具批次、终态合同、预算 | 不信任模型工具调用内容 |
| VRTM | `core/vrtm`、`core/surface` | 运行面、威胁模型、快照和差异 | 声明与观测分离，未经 Harness 不升级 |
| Tool Fabric | `core/tool_fabric` | ToolSpec、Gateway、Adapter、执行审计 | 只暴露经过策略筛选的工具 |

| Skill | `skill` | Agent 方法论、命令契约和输出协议 | Skill 不能替代平台控制器 |

#### 数据流与边界

一个典型审查请求的数据流如下：

```text
用户/Agent
  │  项目路径、变更文件、审查选项、授权范围
  ▼
Skill Trigger
  │  生成 scope、RunSession、trigger_decision
  ▼
Project Resolver
  │  确认项目根、相对路径、状态目录和排除项
  ▼
VRTM Builder ───────────────┐
  │ graph + hypotheses       │
  ▼                          │
Static/semantic lanes        │
  │ candidate findings       │
  ▼                          │
Global review allocator      │
  │ severity/confidence/order│
  ▼                          │
LLM ReAct Audit              │
  │ read-only evidence       │
  ▼                          │
Finding binding              │
  │ immutable fields + gaps   │
  ▼                          │
Harness authorization ──────┤
  │ service/browser/sandbox  │
  ▼                          │
Evidence bundle + VRTM obs ◄┘
  │
  ▼
Remediation package → Agent → approval → retest → closure
```

数据流的关键约束是：候选可以被 LLM 解释，但不能被 LLM 任意改写；模型可以提出 PoC 计划，但不能由模型单独启动服务、写文件、执行命令或把 Finding 置为 `verified`；整改包可以被编码 Agent 读取，但高风险修改必须经过确认门和变更范围检查。

#### 可部署形态

平台有三种运行形态。第一种是本地 Python/CLI 形态，适用于开发者在自己的工作区执行源码审查、VRTM 和 Skill。第二种是本地 Web/API 形态，API 使用 SQLite 和 RunSession，前端使用 Vite/Vue，适用于团队共享审查结果。第三种是 Docker Compose 形态，`web` 提供前端和反向代理，`api` 提供后端与 CLI，`audit` profile 提供无头命令执行。

Docker 默认不挂载 Docker Socket，不把平台容器变成宿主机的高权限执行器。容器扫描器需要宿主机授权 Runner，是因为外层 Docker 看到的 `/workspace` 与宿主机路径必须做一致映射，直接在容器内转发 Socket 既有权限风险，也容易产生路径错位。





嫘祖鉴丝的设计围绕一个核心判断展开：AI 生成页面和轻量智能体的安全风险具有复合性，由页面、提示词、模型上下文、工具权限、浏览器状态和后端接口共同作用形成。系统用统一对象链把目标接入、运行面建模、风险解释、会话化验证、证据整理、报告输出、整改回送、定向复测和回归治理组织为连续闭环。

系统定位为 **面向 vibe coding 范式的 Web 与轻量智能体安全审查验证平台**。直接使用者是正在通过 AI 编程助手、智能应用搭建平台、低代码智能体平台或自然语言生成方式快速搭建页面、后台、表单、课程系统和页面助手的开发者。此类开发方式强调“先让功能跑起来”，容易把认证、权限、输出渲染、工具调用、文件访问和数据边界交给默认模板或模型推断。嫘祖鉴丝的设计目标，是在这类系统上线前把高价值风险看全、讲清、验证实，并把确认结果转化为开发者和 AI 编程助手能够继续执行的整改输入。
### 2.1 核心对象链

主对象链为：

```text
Task
  -> RuntimeSurface / RuntimeSurfaceGraph
  -> Finding / RiskChain
  -> ValidationSession / EvidenceBundle
  -> 报告材料 / RemediationBundle
  -> 整改状态
  -> CLI/Python 复测材料
  -> 回归基线（规划/目录化）
```

`Task` 是平台的任务语义根对象，承载目标入口、源码位置、业务背景、提示词配置、工具说明、权限范围和验证边界；API 层实际持久化的是 `Project`、`AuditTask` 等记录。`RuntimeSurface` 与 `RuntimeSurfaceGraph` 将输入归一化为页面入口、关键动作、提示词画像、工具画像、权限画像、信任边界、代码块索引和文件关系。`Finding` 承载结构化发现项，`RiskChain` 进一步描述风险入口、前置条件、边界失效、触发路径、可观察信号和影响结果。`ValidationSession` 和 `EvidenceBundle` 分别表示验证会话及其证据材料。报告输出、`RemediationBundle`、复测结果和回归基线是现有 API/CLI/目录材料中的交付语义，不对应一组已经拆分完成的服务类。

围绕这条主对象链，设计上可以抽象出阶段、Agent 执行、审批、指标和时间线等控制面语义；当前源码没有独立的 `StageRun`、`AgentRun`、`ApprovalTicket`、`MetricSnapshot` 或 `Timeline` 模型。现有任务状态、RunSession、Harness 事件和 manifest 共同表达这些信息，能够支撑有限的审计和复核；统一控制面与批量回归仍属于后续演进。

这条对象链使平台的每个结论都有来源、路径和后续动作。一个风险从疑似线索进入确认结论，必须经历运行面定位、风险链解释、验证会话执行和证据整理。一个确认风险进入整改，也必须携带失败边界、修补目标和复测条件。报告围绕这一对象体系呈现系统能力。

从读者角度看，这条对象链可以理解为一条“安全证据流水线”。自然语言生成开发的原始输入往往很杂：开发者的一段需求说明、几个源码目录、一段系统提示词、一个工具说明文档、一个可访问页面地址，甚至还包括临时补丁和运行日志。平台首先不急于判断“有没有漏洞”，而是先把这些杂乱材料变成同一类可计算对象。页面入口进入运行面，提示词进入提示画像，工具说明进入能力画像，权限说明进入边界画像，源码片段进入代码索引。只有完成这一步，后续智能体和规则才能围绕同一份事实材料工作。

对象链中的每一环都承担不同的证据责任。`RuntimeSurface` 负责回答“系统长什么样、边界在哪里”；`RiskChain` 负责回答“问题从哪里进入、穿过了哪条边界、为什么可能影响业务”；`ValidationSession` 负责回答“这条路径在真实页面或服务里能不能触发”；`EvidenceBundle` 负责回答“证据在哪里、能不能复核”；`RemediationBundle` 负责回答“应该怎样修、修完怎样验收”。这样组织之后，报告中的风险不再停留在笼统判断层面，能够沿着对象链回到输入、路径、验证、证据和整改。

这一设计也为多轮开发提供了稳定参照。vibe coding 中的页面很可能在一天内被 AI 改很多次，如果每一次审查都重新从零开始，安全结果就很难沉淀。嫘祖鉴丝把一次审查中的运行面、风险链、验证会话和整改包挂在同一个任务下，使后续复测可以直接复用前一轮证据和复测条件；当同类问题再次出现时，也可以基于已沉淀的回归基线快速定位。这是平台区别于一次性安全清单的重要基础。

### 2.2 分层架构

系统由五个层次组成。

第一层是前端控制台。前端采用 Vue 3 + Vite，当前路由实际包括 `Workspace`、`AuditEngine`、`ThreatModel`、`ToolFabric`、`Findings`、`Evidence`、`Remediation`、`Knowledge`、`Foundation`、`Integrations` 和 `Settings`。这些视图围绕工作区、审查引擎、运行面威胁模型、工具能力、风险发现、验证证据、整改回送和系统配置组织阅读路径。页面目前以任务结果查询、运行面展示、Finding/整改查看和本地回送状态展示为主；动态验证提交、复测启动和回归执行仍由 CLI/Python/Harness 完成。

第二层是 FastAPI 接入层。当前真实任务入口是 `/api/projects`、`/api/audit-tasks`、`/api/audit-tasks/{id}/findings`、`/api/audit-tasks/{id}/remediations`、`/api/model-configs` 和 VRTM 相关接口。旧的 `/api/tasks*`、`/api/process-task`、知识库和智能体实验路由未实现，前端仍保留部分演示回退，不能作为真实后端能力统计。

第三层是当前仓库的核心服务层，主要位于 `core/surface`、`core/vrtm`、`core/audit`、`core/verification`、`core/harness`、`core/remediation`、`core/orchestrator` 和 `api`。系统在这里完成运行面重建、静态与 LLM 审查、Finding 绑定、Harness 计划与证据、整改包和有限的 CLI/Python 复测。文档不把不存在的 `control_plane.py`、`workflow_contract.py` 或多 Agent 角色文件描述为已实现模块。

第四层是持久化与证据材料层。`api/state_store.py` 当前只在 SQLite 中保存 `projects`、`audit_tasks`、`findings`、`remediations` 和 `model_configs` 五类记录，用于项目、审计任务、发现项、整改项和模型配置的查询。RunSession、Harness 事件、浏览器证据、VRTM 快照和复现实验材料主要以目录文件、JSON/Markdown manifest 及报告形式保存，不应表述为已经全部入库。数据库提供管理页的基础查询，目录化材料提供验证复核和结果审计。

第五层是结果输出与整改衔接层。当前由报告材料、API 的 `RemediationBundle`、CLI/Skill 输出以及 `core/remediation/skill_relay.py` 组成；它可以生成面向 Agent 的整改提示、约束和复测计划，但外部修补会话桥接、前端回调和自动复测回写尚未形成完整可用链路。

五层架构之间的数据流是连续的。开发者提交目标后，接入层先生成任务并保存基础材料；核心服务层构建运行面和运行面图；审查与监控单元产生发现项并筛选验证优先级；执行层通过受控验证会话采集浏览器、接口和函数级证据；报告层将确认风险汇总为统一中文报告；回送层再把整改材料组织成开发者和 AI 编程助手都能消费的输入。前端控制台贯穿这一过程，负责把对象链展示为人可读的页面路径；持久化层则保证每次验证、复测和回归都能被追踪。

这样的分层已经支持“项目 -> 审计任务 -> 历史任务 -> Finding/整改 -> VRTM”主链路；受控验证和 CLI/Python 复测可以单独运行，但前端尚不能代表完整的动态验证、复测和 Agent 回调闭环。文档将已实现能力与待完善能力分开呈现。

### 2.3 控制面、执行面与证据面

为了适应 vibe coding 场景中“生成快、边界散、验证难、修复仍由 AI 参与”的特点，平台在五层架构之上进一步划分为控制面、执行面、证据面和回送面。控制面负责阶段编排和角色治理，回答当前任务处于哪个阶段、哪个角色已经产出共享对象、哪些门禁阻断了下一步；执行面负责把验证计划转化为受控浏览器、接口或函数级动作；证据面负责把运行结果归并为可复核材料；回送面负责把确认风险变成开发者和 AI 编程助手可以继续执行的整改输入。四个平面共同支撑一条从送检到回归的状态机。

当前实现不是一个由十余个独立角色组成的控制平面，而是 `core/orchestrator/orchestrator.py`、`core/agent_runtime`、`core/audit`、`core/verification` 和 `core/remediation` 协同完成的阶段式流程。实际存在的主要执行单元包括编排 Agent、Audit/ReAct 审查器、Verification/ReAct 审查器、VRTM 服务、Harness 和整改服务；它们通过任务状态、工具记录、Finding、验证会话和证据包衔接。`StageRun`、`AgentRun`、`orchestration_summary.py` 以及拆分式角色合同属于目标态设计，不作为当前版本实现承诺。

当前实际接力关系可以概括为：`Project/AuditTask -> RuntimeSurface/VRTM -> ReActFindingReviewer -> Finding binding -> RemediationBundle -> Validation/ReAct reviewer -> EvidenceBundle`。高风险动作由 Harness 的授权策略和验证状态机控制；审查结果不因模型自然语言而自动升级；前端只读取 API 结果，不能直接驱动受控执行。

当前实现的失败路径由 ReAct 审查降级、Finding 证据绑定、ToolGateway 策略阻断、Harness 会话失败、Provider 错误和 Remediation 状态共同组成。缺少源代码读取、相关证据或授权时，结论保留为 `potential`、`needs_evidence` 或 `unverified`；模型输出不能直接写入 `verified`。前端或旧 API 缺失时，任务本身仍可通过 CLI/Python 结果审计，但不会伪造为已完成闭环。

执行面的核心是 `HarnessRuntime` 与浏览器执行器。`HarnessRuntime` 维护验证会话、步数预算、权限策略、工具注册和事件回调；每一步执行前都会根据工具名、目标地址和关键动作做策略检查，遇到越权域名、禁用工具或高风险动作时进入阻断或审批流程。浏览器执行器基于 Playwright 适配器提供 `goto`、`click`、`fill`、`extract_text`、`screenshot`、`evaluate` 和 `collect_requests` 等动作，并将截图、文本、网络请求、脚本执行结果、助手输出和状态差异转化为证据。这样，平台可以在真实页面里验证“按钮是否触发请求”“脚本是否执行”“本地身份篡改是否影响后端读写”“工具调用是否越过权限边界”，让结论建立在静态代码、模型判断与运行证据的共同支撑上。

证据面的核心是 RunSession/Harness 会话文件、浏览器执行器结果和证据 manifest。当前仓库没有独立的 `ValidationSessionManager` 或 `EvidenceStore` 服务类；会话创建、步骤执行、事件记录和证据归并由 `core/session`、`core/harness`、`core/verification` 及相关 CLI/Python 入口协同完成。截图、DOM/页面结构、网络日志、助手输出、工具调用轨迹和状态差异会写入会话目录，供报告、整改和复测脚本读取。三态复现实验中的漏洞态、修复态和合法控制，也是在这些目录化材料中组织为可比较的证据集合。

这四类平面共同支撑平台的技术创新：控制面使多智能体审查可治理，执行面使浏览器和服务级验证可落地，证据面使结论可复核，回送面使确认风险可以继续进入 AI 编程会话。对于 vibe coding 产生的 Web 与智能体应用，这种架构比单一扫描器更适合真实流程，因为它同时处理“发现、证实、整改、复测”四个环节，并且每个环节都有明确的输入、输出、门禁和回退状态。

### 2.4 Harness 受控验证执行层

受控验证执行层是平台把模型生成的验证计划落到真实浏览器和服务接口上的关键执行层，代码中对应 `harness.py`。本报告保留 `Harness` 这个实现名，但在设计上可以把它理解为“验证沙箱 + 权限门禁 + 证据记录器”的组合。它的目标是让验证“能自动化”，同时保持任务边界、权限边界和证据边界可控。`SessionStore` 将 `validation_session_id`、`task_id`、`risk_id`、目标 URL、执行上下文、步骤日志和证据列表持久化到会话文件，并对会话 ID 做字符级校验，只允许字母、数字、点、下划线和连字符进入文件名，避免验证会话被伪造路径写到任意位置。

`PermissionPolicy` 负责把执行权限收口到明确规则中。策略同时检查禁用工具、禁用工具前缀、允许域名和关键动作；域名匹配精确比较 scheme、hostname、port，并在设置路径时要求候选路径等于允许路径或位于其子路径下。这样，`https://example.com/app` 不会被 `https://example.com.evil`、不同端口、不同协议或路径前缀伪装绕过。验证步骤执行过程中，`HarnessRuntime` 会根据上一步浏览器返回的 URL 动态更新 `current_url`，后续步骤继续使用新的上下文做权限判断；这使平台能够处理登录跳转、页面内导航、表单提交后的重定向，也能阻断跳出允许范围后的继续动作。

Harness 的运行过程按 turn 推进。每个步骤先进入 `check_step`，通过后才解析工具并执行；工具不存在会失败，策略不通过会阻断，执行异常会记录失败原因，执行成功会把标准化结果写入日志，并把返回的 evidence 追加到会话证据列表。事件回调会发出 `session_started`、`step_succeeded`、`step_blocked`、`step_failed` 和 `session_completed` 等状态，用于前端控制台、审批记录和证据包同步。这个执行层让平台可以安全地运行 `browser.evaluate`、网络采集、页面点击和服务探针，同时给每一步留下可追踪的执行记录。

受控验证执行层解决的是一个非常现实的问题：AI 可以很快生成“验证步骤”，但这些步骤不能被无条件执行。以课程系统的身份篡改验证为例，模型可能建议写入本地存储、点击保存按钮、访问进度接口；这些动作本身有价值，但如果目标地址跳转到无关域名、如果步骤要求删除数据、如果工具调用超出允许范围，就必须被阻断或进入审批。受控验证执行层把“模型建议”转化为“可执行但受约束的验证动作”，使自动化验证不会变成新的风险来源。

在真实运行时，验证会话通常包含四类步骤。第一类是准备步骤，例如打开目标页面、写入测试状态、建立基线数据；第二类是触发步骤，例如提交表单、修改参数、调用接口、触发工作流节点；第三类是观察步骤，例如提取页面文本、采集网络请求、读取状态差异、保存截图；第四类是收尾步骤，例如清理临时上下文、记录结果、生成复测依据。受控验证执行层将这些步骤统一记录为 turn 日志，使报告可以复原“验证怎么发生”，也能说明“为什么某一步被允许或被阻断”。

这个设计对智能体安全尤其重要。轻量智能体往往拥有网页访问、接口调用、文件读写或外部工具能力，验证时如果只追求自动化，很容易把验证动作本身做成越权动作。嫘祖鉴丝通过允许域、禁用工具、禁用前缀和关键动作门禁，把验证权限限制在任务合同内；通过事件日志和证据列表，把每一步执行结果写回会话。这样，平台既能证明风险，也能证明验证过程本身受到约束。

### 2.5 浏览器验证与证据抽取

浏览器验证由浏览器适配器和浏览器执行器标准化，代码中对应 `BrowserAdapter` 与 `BrowserExecutor`。适配器封装浏览器页面能力，执行器将其注册为打开页面、点击、填表、提取文本、截图、脚本求值和采集请求等受控工具。所有动作统一返回“状态、动作、结果”三类字段，便于受控验证执行层作为普通工具执行，也便于证据层把结果归并到同一个验证会话。

证据抽取并不只保存截图。文本提取会根据选择器推断证据类型，页面助手、回复区、模型输出等选择器会进入“助手输出”证据；截图会生成步骤级图片路径；脚本求值会记录表达式和返回值，并尝试从返回值中提取助手输出与状态差异；网络采集会优先保留高信号请求，例如带请求体、非只读方法、异步接口请求，并将网络日志限制在前 20 条高价值记录中。这样的处理使浏览器验证既能证明脚本是否执行，也能证明本地身份篡改是否影响接口、提示词注入是否改变助手输出、清理动作是否真正改变页面状态。

对于 vibe coding 生成的页面，浏览器验证的价值尤其突出。AI 生成代码经常把页面状态、DOM 渲染、接口调用和助手回复拼在一起；同一风险可能在源码里只是一个模板字符串，在浏览器里却变成脚本执行、身份覆盖、接口请求或模型回答偏移。嫘祖鉴丝将这些信号转为结构化证据，使报告不依赖“模型认为有风险”的描述，而依赖浏览器和服务层实际观察到的状态变化。

浏览器验证还承担“合法功能保留”的证明责任。安全修复不能只证明攻击失败，还要证明正常功能仍然可用。例如富文本风险修复后，恶意脚本应该被消毒，但安全的 Markdown 内容仍应能正常显示；身份篡改修复后，伪造学号应该失败，但真实登录用户仍应能保存自己的学习进度；文件访问修复后，目录穿越应该被阻断，但合法上传和下载仍应工作。浏览器验证把这些对照路径也纳入证据，使报告更接近真实验收标准。

与传统页面测试相比，平台的浏览器验证围绕风险链进行定向观察。每一次点击、填表、脚本求值和请求采集，都对应风险链中的某个证据谓词：是否进入危险渲染点，是否触发敏感接口，是否出现跨用户数据，是否改变助手回答，是否保留合法功能。这样，浏览器验证从附属截图升级为风险确认、整改验收和回归复测的共同证据来源。

### 2.6 技能化接入架构

当前仓库实际提供的是一个 `vibe-sec` Skill，定义在 `skill/SKILL.md` 与 `skill/metadata.json`，由安装脚本安装到 Codex、Claude Code 或项目级 Agent。它负责组织 `skill-audit`、`model`、`retest` 等命令的输入输出，并保留授权边界、证据缺口和终态状态；它不是第二个扫描器，也不直接取得执行权限。

当前 Skill 的边界是轻量入口和结果协议。真实任务接口使用 `/api/projects`、`/api/audit-tasks` 及 findings/remediations 子路径；旧的 `/api/tasks*`、`/api/process-task` 和规划中的双 Skill/桥接路由不属于当前可用接口，不应在产品演示中当作已实现能力。

技能化接入的意义在于降低 CLI 审查门槛。平台可以通过 Skill 组织项目路径、审查范围、LLM 选项和授权配置，并返回结构化审查结果、VRTM 快照引用、整改包和复测计划；前端验证提交、复测启动和外部 Agent 回调目前仍未完整接通。

从系统设计看，技能只负责触发 CLI 和传递结果，审查、验证、证据绑定和整改生成仍由平台代码完成。技能不能修改 Finding 的不可变字段，不能伪造 `verified` 或 `closed`，不能启动服务、执行 PoC、写入源码或扩大目标范围。

部署时使用 `scripts/install-agent-skill.ps1` 或 `scripts/install-agent-skill.sh` 安装单一 `vibe-sec` Skill。完整的任务创建和历史查询通过 `/api/audit-tasks` 完成；前端能够查看审计、Finding、整改和 VRTM 结果，但前端动态验证、复测回写和外部修补会话仍属于待完善能力。

整改回送当前以 API 的 `RemediationBundle`、CLI 输出和 `core/remediation/skill_relay.py` 的本地状态合同为主。仓库没有独立的 `RemediationTicket` 服务；外部修补会话桥接和前端回写尚未形成真实可用的完整路由，相关内容只能作为后续设计方向。

这种技能化形态与 Skill 生态安全案例形成呼应。公开审计显示，技能本身可能成为指令劫持、权限劫持和数据外传入口，因此嫘祖鉴丝没有把安全审查逻辑塞进技能脚本，也没有让技能直接执行任意分析和验证动作。技能只承担“整理输入”和“取回输出”的轻量职责，真正的运行面建模、风险判断、验证执行、证据复核和整改生成都留在平台内部，并受控制面和受控验证执行层约束。这样，平台既能享受技能化接入带来的低门槛部署，又避免把技能包装变成新的安全边界缺口。

### 2.7 面向现实问题的设计主线

设计主线紧贴自然语言生成开发和 AI 生成应用的真实风险。自然语言生成页面缩短了交付周期，但也让许多边界由模型和模板临时拼接决定。平台围绕六类高价值问题设计能力：身份可信源失配、数据权限边界失配、提示词和外部内容边界失配、输出渲染与缓存边界失配、工具/文件/执行环境边界失配，以及公告版本与运行行为边界漂移。

身份可信源失配对应前端字段、本地存储和后端身份之间的错位。平台通过 RuntimeSurface 找到身份字段和接口关系，通过 RiskChain 描述字段如何进入业务读写，通过 ValidationSession 执行基线、篡改、写入、读回和差异比较，通过 RemediationBundle 要求服务端登录态、令牌链或后端会话成为身份来源。

数据权限边界失配对应 workspace、owner、role、issue、project、label、agent 等对象的跨空间操作。平台通过风险链把对象 id、角色、空间、读改删动作和响应差异连起来，通过三态实验确认漏洞态可触发、修复态可阻断、同空间合法控制仍可用。

提示词和外部内容边界失配对应页面助手读取网页结构、检索结果、用户输入和第三方文档后的上下文污染。平台要求系统提示、用户输入、外部内容和工具说明分层，验证中关注提示词暴露、回答偏移、工具调用偏移和不安全渲染信号。

输出渲染与缓存边界失配对应富文本、Markdown、文件预览、SVG、音频缓存、聊天消息和头像图片等进入浏览器执行面的路径。平台通过浏览器和页面结构证据确认脚本执行，通过消毒、MIME 校验、附件响应头和安全组件验证修复效果。

工具、文件和执行环境边界失配对应 AI 工作流平台把用户输入连接到 Python、JS、CustomMCP、OpenAPI、Webhook、Git、文件读写和外部请求。平台以服务级接口、浏览器和函数级验证覆盖工具执行、文件访问、路径穿越、服务端请求伪造、符号链接逃逸和反序列化等风险。

公告边界漂移对应公开公告、版本声明和发布包运行行为之间的不一致。平台将这类目标单独记录为漂移探针，要求人工复核，不把证据不足或版本边界不清的结果并入正式三态复现成绩。

上述六条设计主线共同服务于同一个现实过程：开发者用自然语言生成页面后，系统会在很短时间内形成页面入口、后端接口、提示词、工具说明、权限设定和运行状态；风险也会沿着这些连接关系传播。身份可信源失配往往会进一步造成数据权限问题，提示词边界失配可能触发工具调用边界问题，输出渲染边界又可能把模型或用户内容带入浏览器执行面。嫘祖鉴丝因此把每一类问题都放回运行面和风险链中处理，避免只按漏洞名称做割裂判断。

以课程型 AI 页面为例，学生学号被写在本地状态中，看似只是前端实现细节；当它继续进入学习进度保存接口和读取接口时，就变成身份可信源问题；如果教师端又基于同一字段查看学生进度，还会扩展为权限边界问题；如果页面助手读取这些状态并参与回答，则提示词和输出边界也会被牵连。平台的设计主线就是要把这类跨层关系一次性看清，再决定哪些风险需要进入受控验证，哪些材料需要补充，哪些整改必须回到服务端会话、权限范围或渲染前处理。

以 AI 工作流平台为例，用户输入可能先进入聊天节点，再进入工具节点，随后触发文件、网络、代码或第三方接口能力。开发者在界面上看到的是“节点连通、流程能跑”，安全边界却分布在工具描述、节点参数、执行环境、凭据、网络出口和文件系统之间。嫘祖鉴丝将这类流程拆成入口、能力、权限、执行动作和证据谓词，使代码执行、文件访问、服务端请求伪造和凭据泄露都可以被同一套对象链解释。这样，系统架构面向的是一类快速生成应用的共性安全结构。

这也是平台选择“控制面、执行面、证据面、回送面”组合架构的原因。控制面确保多角色审查不会失控，执行面确保验证动作受到权限门控，证据面确保确认结论能够复核，回送面确保结论能够进入下一轮 AI 修改。对于 vibe coding 这种高频生成、高频修改的开发方式，安全系统如果只完成一次扫描，很快就会被下一轮代码生成覆盖；只有把审查、验证、整改和复测都纳入状态化工作流，才能跟上真实开发节奏。

## 三、系统实现

### 当前实现核对：工程部署与运行手册

#### Docker Compose 默认部署

```powershell
scripts/deploy.ps1 -Build -Detach
```

```bash
sh scripts/deploy.sh --build --detach
```

默认 Web 地址为 `http://localhost:8000`。主机目录 `projects/` 映射为容器内 `/workspace`；注册项目时使用 `/workspace/<project-directory>`，不能填宿主机 Windows 路径。默认状态卷名是 `vibe-sec-state`，保存 API SQLite、Session、Artifact 和外置 VRTM snapshot。

#### LLM Secret 部署

```powershell
scripts/deploy.ps1 -Build -Detach -LlmSecretFile C:\secrets\deepseek.key
```

```bash
sh scripts/deploy.sh --build --detach --llm-secret /run/user/1000/secrets/deepseek.key
```

Secret overlay 只把文件挂载为 `/run/secrets/deepseek_api_key`，入口脚本在启动时读取并导出给当前进程。密钥不进入镜像层、Skill 文本、`.env` 示例、RunSession、测试结果或报告。

#### Web/API/CLI 三种操作方式

Web UI 适合项目注册、任务创建、历史状态、Finding 队列、运行面图和整改包阅读。REST API 适合集成 CI、内部工作台和自定义 Agent。CLI 适合本地脚本、宿主机工具 Runner 和无头 Skill：

```bash
vibe-sec doctor --json
vibe-sec skill-audit /workspace/demo --format json --session-dir /var/lib/vibe-sec/sessions
vibe-sec model /workspace/demo --format json --output /var/lib/vibe-sec/vrtm.json
vibe-sec retest /workspace/demo --input /var/lib/vibe-sec/audit-result.json --session-id run-...
```

#### Agent 一键接入

Agent 安装器不修改已有配置，不写入凭据，提供三种目标：Codex 用户级 Skill、Claude Code 用户级 Skill 和当前项目 `.agents/skills/vibe-sec`。安装成功后，Agent 按 Skill 读取平台命令合同；如果本机没有 `vibe-sec`，可以使用源码仓库的 bootstrap 或 Compose `audit` profile。

#### 数据备份与恢复

生产或团队使用时至少备份 `vibe-sec-state` 卷中的 SQLite、session manifest、artifact index 和 VRTM snapshot。项目源码和 `.vibe-sec/vrtm.yaml` 仍由项目自己的版本控制保存。恢复后 API 会把上次进程重启时处于 pending/running 的任务标记为 failed，不会伪造为 completed。




### 当前实现核对：前端与交互设计

#### 前端视图

Frontend V2 以审查工作台为中心，不以营销首页为中心。主要视图包括项目列表、创建任务、任务历史、Finding 队列、Finding 详情、整改包、VRTM 模型和运行面图、验证会话与模型设置。

前端通过 REST API 获取项目、任务、Finding、remediation、VRTM snapshot 和 stats。前端不直接执行源码工具、不读取 LLM Key、不决定 verification status，也不绕过 API token 写验证结果。

#### 结果展示原则

Finding 列表默认按 review priority、severity、confidence 和 verification status 排序。每行显示风险类型、位置、结论状态、证据等级、重复数量、未决缺口和是否需要验证。`not_reviewed` 不混在“已审查安全”中，`needs_evidence` 用单独状态说明。

Finding 详情包含一句话结论和中文风险解释、威胁来源、风险链、代码位置、工具证据、VRTM 图节点、证据缺口、验证计划、授权要求、清理要求、整改包、修改约束、验收标准和复测入口。

#### 运行面图交互

图视图提供投影切换、节点拖动、缩放、风险链聚焦、严重度过滤、节点类型过滤、搜索、布局重置和旁栏详情。拖动后的布局可以按项目和视图保存，但布局数据与 VRTM 事实分离。图中节点数量很多时，优先显示高价值路径和聚合节点，点击聚合节点后再展开局部子图。

#### 动态验证加载状态

前端对动态验证状态的展示目前属于状态模型和演示视图，不能视为完整的 UI 验证执行器。真实验证由 CLI/Python/Harness 和受保护 API 完成；前端尚未接通完整的计划提交、动态执行、证据复核、复测启动和状态回写。后端任务重启后，未完成的后台任务会失败，用户需要重新创建或通过 CLI 恢复。







### 当前实现核对：LLM 驱动的会话验证

#### 审计与验证的区别

LLM 审计回答“从代码和运行面看，这条风险链是否合理”；LLM 驱动验证回答“在受控、授权和可清理的条件下，这条风险链能否产生预期信号”。验证不是把审计 prompt 再问一次，而是生成验证计划、选择工具、解释观测并由 Harness 决定状态。

验证会话必须指向一个 Finding、一个 RunSession、一个 VRTM 假设和一个验证谓词。没有这些引用的“模型说已经验证”不具有平台证据意义。

#### Harness 授权模型

Harness 授权对象包括目标标识、允许的服务、允许的端口、允许的浏览器页面、是否允许启动服务、是否允许执行 PoC、写入范围、清理动作、时间窗和速率限制。授权通过本地可信令牌或签名 envelope 传入，不能由项目文本、网页内容或 LLM 工具调用设置。

API 动态验证写入需要 `VIBE_SEC_VALIDATION_TOKEN`。验证状态只有在方法、结果、正控制和负控制满足契约时才能写入 `verified` 或 `rejected`。未配置验证 token 时，写入端点返回 503，防止前端直接伪造结果。

#### 三态验证方法

每一个正式验证至少包含三组动作：

| 组别 | 目的 | 示例 |
| --- | --- | --- |
| 漏洞态/候选案例 | 观察风险信号能否出现 | 恶意输入到达 sink、跨 workspace 读取、脚本执行 |
| 修复态/负向控制 | 观察修复是否阻断同一路径 | 400/403/404/422、权限拒绝、路径包含检查 |
| 合法控制 | 证明正常业务仍然存在 | 同空间读取、合法 Markdown、有效 token、正常上传 |

三态不是必须全部使用同一个 HTTP 状态码。关键是每组都绑定预期信号、实际信号、控制摘要和 evidence artifact。只有漏洞态单独成功时，状态仍可能只是 `needs_evidence`，因为无法判断修复验收和合法功能保留。

#### 浏览器和服务验证

服务级验证适合 API、认证、对象权限、文件、SSRF、工具调用和工作流。浏览器级验证适合 DOM XSS、富文本、前端身份、页面存储、渲染后脚本和跨页面状态。两者都由 Harness 控制，浏览器读取的页面文字和外部内容仅是 untrusted observation。

浏览器证据包括 URL、导航步骤、控制组、DOM 选择器摘要、脚本执行信号、截图 artifact ref 和清理结果；不把整页敏感内容或 cookies 写入报告。服务证据包括请求摘要、状态码、响应字段白名单、服务日志摘要和清理动作；不保存未授权的批量数据。

#### 会话清理

验证完成必须执行清理：删除测试用户、恢复文件、移除 vendor context、清理上传对象、还原配置、停止测试服务和删除临时 artifact。清理动作本身是证据，失败时验证会话保持 open 或 needs_evidence，并在报告中明确残留状态。

#### 验证状态机

```text
PLANNED
  │ authorization accepted
  ▼
READY
  │ positive control
  ▼
RUNNING
  ├── candidate signal + negative control + positive control ─► SUPPORTED
  ├── candidate absent but controls valid ─► CONTRADICTED
  ├── authorization/tool/runtime gap ─► NEEDS_EVIDENCE
  └── cleanup failure ─► OPEN_WITH_CLEANUP_GAP
```

`SUPPORTED` 只有在验证方法是 service、browser 或 sandbox，outcome 是 supported，且三组控制通过时才能映射到 `verified`。`CONTRADICTED` 只有在合法控制有效并且目标信号无法复现时才能映射到 `rejected`。其余情况不做二值化。








### 当前实现核对：LLM 驱动的智能审计

#### LLM 的角色边界

LLM 在平台中承担三项工作：候选证据阅读、风险链解释和整改建议生成。它不承担四项不可委托的工作：事实发现的唯一来源、权限授权、动态利用确认和高权限修改批准。

LLM 看到的上下文由平台组装，包括候选基本字段、代码位置、VRTM 假设、已授权工具 schema、工具结果和状态机反馈。项目源码、网页内容、MCP 返回和工具说明都被标记为不可信数据，不能覆盖系统消息和控制合同。

#### Provider 与模型配置

当前默认 DeepSeek 配置为 OpenAI-compatible API：

| 配置项 | 默认值/规则 |
| --- | --- |
| Provider | `deepseek` |
| Base URL | `https://api.deepseek.com` |
| Model | `deepseek-v4-flash` |
| Key 来源 | `VIBE_SEC_DEEPSEEK_API_KEY`、`DEEPSEEK_API_KEY` 或本地模型配置 |
| 默认温度 | 审查低温，减少格式漂移 |
| 超时 | 受 `LLM_REQUEST_TIMEOUT_SECONDS` 控制 |
| 网络范围 | Provider 请求属于显式 LLM 能力，项目依赖网络默认关闭 |

API 的模型配置接口只返回脱敏后的模型信息和 `api_key_configured`，不把凭据返回前端。连接检查只返回 connected、authentication_failed、invalid_configuration、timeout 或 unavailable 等分类结果。

#### ReAct 审查状态机

LLM 审查不是一次 prompt/response，而是有边界的 ReAct 循环：

```text
START
  │
  ▼
Build context（candidate + VRTM + system guard）
  │
  ▼
MODEL_TURN
  ├── tool_calls ──► WAITING_TOOL ──► paired tool results ──┐
  ├── terminal call ─► CONTRACT_VALIDATE ────────────────────┤
  ├── structured JSON ─► CONTRACT_VALIDATE ─────────────────┤
  └── text/invalid ─► feedback + bounded next turn ─────────┘
  │
  ├── valid contract ─► COMPLETED
  ├── invalid contract with budget ─► MODEL_TURN
  ├── max turns/timeout/token ─► DEGRADED
  └── guard/policy failure ─► WAITING_HANDOFF or FAILED
```

每个模型工具批次先完整写入 assistant transcript，再由 Loop 串行执行所有工具并为每个 call id 写入对应 tool message。这样即使 Provider 在 `parallel_tool_calls=false` 时返回多个工具调用，也不会出现未配对消息导致下一轮请求失败。

#### 工具预算与全局优先级

大项目候选数可能远大于 LLM 预算。平台先在各审查 lane 登记静态候选，再由全局分配器按照严重度、置信度和稳定顺序选择，而不是让第一个 lane 抢占全部预算。这样 Juice Shop 中的 critical B2B evaluator 会优先于大量低证据 prompt injection 噪声。

审查预算和验证预算分开计算：`react_review_limit` 限制 LLM Finding 审查数量，`max_verification_count` 限制验证会话数量，`verification_fraction` 控制按比例验证的候选量。预算外候选保留 `not_reviewed`，不被删除或默认拒绝。

#### DeepSeek 终态兼容

DeepSeek 的 OpenAI-compatible endpoint 支持正常工具调用，但对 OpenAI 风格的命名 `tool_choice` 约束不同。终态强制阶段不再依赖不兼容的 named-function hint，而是只保留 `Finalize*` 能力边界，在证据预算达到阈值后禁用工具 schema，要求模型返回 `{ "terminal_action": "FinalizeFinding", "output": { ... } }`，并明确禁止把 `type`、`properties`、`required` 等 Schema 关键字回显成 Finding 字段。

终态 JSON 不是对模型的信任，而是减少 Provider 工具格式差异的传输协议；真正的完成仍以 CompletionContract 验证为准。

#### LLM 失败降级

Provider unavailable、authentication failed、timeout、rate limited、permission denied、invalid response 和 `react_session_incomplete` 被转换为稳定的 `error_category`。原始供应商错误不写入 verification artifact、审计 evidence 或对外报告。

如果 LLM 会话中断，平台保留静态 Finding 和成功读取的证据，并把结果降级为 `needs_evidence` 或 `potential`。如果没有成功的源码工具结果，不能生成 confirmed/verified。这样模型不可用时，系统的行为是“少做结论”，而不是“把静态候选清空”。

#### 证据绑定和不可变字段

LLM 可以补充标题解释、描述和 evidence bundle，但 Finding ID、漏洞类型、文件路径、行范围和候选来源由平台绑定。模型返回的路径如果逃逸项目根、行号不在读取证据范围或类型改变，绑定层会恢复候选事实并记录缺口。

模型提供的 `evidence_bundle.items` 会被标记为 LLM 摘要；真正的工具执行审计以 ToolGateway record 为准。`confirmed` 或 `verified` 还必须满足成功 source record、路径依赖语义 trace 和对应的验证条件。








### 3.1 前端实现

前端控制台围绕“工作区、审查、运行面、风险、证据、整改和集成”组织。`Workspace` 管理项目和审计任务；`AuditEngine` 展示审查配置与运行；`ThreatModel` 展示运行面威胁模型；`ToolFabric` 展示工具与能力；`Findings` 展示风险发现；`Evidence` 展示已生成的验证材料；`Remediation` 展示整改包和本地回送状态；`Knowledge`、`Foundation`、`Integrations` 和 `Settings` 分别提供知识、运行检查、Skill/CLI 集成和配置。当前这些视图以查询和展示为主，动态验证提交、复测启动和批量回归不由页面直接完成。

这种页面组织方式对应系统对象链的阅读路径。用户可以从工作区或审查结果逐步查看目标、运行面、Finding、已有证据和整改输出；验证执行、复测是否通过以及后续回归的操作仍需回到 CLI/Python/Harness 和目录材料，不应理解为页面已经提供完整上下文操作闭环。

前端实现的重点在于把复杂安全流程整理成可阅读的展示路径。`Workspace` 和 `AuditEngine` 承担主线导航，让读者看到任务状态和关键风险；`ThreatModel` 承担边界解释，将页面入口、提示词、工具、权限和代码索引放在一起；`Findings` 承担筛选与解释；`Evidence` 读取已经生成的验证材料；`Remediation` 展示整改包和本地回送状态。验证步骤的实际执行、复测是否通过、同类问题是否进入长期回归，仍由 CLI/Python/Harness 与目录材料负责，页面不提供完整的验证/复测/回归操作面。

这种前端组织方式对评审展示也很重要。AI 生成应用的风险常常横跨页面、接口、提示词和工具，如果界面只展示漏洞列表，读者很难理解系统为什么可信。嫘祖鉴丝将展示顺序设计为“工作区/审查 -> 运行面 -> Finding -> 已有证据 -> 整改输出”，并在文档中补充 CLI/Python/Harness 的验证、复测和回归路径。评委看到的是一条可追溯的展示路径，而不是已经完全自动化的 UI 闭环。

### 3.2 后端实现

后端以 FastAPI 提供当前已实现的项目、审计任务、Finding、模型配置、VRTM、整改和受保护验证接口。任务主入口是 `POST/GET /api/projects`、`POST/GET /api/audit-tasks`、`GET /api/audit-tasks/{task_id}`、`GET /api/audit-tasks/{task_id}/findings` 和 `GET /api/audit-tasks/{task_id}/remediations`。旧的 `/api/tasks*`、`/api/process-task`、知识库和智能体实验路由不属于当前版本。

后端保留受保护的 Finding 验证接口和 Harness/Python 服务，但前端没有完整的验证计划提交、动态执行、证据复核和状态回写页面。因此验证能力应以 CLI/Python/Harness 测试为准，不能把前端视图中的演示数据写成完整 API 生命周期。

整改结果通过 `/api/audit-tasks/{task_id}/remediations` 查询，CLI/Python 层提供整改包和复测对象；前端复测启动、外部 Agent 回调、报告差异和回归批次接口尚未全部实现。接口清单以 `docs/API.md` 和 `api/server.py` 为准。

这些接口体现系统实现的工作重心：任务有状态，运行面可查询，风险链可追踪，已生成证据可复核，整改结果可查询和本地标记；受控验证、复测回写和回归批量运行目前依靠 CLI/Python/Harness，不应理解为前端已经提供完整操作闭环。

后端接口的设计目标是支持“状态化安全审查”。一次完整审查可以抽象为任务创建、模型审查、发现项生成、验证计划、授权/审批、执行、复核、整改和复测等阶段；当前 FastAPI 主要提供项目、审计任务、Finding、整改、配置和受保护验证相关接口，阶段暂停/恢复/重试/复核由 CLI/Python/Harness 与会话材料有限支持，尚未形成独立的阶段控制 API。对于真实团队而言，这种分阶段材料仍比一次性返回扫描结果更容易审计，但不能宣称每个阶段都能通过 Web API 操作。

接口层还承担有限的对外集成职责。前端控制台使用这些接口展示任务状态，单一 Skill/CLI 使用项目与审计任务接口完成送检并读取结果；复测和回归批处理目前不由独立 Web API 创建，而是通过 CLI/Python/Harness 和目录化材料执行。这样的接口设计已经支持平台作为本地安全审查系统运行，也为后续 AI 编程工作流集成保留扩展点。

### 3.3 核心服务实现

`RuntimeSurfaceBuilder` 负责把目标输入转化为运行面。它组织页面入口、提示词、工具能力、权限范围、关键动作、信任边界、代码块和文件关系，为后续审查提供统一上下文。`JsonAuditAgent` 与 `HeuristicFindingDetector` 共同产出发现项：模型侧识别跨层风险线索，规则侧补充稳定工程信号，归并后进入统一 `Finding` 主表。

运行面构建并不只保存目标 URL。系统会从任务输入中提取页面入口、系统提示、角色提示、工具画像、权限说明、关键动作和代码块索引，并记录默认信任边界，例如“用户可控输入进入前端运行时”“不可信提示进入智能体提示词/工具边界”“前端运行时进入后端 API”“模型输出进入 DOM 渲染点”。代码块只在索引中保留长度、哈希、文件路径和语言，原始代码作为审查上下文传递给模型或规则，避免报告对象膨胀。这样的设计使平台可以把一个看似普通的页面送检任务，转化为后续审查、验证和整改都能复用的结构化运行面。

运行面图进一步把页面、提示词、工具、权限、关键动作、信任边界、代码文件、接口、存储键、请求参数、路由参数和 DOM 写入点组织为节点与边。系统据此回答“风险经过了哪些对象”，并把单个代码问题放回页面、接口、提示词和浏览器行为共同组成的路径中。例如，请求参数篡改会同时关联页面入口、存储键、接口参数和后端响应；提示词注入会关联外部内容、提示词片段、工具说明和关键动作；输出渲染问题会关联模型输出、富文本组件、DOM 写入点和浏览器执行结果。运行面图为后续 `RiskChain` 的 `graph_trace` 提供依据，也让整改输出能够定位到具体边界。

运行面构建的关键难点在于“信息不完整”。vibe coding 场景下，开发者送检时未必能提供完整工程，可能只提供目标地址、部分源码、几段提示词和工具说明。系统因此采用渐进式建模：先从目标地址和任务材料建立页面入口，再从显式字段和提示词文本中提取角色、工具、权限和关键动作；源码存在时，补充代码块索引和文件关系；资料缺失时，保留缺失信号，后续由上下文补全与人工复核处理。这样，平台可以在不完整输入下先形成可审查对象，同时避免把资料不足伪装成确定结论。

审查阶段采用“模型判断 + 规则信号 + 监控复核”的组合。模型适合识别跨层语义，例如提示词如何影响工具调用、页面状态如何进入接口；规则适合捕获稳定模式，例如危险渲染点、前端身份字段、可疑存储键、未授权接口和高危工具描述；监控复核则负责检查发现项是否有证据引用、是否覆盖运行面、是否需要人工复核。三者结合后，平台能够在高噪声的 AI 生成项目中保持结果质量，不把所有可疑片段都推给开发者。

模型审查采用压缩上下文和结构化输出。`JsonAuditAgent` 会先从运行面中提取系统提示、角色提示和关键代码块，并按评分选择最多 `8` 个高价值代码块；单个代码块会被截断到预算范围内，代码块整体 JSON 也有上限，避免一次审查因为材料过长而失控。模型被要求只返回 JSON 数组，字段名保持英文，面向人的标题、描述、影响和建议使用中文。返回结果会经过代码块围栏剥离、JSON 解析、候选字段归一化和单条发现项标准化处理。这样，模型输出从一段自由文本变成可入库、可复核、可继续进入风险链的结构化发现项。

当前实现通过 `ReActFindingReviewer._bind_review_result`、Finding 不可变字段和证据绑定收紧模型结论。审查器使用只读源码工具、有限轮次和终态合同；Provider 失败、工具失败、源代码缺失或证据不相关时，结果会降级为 `potential`、`needs_evidence` 或 `unverified`。仓库没有独立的 `StructuredFindingMonitorAgent`，监控语义由审查绑定、ToolGateway 记录和测试断言共同实现。

当前实现的审查合同位于 `core/audit/react_review.py`、`core/verification/react_review.py`、`core/agent_runtime` 和 Tool Fabric。`ReActFindingReviewer` 负责有限轮次的只读代码审查，`ReActVerificationReviewer` 负责验证计划与证据绑定，`AgentTaskLoop` 负责 Agent 运行状态，`AgentGuard` 和 `ToolGateway` 负责工具权限与审计。不存在一个名为 `control_plane.py` 的角色合同中心，也不存在下文中列出的拆分式 Monitor/Guard/Planning/Coordinator 角色；这些名称只能作为未来拆分设计，不作为当前代码事实。

当前版本没有独立的阶段记录表或控制面服务。阶段状态主要由 `AuditTask`、Agent Runtime/RunSession、审计事件和 Harness 会话 manifest 组合表达；运行面节点数、Finding 数量、验证结果等指标由 CLI 报告和前端查询时计算。`StageRunRecord`、`AgentRunRecord`、`MetricSnapshotRecord`、`ControlPlaneService` 和 `task_control_plane` 是可选的后续拆分方向，不是当前源码中的类、表或 API。

当前真实主流程由 CLI/API 创建 `AuditTask` 后调用审计服务：先解析项目和运行面，再执行静态/语义发现，按全局预算选择 LLM 审查对象，最后绑定 Finding、VRTM 快照和整改结果。仓库没有 `/api/process-task` 路由，也没有一个会写入上述虚构角色摘要的编排 API；阶段化、多角色控制面属于后续演进方向。

验证阶段由 `core/verification`、`core/harness` 和 Tool Fabric 执行。计划先经过授权和目标绑定，再由 Harness 运行服务、浏览器或函数级工具，并将步骤、阻断原因和证据写入验证会话。模型不能单独批准执行，前端目前也没有完整的验证计划提交和结果回写闭环；能否确认风险以 Harness 证据和绑定函数为准。

当前版本没有 `orchestration_summary.py` 或 `/api/tasks/{task_id}/orchestration-summary`。任务状态、审计事件、验证会话和整改状态分别由现有 API、SQLite 状态存储、Agent Runtime 和 Skill Relay 状态对象记录；未来如增加控制面摘要，必须以真实路由和端到端测试为准。

当前平台的下一步动作来自任务状态、Finding 状态、验证授权结果和整改状态，而不是一个独立的多 Agent 编排摘要。证据不足时保留 `needs_evidence`，工具或授权失败时保留失败事件，整改包未满足复测条件时不关闭；这些状态可由 CLI/API 查询。

当前任务可通过 `/api/audit-tasks` 查询历史状态，RunSession/Agent Runtime 和 VRTM 状态目录保存审查过程。验证会话和 CLI/Python 复测可以单独重试或重建，但旧的 `/api/tasks/{id}/resume`、外部修补回调和前端复测回写并未全部实现。文档将这些能力标为当前可用、局部可用或规划中，避免把设计状态误写成完成状态。

`RiskChain` 将发现项转化为可复述的路径：风险从哪里进入，经过哪条边界，依赖什么前提，触发后有什么可观察信号，可能造成什么业务影响，验证需要满足什么条件。这个结构使报告能够解释风险，避免停留在命中项罗列。

在风险生成之后，当前系统通过 Finding 去重、全局审查预算、严重度/置信度排序、`ReActFindingReviewer` 的证据绑定和失败降级压缩噪声。平台不会把自然语言解释当作独立监控 Agent 的证据；缺少相关源码读取、语义路径或验证材料时，候选保持 `potential`、`needs_evidence` 或 `not_reviewed`。这更符合 Vibe Coding 输入混杂、模型响应有波动的现实。

风险排序产出验证队列。每个队列项会携带风险链编号、验证理由、预期证据、前置条件和验证成本，供验证计划智能体转成具体步骤。对于页面风险，计划会倾向于浏览器动作、选择器、网络请求采集和状态差异；对于服务风险，计划会倾向于接口调用、身份变化、对象读写和响应差异；对于函数级风险，计划会倾向于最小函数探针。这样，嫘祖鉴丝能够根据风险所在位置选择证据面，避免把所有问题都强行做成同一种测试。

验证会话由 `core/session` 的 RunSession 模型/存储、`core/harness` 的 HarnessRuntime 和 `core/verification` 的授权、复核逻辑协同管理。当前支持的重点是受控步骤执行、事件记录、证据目录化保存和 CLI/Python 复核；不存在独立的 `ValidationSessionManager` 或 `EvidenceStore` 服务类。浏览器动作、网络采集、页面结构观察、状态差异和工具调用记录由执行器写入会话材料，报告和整改脚本再读取这些材料。

验证执行时，平台不会直接把模型输出的步骤无条件运行。验证计划先进入会话草稿，提交后检查是否包含关键动作；如果存在删除、写入、外部请求、危险工具调用等动作，会进入审批状态并生成审批票据。执行层再根据权限策略检查工具、目标地址和动作范围，符合条件的步骤才会交给工具注册表中的处理器。浏览器步骤由 Playwright 适配器执行，服务级或函数级步骤由相应脚本和回放目标执行。执行过程中产生的事件会被写入会话日志，关键证据会进入证据包。这样，平台既能自动化验证，也能在高风险动作前保留人工确认和审计痕迹。

Harness 的实现还让验证过程可以恢复和复核。每次 turn 成功后，系统会写入工具名、关键动作、标准化结果和证据，并在浏览器跳转或接口返回新 URL 时更新会话上下文；当步骤被阻断时，日志会保留阻断原因，例如域名越界、工具被禁用、工具前缀命中或关键动作不允许。这个细节对安全审查很重要：平台的自动验证不会直接运行 AI 生成步骤，每一步都会先经过受控策略检查，并留下可审计事件。

浏览器验证是系统区别于普通静态审查的重要部分。对于 Open-WebUI 富文本、文件预览、SVG 头像、课程页面身份篡改和轻量智能体上下文污染等问题，静态检查只能说明“代码里可能存在危险路径”，浏览器验证可以进一步说明危险内容是否真实进入渲染点、脚本是否执行、页面状态是否变化、请求是否发出、模型回答是否受到外部内容影响。平台把截图、文本提取、网络请求和脚本求值结果都规范化为证据项，既服务于风险确认，也服务于修复后的对照验证。

浏览器执行器对输入做必要字段校验，例如 `goto` 必须有 URL，`click/fill/extract_text` 必须有 selector，`evaluate` 必须有表达式。网络采集时，执行器会优先保留带请求体、非 GET、XHR 和 fetch 类型请求，避免高价值接口调用被图片、字体和静态资源淹没。对于页面助手类目标，选择器中的 assistant、reply、model-output、chat-response 等语义会被自动归为 `assistant_output`；对于本地状态或页面结构观察，`evaluate` 返回的 `url/title/observations/buttons` 会进入 `state_diff`。这些实现让证据更接近评审和开发者关心的问题：风险是否真的到达业务接口、DOM 执行点、助手输出或状态变化。

报告与整改输出由现有审计/整改模块和 CLI 组装为报告材料与 API 的 `RemediationBundle`。每条确认风险可以携带失败边界、根因、修补动作、AI 修改提示、复测计划和验收条件；仓库没有独立的 `UnifiedReport`、`RemediationBundleService`、`RemediationService`、`RetestService` 或 `RegressionCaseService` 类。复测与回归目前依靠 Harness/CLI/Python 脚本和目录材料完成，前端没有完整的启动、回写和批量回归 API。

整改回送当前不依赖 `developer_handoff.py`、`workflow_contract.py` 或 `skill_relay_*` 系列文件。现有实现由整改数据模型、`core/remediation/skill_relay.py` 和 CLI/前端本地输出组成：系统把确认风险整理为开发者摘要、修补提示词、补丁约束、复测计划和验收条件，供开发者或 Agent 手工/脚本消费。外部修补任务派发、回调、自动复测和归档提升仍是后续集成目标。

当前整改输出由 API 的 `RemediationBundle`、CLI/前端结果对象和 `core/remediation/skill_relay.py` 负责。它们保存开发者摘要、修补约束、验收条件、复测目标和本地投递状态；不存在独立的 `RemediationTicket` 服务，也不存在 `WorkflowContractService`、`DeveloperHandoffService`、`SkillRelaySummaryService` 或 `SkillRelayDeliveryService` 这些独立服务类。外部会话的 acknowledged/consumed/returned 只属于本地状态合同和未来集成方向，不能写成已打通的 API 闭环。

技能接入的安全边界通过单一 `vibe-sec` Skill 的命令参数和输出约定实现。送检命令接收项目路径、目标地址、审查范围、LLM 选项和授权配置，并调用现有 CLI/API；结果以 Finding、VRTM 快照引用、RemediationBundle 和复测计划等现有对象输出。仓库没有第二个“回送技能”，也没有 `session_bridge`、`callback_monitor_contract` 或 `finalization_summary` 等稳定外部对象。技能层只负责参数整理和结果传递，不直接接触平台内部审查状态机。

当前本地回送状态只表示整改包是否生成、是否由 CLI/前端标记为已投递，以及是否等待开发者处理。前端 `dispatchBundle` 目前只更新本地 store 状态并提示后端 adapter 尚未接入，不会调用外部 Agent 回调 API。acknowledged、consumed、returned 等状态可以作为后续桥接设计，但不能被解释为当前已打通的外部会话闭环。

整改服务的实现强调“给 AI 修改也要有边界”。同一条风险进入整改包后，系统会保留失败边界、入口页面、前置条件、影响假设和证据谓词，并把它们转化为修补约束和验收条件。例如身份可信源问题不会只写“加强校验”，而会要求以后端会话或令牌链作为身份事实；多租户问题不会只写“检查权限”，而会要求工作区、所有者、角色和对象范围都在服务端校验；渲染问题不会只写“过滤输入”，而会要求在进入渲染点前消毒并验证合法内容仍然可显示。这样的整改输出更适合交给 AI 编程助手执行，因为它明确限定了“不能怎么改”和“改完怎么验”。

从模块协作角度看，核心服务实现可以理解为四次“收束”。第一次收束发生在任务接入阶段，系统把自然语言、目标地址、源码目录、提示词、工具说明和权限说明收束为 `Task` 与 `RuntimeSurface`。第二次收束发生在审查阶段，模型发现、规则信号和监控复核被收束为结构化 `Finding` 与 `RiskChain`。第三次收束发生在验证阶段，浏览器动作、接口调用、函数探针、截图、网络请求和状态差异被收束为 `ValidationSession` 与 `EvidenceBundle`。第四次收束发生在整改阶段，确认风险、失败边界、修补约束、复测计划和验收条件被收束为 `RemediationBundle` 与开发者回送包。四次收束贯穿同一任务对象，使报告中的每个结论都能回到输入、过程和后续动作。

这种实现方式降低了 AI 参与安全审查时的噪声。模型适合识别跨层语义，但容易过度概括；规则适合捕获稳定模式，但容易缺少业务上下文；浏览器验证能给出强证据，但成本高，不能无差别运行。平台通过风险排序和验证计划，把模型和规则发现的线索先压缩为高价值风险，再进入受控验证。这样既保留了 AI 对复杂语义的理解能力，也通过规则、权限门控、证据复核和人工审批约束其输出。

实现中还特别强调可恢复性。已有 RunSession/Agent Runtime 能够保存审查过程，Harness 会话材料支持按目录重建和 CLI/Python 复核，报告可以从现有结果材料重建，整改记录可以更新状态。vibe coding 场景下，同一页面可能在一天内被 AI 编程助手改写多轮，如果平台只保存最终报告，就无法判断某个风险是在本轮修掉、被新补丁重新引入，还是从未被验证。当前实现通过任务记录、审计事件、会话 manifest 和复测材料支持有限的跨轮次比较；尚不存在统一的阶段记录表或自动回归编排器。

面向工程可靠性，平台还通过测试覆盖关键安全边界。受控验证执行层覆盖禁用工具、禁用前缀、伪装域名、路径前缀绕过、跳转后跨域阻断和关键动作审批；浏览器执行器覆盖动作参数、文本提取、截图、脚本求值和网络采集；单一 Skill 包装覆盖送检输入、结果输出和本地整改状态。当前没有外部派发、回调、消费和终态摘要 API 的端到端测试，因此测试结论只适用于现有 CLI/Python/Harness 与本地 Skill 能力。

### 3.4 工作流

目标工作流为：目标接入、运行面重建、联合审查、风险链生成、会话化验证、证据整理、报告与整改输出、定向复测、多目标回归。当前已实现并可稳定使用的是项目/审计任务创建、Finding/VRTM/整改查询和 CLI/Python 审查验证；前端动态验证、复测回写和外部 Agent 回送仍是待完善链路。

整个流程围绕交付效果设计。平台面向用户呈现目标如何被建模、风险如何被解释、证据如何形成、修复如何被要求、复测如何确认。

在当前 Skill 形态下，开发者调用单一 `vibe-sec` Skill 和 CLI 命令完成项目审查、VRTM 建模或复测。真实 API 使用 `/api/audit-tasks`，平台返回 Finding、VRTM 和整改结果。前端验证提交、复测启动、外部修补会话和状态回写尚未打通，因此这里描述的是可用的 CLI/Python 链路，而不是完整的 UI 闭环。

流程中的三道门禁是当前实现的约束目标：送检门禁检查项目和审查范围，验证门禁由 Harness 授权、正负控制和证据绑定决定，闭环门禁要求整改和复测证据齐全。第三道门禁目前主要由 CLI/Python/状态合同执行，前端和外部 Agent 的自动派发尚未完成。

从一次实际送检的视角看，当前可执行路径包括：开发者提交项目和审计任务；平台生成运行面与 Finding；LLM/规则结果经过证据绑定；需要动态证明时由 CLI/Python/Harness 创建验证会话；证据和整改包写入任务结果；开发者根据整改包修改代码并通过 CLI/Python 复测。前端验证提交、外部修补回调和自动回归仍需后续实现。

这条主线把平台的复杂实现压缩成读者能理解的路径：先看清系统，再解释风险，再在授权条件下验证，再生成整改和复测要求。它证明当前核心审查和证据链已经可用，但不证明前端和外部 Agent 的完整闭环已经交付。

## 四、真实应用场景下的系统使用效果

嫘祖鉴丝的应用对象覆盖 vibe coding 生成出来的一类复合应用：前端页面由 AI 快速生成，后端接口可能由模板或平台自动连接，页面助手会读取当前页面和外部资料，工具节点可能拥有文件、网络、数据库或第三方 API 能力。这样的系统在教学平台、中小团队原型、智能表单、生成式建站、AI 工作流、内部运营后台和轻量智能体页面中都很常见。当前可执行的使用方式是：开发者通过单一 `vibe-sec` Skill/CLI 送检，平台完成运行面建模和审查，CLI/Python/Harness 负责受控验证和复测，前端展示结果并提供本地整改回送状态。

### 4.1 课程型 AI 页面

课程型 AI 页面代表教师、课程团队和外包开发者使用 AI 快速生成教学系统的场景。系统通常包含登录注册、课程学习、AI 问答、智能体对话、教师主页、学员列表、学员详情和学习进度接口。嫘祖鉴丝在该类目标上把页面入口、本地状态、学习进度接口、页面助手和外部内容统一放入 RuntimeSurface。

上一版历史真实目标数据中，Dengcheng Junshi Guanli Book 2026 形成 4 个验证会话，确认 `H-AGENT-PROMPT-1` 与 `H-REQ-2` 两类风险，`H-EXTDOM-3` 与 `H-STORAGE-3` 保持 `inconclusive`。`H-REQ-2` 的价值在于展示前端身份字段可以穿透到后端进度读写链：验证过程建立基线学号，篡改本地身份，触发 `save_progress.php` 写入，再通过 `get_progress.php` 读回差异。该历史链路说明系统具备识别和验证 AI 生成页面中“前端状态被当作身份可信源”问题的方法，不代表当前版本已重新执行该目标。

从真实使用角度看，这类系统的安全痛点非常具体。课程团队关心的是学生身份、学习进度、教师权限、作业提交和 AI 助手回答是否可信；外包开发者关心的是快速交付后能否拿出可解释的验收材料；测试人员关心的是“学号字段可改”是否真的影响后端状态。嫘祖鉴丝在该场景中提供的内容超出泛泛漏洞名，会把前端身份字段、本地存储、进度接口和读写差异连成一条证据链，再把服务端身份来源、进度接口鉴权和复测步骤写入整改输出。这样，课程型 AI 页面可以从“功能能跑”推进到“身份边界能被证明”。

这个案例适合说明平台如何把“小问题”解释成“业务风险”。如果只看前端页面，篡改本地学号似乎只是浏览器里的临时状态；如果只看接口，`get_progress.php` 和 `save_progress.php` 也可能只是普通学习进度接口。平台把两者放在同一条风险链里：本地身份字段是入口，进度保存接口是写入动作，进度读取接口是验证出口，读回差异是证据。这样，问题就从“前端字段可改”变成“服务端把前端字段当作身份事实”，评审和开发者都能理解风险成立的原因。

整改回送在该场景中同样有实际意义。平台不会只建议“不要信任前端”，而会把整改拆成几条可执行要求：学习进度接口必须从服务端会话或令牌中取得学生身份；保存与读取接口都要校验当前用户与目标学号的一致性；教师查看学生进度必须走教师权限链；复测时要验证伪造学号失败、真实学生进度保存成功、教师合法查看仍然可用。这样的输出可以直接回到 AI 编程助手会话中，驱动下一轮代码修改。

课程型 AI 页面还暴露了提示词边界问题。页面助手如果读取课程内容、学习状态和外部资料，就需要区分“课程资料”“用户提问”“系统提示”和“工具返回结果”。平台在真实目标中确认了提示词相关风险，说明 AI 助手的安全复核不能只看页面接口，还要看模型回答是否暴露系统提示、是否被外部内容影响、是否把用户输入当作高优先级指令。对教学系统而言，这类问题会影响助教回答可信度，也会影响学生隐私和课程资料边界。

### 4.2 轻量智能体页面

FinBot Local 和 FinBot Public 是上一版历史实验中的轻量智能体页面与供应商上下文场景。系统在 `/vendor` 入口下形成验证会话，围绕提示词注入、外部页面结构影响、onboarding prompt 暴露和 vendor contexts 清理进行验证。历史记录显示 FinBot Local 形成 3 个验证会话并确认 3 个风险；FinBot Public 形成 3 个验证会话并确认 2 个风险；两个目标均观察到上下文清理，对 vendor contexts 完成清理。当前版本未将这两目标的历史会话计入 2026-08-02 多靶场成绩。

这类场景体现了轻量智能体的典型风险：页面内容、供应商上下文和模型回答处在同一链路中，不可信外部内容可能影响助手行为；同时，清理动作本身也是安全治理的一部分。嫘祖鉴丝不只验证提示词或页面结构影响，还记录上下文清理和状态变化，使报告能够同时回答“风险是否成立”和“清理是否完成”。

在实际产品中，轻量智能体常被嵌入销售、采购、客服、课程助教和内部运营页面。开发者通常会把外部资料、供应商说明、用户输入和系统提示词放到同一上下文里，模型再根据这些内容回答问题或触发工具。风险在这里并不表现为传统的单个接口漏洞，而是表现为上下文污染、提示词暴露、工具边界失配和状态清理不完整。平台通过浏览器验证和会话证据把这些抽象问题落到可观察信号上：模型回答是否偏移、敏感提示是否暴露、供应商上下文是否被清理、清理后状态是否真正变化。

FinBot 场景的价值在于展示“智能体状态”也需要被验证。普通网页测试通常关注按钮、接口和页面展示；轻量智能体还要关注上下文是否被污染、历史材料是否被清理、外部页面是否改变回答、敏感提示是否泄露。平台在 `/vendor` 入口下记录验证会话和上下文清理动作，使报告能够说明智能体会在多个上下文状态之间流转。只有把这些状态纳入证据，才能判断风险是否真正消除。

这一场景也说明了浏览器验证和证据包的必要性。提示词注入往往表现为模型回答偏移、工具调用意图变化或敏感上下文泄露，不能只按固定字符串命中判断。平台通过页面文本、助手输出、状态差异和上下文清理记录，证明风险是否进入模型行为。对于开发者来说，这比“疑似提示词注入”更有价值，因为它告诉开发者风险发生在哪个页面入口、受哪些上下文影响、清理后状态是否回到安全状态。

### 4.3 AI 应用平台与工作流平台

AI 工作流平台和应用构建平台代表自然语言生成开发的高风险落地形态。Flowise、Langflow、Open-WebUI、PraisonAI、n8n、Gradio、LangChain Core、AgenticMail 和 MCP SDK 等样本覆盖了从聊天界面到工作流编排、从工具调用到文件访问、从多租户对象到浏览器渲染的多个风险面。嫘祖鉴丝在这些目标上的能力不依赖某一产品的特殊结构，而依赖统一运行面、风险链和三态验证方法。

在 Flowise 样本中，系统验证了生成代码进入 pyodide、MCP 命令、OpenAPI/Execute Flow 服务端请求伪造、文件上传、读写文件、重置密码、OAuth token 泄露和对象接管等风险。Open-WebUI 样本集中验证富文本、文件预览、音频缓存、SVG 头像、工具绕过、批量赋值、RAG 配置等风险。PraisonAI Platform 样本集中验证 workspace、issue、comment、project、dependency、member、label、agent 的跨空间读改删和角色提升。这些样本说明，AI 应用的真实风险已经从“页面能否显示”扩展到“工具能否执行、对象能否越权、输出能否执行、文件能否越界、身份能否伪造”。

这类平台最适合说明嫘祖鉴丝的规模化价值。vibe coding 让开发者可以用自然语言把工作流节点、聊天界面、文件工具、数据库对象和第三方接口串起来，但每一个自动生成的连接点都可能成为安全边界。Flowise 与 n8n 代表“自然语言把用户输入接到工具和文件系统”的风险，Open-WebUI 代表“用户内容进入聊天界面和浏览器渲染面”的风险，PraisonAI 代表“智能应用搭建平台自动生成协作后台后，对象归属和角色边界失效”的风险，LangChain Core 代表“底层提示词和模板函数在函数级输入中暴露路径、属性和序列化风险”的问题。平台用同一套三态验证方法处理这些差异很大的目标，说明其方法并不依赖某个演示项目。

如果把这些样本放回真实开发流程，风险会更加清晰。Flowise、Langflow 和 n8n 这类工作流平台让开发者用节点把模型、数据源、接口、文件和脚本连接起来，开发效率很高，但每个节点都可能隐藏执行边界：用户输入是否进入代码生成，工具配置是否能触发命令，文件路径是否越出工作区，外部接口是否造成服务端请求伪造。Open-WebUI 这类聊天界面则把用户内容、模型输出、富文本渲染、文件预览和头像资源放进同一个浏览器页面，输出处理稍有疏漏就可能变成脚本执行。PraisonAI 这类协作后台体现的是另一类问题：AI 可以快速生成项目、成员、标签、评论、智能体等对象管理页面，但对象归属和角色边界必须在服务端重新收口。

平台在这些目标上采用统一方法：先把产品特性还原为运行面，再把风险解释为风险链，最后用漏洞态、修复态和合法控制做三态验证。这样，Flowise 的工具执行、Open-WebUI 的富文本脚本执行、PraisonAI 的跨工作区越权、n8n 的符号链接文件访问和 LangChain Core 的模板边界，都能进入同一套解释框架。对读者而言，这说明系统处理的是一类问题的共性结构，而不是为某个单独产品写的专用脚本。

### 4.4 AI 编程会话中的送检与回送

在开发者日常使用场景中，嫘祖鉴丝可以被包装成 AI 编程助手旁边的安全质量门禁。开发者在生成页面、后台或智能体功能后，通过单一 `vibe-sec` Skill 提交目标入口、源码路径、提示词说明、工具说明和权限说明。平台创建任务后，前端控制台和 API 可以查看运行面、Finding、已生成证据和整改包；整改摘要、`ai_patch_prompt`、`retest_plan` 和验收条件由 CLI/API 输出，开发者再手动或由 Agent 继续执行。

这个流程适合中小团队、课程项目、外包交付和快速原型：开发速度可以保持 vibe coding 的优势，安全要求则通过平台变成可执行的检查点。开发者继续让 AI 编程助手修改代码时，输入会从“修一下安全问题”这种模糊要求，升级为带有失败边界、修补约束、验收条件和复测目标的结构化提示。修补完成后，平台可以围绕同一个 `task_id` 创建定向复测，并把通过的路径沉淀为回归基线。

从实际部署方式看，平台提供的是单一 `skill/` 目录和安装脚本。开发者使用 `scripts/install-agent-skill.ps1` 或 `scripts/install-agent-skill.sh` 将 `vibe-sec` Skill 安装到支持的 Agent 环境，再通过 CLI/API 送检。仓库没有 `scripts/build_skill_packages.py`，也没有 `security-inspection-skill` 与 `remediation-return-skill` 两个独立包。当前会话中的目标 URL、源码路径、提示词、工具说明和权限说明可以直接进入送检参数。

送检 Skill 的作用可以概括为“把一句话变成平台任务”。例如开发者在 AI 编程会话里说：“把这个刚生成的课程系统送检，重点看学生身份、进度接口和 AI 助手。”Skill 会把目标地址、工作区路径、源码范围、业务背景、提示词/工具/权限说明和验证范围归一化；如果传入已有任务标识，则按现有 CLI/API 约定续接任务；如果缺少部分源码路径，输出会明确列出缺失材料，但不会把资料不足误判为平台失败。送检成功后，开发者拿到现有任务标识、Finding/VRTM/整改结果引用和 CLI/Python 复测要求，不会得到未实现的 `workflow_contract`、`validation_sessions` 或 `developer_handoff` 路由。

整改结果目前以 CLI/API 可读取的 RemediationBundle 和 Skill Relay 状态返回开发者；不存在 `prepare-launch`、`bind`、`dispatch`、`callback` 等前端桥接路由。未来若接入高权限编码 Agent，应先实现范围门、人工确认门、补丁验证和复测回写，再开放自动派发。

这个包装为后续复测和归档保留了门禁位置，但当前没有外部修补回调、自动复测许可或 `finalization_summary` API。修补完成后，开发者需要根据整改包中的复测要求，通过 CLI/Python/Harness 重新执行并人工确认是否可以提升基线；漂移候选、误报候选和校准材料也继续以目录化实验记录单独治理。对于 vibe coding 场景，平台当前能提供可执行的证据和验收条件，自动闭环仍是后续工程工作。

面向用户体验，这一套流程可以包装成三句自然语言操作：第一句“把当前页面和源码送检”，第二句“把确认风险回送给 AI 编程助手修复”，第三句“按平台复测计划验收并沉淀回归”。三句背后分别对应 intake contract、return contract 和 closure/finalization contract。这样的设计保留 vibe coding 的速度，同时把安全审查、整改、复测和回归嵌入同一条开发工作流。

以一个外包交付场景为例，开发者可能先用 AI 生成一个内部报名系统，包含登录、表单、文件上传、后台审核和页面助手。交付前，开发者调用 `vibe-sec` Skill，把目标地址、源码目录、提示词说明和工具说明送入平台。平台发现文件上传边界、身份字段和富文本渲染存在高价值风险后，由 CLI/Python/Harness 进入受控验证会话，确认哪些风险真实可达。随后，整改包把“文件路径必须服务端真实路径校验”“身份必须来自会话”“富文本进入渲染点前必须消毒”等约束输出给开发者或 AI 编程助手。修补完成后，再通过 CLI/Python 复测恶意路径和合法控制。这个过程把审查、修改和复测组织在同一任务材料下，但外部自动回送仍需人工或后续适配器参与。

对课程项目和中小团队来说，这种包装降低了安全实践门槛。团队不需要先培养完整安全测试队伍，也不需要让每个开发者都掌握所有漏洞细节；平台把复杂风险转化为运行面、风险链、验证证据和整改提示，开发者只需把当前 AI 生成页面送检，再根据回送结果修改和复测。这样，vibe coding 的速度优势不会被安全流程完全抵消，安全审查也不会停留在交付末尾的临时检查。

### 4.5 现实事件语义映射与能力沉淀

平台将 AXIS Camera Station Pro、Base44 Private App、Lovable Data Permission 和 AI Form Builder 四类公开事件沉淀为现实事件能力样本。它们不以厂商复现成绩参与 70 条正式三态统计，而是进入平台的运行面建模、风险链模板、验证条件、整改模板和回归目标体系，用来支撑后续同类项目的送检与验收。公开事件经由这一处理路径，转化为平台可以复用的能力资产。

AXIS Camera Station Pro 对应高价值管理资源的认证边界。平台将登录、bootstrap、live view、recordings、smart search、dashboard、users、devices 等入口组织为运行面节点，风险链关注“未认证入口能否触达高价值资源”“认证前置是否覆盖搜索、录像、设备和用户管理”等条件。该类能力可以服务校园安防、实验室设备管理、企业内部监控等项目验收：只要目标存在高价值管理资源，平台就能把资源入口、认证前提、授权范围和访问证据放到同一条验证路径中。

Base44 Private App 对应生成式私有应用的认证链能力。许多生成式应用平台会在前端提供 register、verify-otp、private-app、members 等页面，使应用看起来已经具备私有访问控制；平台在这类样本中关注的是后端是否真正把登录态、一次性凭据、成员关系和资源访问绑定起来。送检时，嫘祖鉴丝会把“私有入口”“成员列表”“OTP 校验”“受保护页面”拆成对象链，检查前端私有标记是否穿透到服务端认证与授权判断。整改模板也随之聚焦后端会话事实、一次性凭据校验、成员范围和受保护路由门禁。

Lovable Data Permission 对应生成页面连接后端数据后的权限边界。生成式页面常常能快速连上数据库、表单、成员数据或业务记录，但行级权限、租户范围和对象归属需要后端策略证明。平台将该类事件沉淀为“页面身份 -> 数据查询 -> 行级策略 -> 响应差异”的风险链，验证时关注不同用户、不同工作区、不同对象编号下的数据读写差异；整改时要求服务端策略、租户范围、owner/role 字段和响应过滤同时收口。这个能力直接对应中小团队常见的生成式后台、报名系统、客户列表和课程进度页面。

AI Form Builder 对应生成内容进入预览、提交页和管理页后的输出渲染能力。平台将 builder、preview、submissions 等入口转为运行面节点，风险链关注模型或用户生成内容是否进入富文本、Markdown、表单预览、提交结果或管理后台展示点。验证时，浏览器证据用于判断危险内容是否到达执行点、脚本是否执行、修复后安全内容是否仍可正常展示；整改模板聚焦内容消毒、输出编码、响应头、MIME 约束和安全渲染组件。该类能力适合智能表单、课程作业提交、自动生成问卷和内容管理页面。

四类现实事件能力共同覆盖认证边界、数据权限、输出渲染和高价值资源访问四条主线。它们和正式复现实验形成互补：70 条公开漏洞复现提供可运行三态证据，3 个真实目标提供现场验证，现实事件能力样本负责把已发生的行业问题转化为平台可复用的任务模板。后续项目送检时，平台可以直接复用这些模板，把“私有应用是否真的私有”“生成页面是否越权读写数据”“表单预览是否会执行内容”“管理资源是否先经过认证”转化为运行面对象、风险链和复测条件。

因此，4.5 所展示的是平台的现实问题吸收能力。公开事件进入平台后，会被拆成入口、边界、证据谓词、整改约束和回归条件；开发者得到的是可执行的送检范围和修补要求，测试人员得到的是可复核的验证路径，评审可以看到系统如何把真实事件沉淀为长期能力。这一层能力让嫘祖鉴丝不只验证已有样本，也能把外部安全事件持续转化为平台内部的审查能力。

## 五、关键创新与系统能力

### 当前实现核对：可靠性、审计性与安全设计

#### 失败降级和状态一致性

当前系统把可靠性定义为“失败时仍然给出保守、可追踪的结果”，而不是假设 LLM、浏览器、服务和外部工具始终成功。Provider 超时或返回格式错误时，平台保留静态候选并将审查状态降级为 `needs_evidence`；工具调用失败时写入成对的请求与观察记录；任务超时或进程重启时保留失败事件；验证清理失败时禁止将整改包关闭。模型不能通过自然语言把失败改写成完成，也不能通过返回 `verified` 字符串跳过 Harness 和证据校验。

RunSession 的状态机使用显式阶段和检查点：`created`、`queued`、`running`、`awaiting_approval`、`verifying`、`awaiting_remediation`、`retesting`、`completed`、`failed`。进程恢复时，处于 `running` 或 `verifying` 且没有完成检查点的任务会被标记为可重试或失败，不会被伪造为完成；已经写入的 Finding、artifact 和事件保持不变，后续重试以新的 attempt 关联原会话。

#### 幂等、重复执行与版本指纹

ToolGateway 对工具名称、参数摘要、RunSession 和步骤编号计算签名。相同签名的重复请求会记录为 duplicate，避免 LLM 重试造成重复文件写入、重复服务启动或重复证据。API 任务使用稳定 UUID，Finding 使用去重键聚合同类候选但保留原始命中数量；这样前端可以展示一个风险族由多处命中组成，又不会把同一问题误报成多条独立漏洞。

VRTM snapshot 保存项目指纹、建模配置、节点和边摘要、风险假设以及生成时间。相同源码和相同配置不会覆盖旧 snapshot；复测通过新 snapshot 与旧 snapshot 做 security change analysis，输出新增、删除、变化和未变化的运行面对象。报告、整改和回归均引用 snapshot ID，保证结论能回到对应基线。

#### 证据保留、脱敏和可复核性

EvidenceBundle 只保存复核结论所需的最小材料。代码证据按文件、行号、摘要和哈希记录；网络证据按允许字段保存响应状态和关键差异；浏览器截图和 DOM 证据不保存 cookies、authorization header 或完整个人数据；LLM 原始错误转为可分类的错误原因；日志和报告中禁止出现 provider key、token、授权信封和项目秘密。

证据引用采用 artifact ID 和 sha256，不依赖临时路径。报告、前端详情页、Remediation Package 和 CLI/Python 复测材料都可以通过 artifact 引用同一份材料。证据缺失、哈希不匹配或清理记录不完整时，状态只能停留在 `needs_evidence` 或 `open`，不能升级为 `verified` 或 `closed`。

#### 外部内容、提示注入和高权限动作防护

源码、网页 DOM、供应商上下文、MCP 返回、工具输出和靶场响应全部被视为不可信数据。LLM 系统提示明确要求模型不把这些内容当成控制指令；ToolGateway 依据 allowlist、目标范围、参数模式和审批状态决定能否执行；模型输出的 `allow_poc_execution`、`allow_service_start`、`approval_granted` 等字段只能作为请求，不能直接改变控制面状态。

高权限 Agent 修改需要同时通过范围门、语义门、审批门和复测门。范围门比较 changed files 与允许目录；语义门检查补丁是否覆盖原风险的失败边界；审批门要求人工或明确策略确认；复测门要求负向控制阻断、合法控制保留，并且 VRTM 变化没有引入新的高权限路径。任一门失败，整改包返回 `returned` 或 `open`。

#### 供应链和执行镜像边界

Docker、浏览器、CodeQL、OSV 和其他安全工具都通过固定 manifest 或显式配置接入。工具镜像、版本和校验信息记录在部署材料中；未安装或未授权的工具只生成 coverage gap，不模拟为已执行。默认项目源码以只读方式挂载到容器，VRTM 快照和任务状态写入独立状态卷；LLM Secret 通过环境覆盖或 Secret 文件注入，不写入项目源码和报告。

这套边界使平台可以在本地审查项目、远程授权靶场和高权限 Agent 之间保持清晰分离：服务器只承担靶场部署和验证对象，项目代码修改、状态审计和报告生成仍由本地平台负责。部署脚本、Compose 配置、Skill 安装器和 `doctor` 检查共同保证运行前置条件可检查、运行后状态可恢复。


嫘祖鉴丝的应用对象覆盖 vibe coding 生成出来的一类复合应用：前端页面由 AI 快速生成，后端接口可能由模板或平台自动连接，页面助手会读取当前页面和外部资料，工具节点可能拥有文件、网络、数据库或第三方 API 能力。这样的系统在教学平台、中小团队原型、智能表单、生成式建站、AI 工作流、内部运营后台和轻量智能体页面中都很常见。当前可执行的场景链路是：开发者用单一 `vibe-sec` Skill/CLI 送检，平台完成运行面建模和审查，CLI/Python/Harness 负责受控验证与复测，前端展示结果并提供本地整改状态。


### 当前实现核对：整改回送与复测闭环

#### Remediation Package

每一个可回送包包含 Finding ID、漏洞类型、标题、文件路径、行范围、风险摘要、AI patch prompt、patch strategy、patch constraints、retest plan、acceptance criteria、verification status、proposal_only 和 state。

整改包不是把模型描述直接发给 Agent，而是将风险转换成修改约束：

| 风险族 | 整改约束 | 复测谓词 |
| --- | --- | --- |
| 身份覆盖 | 身份由服务端会话派生，客户端字段不能覆盖 | 伪造身份字段与合法身份控制的归属差异 |
| BOLA/IDOR | workspace、owner、role 和 object scope 在服务端共同检查 | 跨空间拒绝，同空间合法操作保留 |
| 提示词注入 | 外部内容标记为数据，工具调用经过 allowlist 和参数校验 | 恶意指令不改变权限，合法任务仍可完成 |
| 代码执行 | 不把用户输入直接传给 eval/exec/pyodide，使用安全表达式或隔离执行 | 恶意 payload 阻断，安全数据处理保留 |
| 文件访问 | 解析真实路径后做允许目录包含检查，拒绝 symlink 逃逸 | 逃逸路径拒绝，同目录文件仍可访问 |
| XSS | 服务端输出编码或可信 sanitizer，保留安全 Markdown | 脚本不执行，合法格式仍渲染 |
| SSRF | URL 解析、主机 allowlist、私网/重定向策略和 DNS 重绑控制 | 私网目标阻断，允许目标可达 |

#### 整改包状态

`draft` 表示候选整改建议，`returned` 表示已经回送给 Agent，`in_progress` 表示 Agent 正在修改，`completed` 表示 Agent 返回修改完成但还没有通过复测，`closed` 表示复测与 VRTM 闭环完成，`open` 表示仍有缺口。

一个包进入 `closed` 必须同时满足：Agent 返回 state=completed、fix_result.status=fixed、改动范围符合约束、项目测试通过、恶意控制被阻断、合法控制保留、必要审批有效、VRTM 没有未审查的安全显著变化。

#### 高权限确认门

如果整改涉及认证中间件、权限策略、工具权限、部署身份、密钥读取、Docker、服务启动或数据库迁移，包会带 `approval_gate.required=true`。确认门包含审批人、项目、Finding、允许范围、理由、签发时间、过期时间和签名/校验值。

模型不能伪造审批，提交消息不能代替审批，前端勾选不能代替 Harness token。审批只允许扩大明确的修复权限，不允许把动态目标或外部网络自动加入范围。

#### Agent 返回协议

编码 Agent 返回：

```json
{
  "state": "completed",
  "fix_result": {
    "status": "fixed",
    "changed_files": ["src/auth.py"],
    "summary": "Server derives identity from the authenticated session",
    "tests": [{"command": "pytest tests/test_auth.py", "status": "passed"}]
  },
  "control_results": {"negative": "blocked", "positive": "retained"},
  "retest_request": {"session_id": "run-...", "finding_ids": ["finding-..."]}
}
```

平台只接受结构化返回中的事实字段，改变后的源码和测试输出由平台或宿主 Agent 重新读取。Agent 提供的 summary 不会覆盖证据；changed_files 会和实际工作树比较；测试状态会重新执行或与可信任务记录绑定。

#### Retest 与 VRTM 演化

复测读取原始 audit JSON、原 RunSession 和当前源码，重新生成运行面。结果分为 resolved、new、changed 和 open。一个风险即使原始 Finding 的代码行被删除，如果同一入口出现新的高权限路径，VRTM security change analysis 仍会要求复核。

复测不是重复执行原始 prompt。它会重建候选、重新执行安全谓词、比较 evidence bundle、检查负向/合法控制，并保留修复前后 artifact refs。VRTM snapshot 使用稳定的项目哈希作为外部状态目录键，Docker 只读挂载项目时也可以保存模型历史。






### 当前实现核对：VRTM 运行面风险建模

#### 建模目标

VRTM（Vibe Runtime Threat Model）不是传统的静态组件清单。它要回答的是：一个 Vibe Coding 应用中，用户输入、模型指令、外部内容、工具能力、文件和部署身份如何在同一个运行面上相互作用；哪些节点跨越了信任边界；哪些风险假设需要验证；修复后运行面是否发生了安全意义上的变化。

运行面建模的最小单位是“能够参与安全属性变化的节点或关系”，而不是任意代码行。一个页面入口、一个 API、一个提示词模板、一个 MCP 工具、一个工作区、一个服务身份和一个文件目录只有在影响输入、权限、数据、指令、能力或外部边界时才应进入图中。

#### 节点类型

| 节点类型 | 示例 | 安全含义 |
| --- | --- | --- |
| `user_entry` | 登录页、聊天框、上传接口 | 不可信输入或用户意图进入点 |
| `web_route` | `/api/v1/prediction`、`/vendor` | 请求入口、身份和会话边界 |
| `data_store` | SQLite、文件、向量库、缓存 | 敏感数据和持久状态 |
| `instruction` | system prompt、template、retrieval chunk | 指令影响和间接提示词注入 |
| `external_content` | URL、供应商上下文、网页 DOM | 不可信外部内容进入模型或工具 |
| `tool` | shell、文件、浏览器、MCP server | Agent 能力和权限扩大 |
| `authority` | service account、workspace、owner、admin | 权限、身份和所有权事实 |
| `artifact` | 上传文件、代码包、报告 | 文件访问、解析、供应链和输出 |
| `model` | DeepSeek、OpenAI-compatible、嵌入服务 | 模型输入输出和供应商边界 |
| `deployment` | container、host、public endpoint | 环境、网络和信任边界 |
| `control` | validator、allowlist、approval、sanitizer | 保护条件和修复控制 |

#### 边类型

| 关系 | 含义 | 典型风险 |
| --- | --- | --- |
| `reads` | 节点读取数据 | 越权读取、敏感信息暴露 |
| `writes` | 节点写入状态 | 身份覆盖、业务状态篡改 |
| `flows_to` | 数据或指令流向另一节点 | 注入、XSS、代码执行 |
| `invokes` | Agent/服务调用能力 | 过度代理、命令执行 |
| `trusts` | 一个节点把另一节点作为事实来源 | 前端身份、外部页面、供应商上下文失信 |
| `authorizes` | 权限节点决定动作是否允许 | BOLA、IDOR、越权 |
| `contains` | 工作区、容器或文件目录包含对象 | 路径穿越、容器边界逃逸 |
| `deploys` | 构建/Agent 发布到环境 | 高权限发布、供应链 |
| `observes` | 工具或 Harness 观察运行信号 | 证据绑定和验证升级 |
| `mitigates` | 控制缓解某个路径 | 修复是否真正覆盖风险 |

#### 建模流水线

VRTM 建模分为六个阶段：资源发现、语义提取、复合拼接、声明合并、假设生成和快照演化。声明中的环境、身份、外部服务和批准边界只能来自用户或可信配置，不能把扫描推测写成项目事实。假设必须包含 evidence predicate、覆盖诊断和状态，不允许仅凭节点存在就声称漏洞。

#### 图的可视化投影

完整图用于算法和证据追踪，不直接作为唯一前端画布。前端展示数据、指令、权限和证据四个投影。投影可以折叠低风险节点、合并相同文件内的重复边、显示风险链主路径，并在旁栏展示节点事实、关系语义、来源位置、证据等级和未决问题。

节点可拖动、缩放和聚焦，但拖动只改变 UI 布局，不改变 VRTM 事实；用户手动布局也不能被当作威胁证据。图中节点数量很多时，优先显示高价值路径和聚合节点，点击聚合节点后再展开局部子图。

#### 去重、严重度与可读性算法

图算法拆成实体规范化、关系压缩、风险聚类和展示排序四层。去重键优先使用漏洞类型、规范化文件路径、行范围、入口节点、危险 sink、关键权限节点和语义流摘要；原始 Finding ID 和 `duplicate_finding_ids` 保留在证据面，防止聚类导致审计不可追溯。

严重度排序使用 `critical > high > medium > low > info` 的基本等级，再叠加置信度、是否跨越权限/部署边界、是否到达高权限工具、是否存在可观测 sink、是否需要动态证据等因素。排序只决定审查和展示优先级，不自动改变 Finding 的事实严重度。

#### 图的质量诊断

VRTM 输出 `quality.diagnostics` 和 `graph.coverage.unknowns`。常见诊断包括框架适配器缺失、调用关系无法解析、部署身份未声明、外部服务未声明、工具权限未知、验证谓词缺失、图节点没有证据来源和模型快照不能与基线匹配。质量诊断不是安全评分，覆盖未知越多，系统越应保守地保留 `needs_evidence`。







### 5.1 复合运行面建模

第一项创新，是把 AI 网页和轻量智能体应用抽象为复合运行面。自然语言生成的页面表面上只是一个前端界面，真实风险却常常分布在本地状态、后端接口、提示词、工具权限、浏览器渲染和模型输出之间。传统检查方法容易把这些对象拆开：代码扫描看文件，接口测试看请求，提示词测试看对话，浏览器测试看页面结果。拆开之后，每个点都可能显得“不够严重”，但它们连在一起就会形成真实业务风险。

嫘祖鉴丝的做法，是用 `RuntimeSurface` 把页面入口、关键动作、提示词画像、工具画像、权限画像、信任边界、代码索引和浏览器状态放到同一张图里。这样，评估对象从“某个文件有没有漏洞”升级为“这个页面在真实运行时有哪些边界会互相影响”。Dengcheng 的学习进度篡改说明前端身份字段、学习状态和后端接口必须一起看；FinBot 的供应商上下文污染说明页面内容、外部材料和模型回答必须一起看；Open-WebUI 的富文本执行说明输出内容、渲染组件和浏览器行为必须一起看；Flowise 的工具执行说明自然语言输入、工作流节点和执行环境必须一起看。复合运行面建模的价值，在于让评委和开发者都能看清平台关注的核心：AI 生成应用真实运行时的安全边界，以及这些边界如何共同形成可验证风险。

这项创新的技术难点在于抽象粒度。抽象过粗，只能得到“前端 + 后端 + 模型”这样的空泛描述；抽象过细，又会把每个文件、每个按钮、每条请求都变成零散节点，读者很难理解。嫘祖鉴丝选择围绕安全边界建模：谁提供输入，谁执行动作，谁保存状态，谁决定权限，谁输出到页面，谁调用工具。这个粒度既能覆盖技术实现，又能服务风险解释。它让平台在面对不同类型目标时保持一致：课程系统、聊天页面、工作流平台和协作后台外观不同，但都能被映射成入口、状态、权限、工具、输出和接口之间的关系。

复合运行面也让整改更具体。单点扫描发现“某处可能越权”之后，开发者往往不知道该改前端、后端、提示词还是工具配置；运行面会告诉开发者风险边界在哪里。例如身份问题通常要从服务端身份来源收口，提示词问题要从上下文分层和工具确认收口，渲染问题要从输出进入页面前的处理点收口，工具问题要从执行前权限门禁收口。这种从运行面到整改边界的对应关系，是平台能够回送 AI 修改提示的基础。

### 5.2 链式风险解释

第二项创新，是用 `RiskChain` 把发现项转化为可复核路径。普通扫描结果往往只告诉开发者“字段可改”“提示词可注入”“页面内容可执行”“文件路径可控”，但没有说明这些信号怎样进入业务链路。对评审和验收来说，真正关键的是“风险为什么成立、触发条件是什么、影响落在哪里、怎样复测”，工具命中只是一条线索。

嫘祖鉴丝会继续补齐入口、前提、失效边界、触发动作、可观察证据和业务影响。这样，开发者能够看懂为什么一个前端学号字段会升级为学习进度冒用，为什么一段外部内容会影响页面助手，为什么缓存文件会进入浏览器执行面，为什么一个工作区编号会导致跨租户数据风险。第六章中的 Dengcheng、PraisonAI IDOR、Flowise Airtable 和 n8n 符号链接案例，都展示了风险从入口到证据的完整路径，避免只停留在“命中漏洞”的单点展示。风险链的价值，在于把安全结论从“工具命中”变成“可解释、可讨论、可复测”的工程对象。

风险链还有一个重要作用：把不同证据强度的结果区分开。一个发现项如果只有代码线索，没有触发路径和证据谓词，就更适合进入待验证队列；一个发现项如果已经有入口、前置条件、状态差异和业务影响，就可以进入高优先级验证；一个发现项如果验证失败或证据不足，则保留为不确定结论，而不是写成确认风险。通过风险链，平台可以解释为什么某些问题被确认、某些问题需要复核、某些问题只适合进入校准或回归候选。

对 AI 编程工作流而言，风险链还可以防止修补提示过于泛化。没有风险链时，AI 编程助手可能收到“修复越权问题”这样的模糊要求；有了风险链后，提示可以明确说明：入口页面是什么，请求参数是什么，服务端信任了什么字段，验证证据是什么，修复后要阻断哪条路径、保留哪条合法路径。这样的提示更容易生成正确补丁，也更容易被平台复测。

### 5.3 会话化验证与证据包

第三项创新，是把验证过程对象化为 `ValidationSession`，并将结果整理为 `EvidenceBundle`。AI 生成应用的安全问题很容易停在“看起来可能有问题”的层面，尤其是提示词、页面结构、工具调用和浏览器行为混在一起时，单靠文字描述很难让开发团队相信问题真实可达。当前模型和 Harness 代码支持会话、授权检查、步骤执行、事件和证据目录化；审批、复核、重试、恢复和回放是会话协议/CLI 能力，尚未由前端统一操作。证据材料保存截图、页面结构、网络请求、状态差异、工具调用和运行结果。

这一设计直接解决“证不实”的问题：报告里的确认风险都能回到会话、请求、截图和状态差异中复核，形成证据链，避免停留在模型猜测或人工备注。上一版历史实验中的 70 条公开漏洞复现实验采用三态方法：漏洞态证明风险可触发，修复态证明恶意路径被阻断，合法控制证明业务能力仍然保留。这个方法对真实开发很重要，但这些历史成绩不等于当前版本的新增检测率；当前版本多靶场与 LLM 复测数据在第六章单独统计。

会话化验证的创新点还体现在“验证过程本身可治理”。平台把验证计划、审批状态、执行事件、阻断原因、证据条目和复核结论都保存在会话对象中。这样，当验证涉及删除、写入、外部请求或高危工具调用时，可以先进入审批；当验证失败时，可以查看失败发生在权限门禁、工具解析、浏览器动作还是服务接口；当证据不足时，可以追加步骤或重试。验证会话因此既是执行对象，也是审计对象。

证据包则解决了“材料散落”的问题。真实实验会产生截图、请求记录、页面文本、状态差异、运行报告、对比摘要和清理记录，如果没有统一证据包，报告很快会变成不可复核的文字描述。嫘祖鉴丝将这些材料挂接到任务和验证会话之下，使报告、整改、复测和回归都能引用同一组证据。对评审而言，系统在展示结论的同时，也保留了结论背后的验证材料。

### 5.4 整改回送与 AI 修改输入

第四项创新，是把确认风险转化为 AI 编程流程可继续使用的整改输入。AI 生成开发的现实流程是：发现问题以后，下一轮修改往往仍然由 AI 编程助手参与完成。如果安全报告只停留在“存在越权”“存在注入”“建议加强校验”，开发者还要手工把报告翻译成提示词、补充修复边界、再写复测要求，过程慢且容易丢失关键约束。

嫘祖鉴丝通过 `RemediationBundle` 写清失败边界、根因、修补原则、修补提示词、复测计划和验收条件。对于前端身份可信源失配，它要求服务端登录态或令牌链成为身份来源；对于提示词注入，它要求上下文分层、不可信标记和工具确认；对于页面脚本执行，它要求安全渲染和内容消毒；对于多租户越权，它要求工作区、所有者和角色范围在服务端收口。这样的输出可以直接进入 AI 编程助手的下一轮修改，使安全审查从“报告给人看”推进到“结果能继续驱动修改”。这也是本作品区别于单纯扫描器的重要价值：它面向的是 AI 开发现场中发现、修补、复测连续发生的真实流程。

整改回送的核心在于把建议变成可执行约束。平台会把“应该修什么”拆成几类信息：失败边界说明问题为什么成立，修补约束说明哪些做法必须避免，AI 修改提示说明下一轮修改应聚焦的位置，验收条件说明修完后如何判断通过，复测计划说明平台如何重新验证。这样，开发者和 AI 编程助手拿到的是一份可以直接进入修改流程的任务说明。

这项能力也使平台适合持续迭代。AI 编程助手生成补丁后，平台可以根据原始复测计划重新创建验证会话；如果修复成功，风险进入回归基线；如果修复失败，回送状态可以标记为 returned，并带回失败证据；如果问题属于误报或公告漂移，则进入校准路径。整改回送因此连接了“发现问题”和“长期治理”，让安全结果不再停留在一次报告中。

### 5.5 多目标回归与公告漂移治理

第五项创新，是把真实目标、公开漏洞复现、现实事件语义样本和公告漂移探针纳入同一注册和指标体系，同时保持统计边界清晰。安全报告最容易出现的失真，是把不同证据强度的材料混在一起：真实页面验证、公开漏洞复现、事件语义映射和版本公告探针看起来都像“案例”，但它们能证明的事情不同。嫘祖鉴丝在指标体系中明确区分这些材料，真实目标用于证明平台能进入实际页面，正式三态实验用于证明漏洞态、修复态和合法控制，语义样本用于映射公开事件风险结构，公告漂移探针用于记录公告版本、发布包和运行行为不一致的情况。

这种做法带来两个实际价值。第一，上一版历史实验中的 `85` 个目标、`70` 条正式复现实验、`63` 个不同 CVE、`133` 条公告引用和 `9` 个产品族共同说明方法能够跨越单个演示样例；这些数字不作为当前版本新增检测率。第二，平台不会把证据不足的结果写成确认漏洞：`4` 条现实事件语义样本只承担风险结构映射作用，`4` 条公告漂移探针单独统计，不并入 70 条正式复现成绩。对评委而言，这种边界意识本身也是工程可信度的一部分。

### 5.6 技能化安全门禁

第六项创新，是把安全审查验证能力包装成可以接入 AI 编程工作流的单一 `vibe-sec` Skill，让开发者在生成页面之后可以继续留在当前会话中完成送检，并取得整改和复测输入。vibe coding 的核心特征是会话连续性：需求、代码、错误、运行日志、提示词、工具说明和下一轮修改都在同一条对话或同一组工作流节点中发生。安全结果如果不能回到这个上下文，就会被开发者重新转述、删减和误解。当前 Skill 负责把会话材料规整为平台任务，并把确认风险、证据引用、修补约束、AI 修改提示和复测计划作为结果返回；自动回送、外部回调和终态门禁仍属于后续集成。

这种创新的价值不在于多做一个脚本入口，而在于建立安全审查与 AI 修改之间的可消费结果约定。当前单一 `vibe-sec` Skill 通过 CLI/API 参数和结构化输出传递任务标识、Finding、VRTM 引用、RemediationBundle、修补提示和复测条件；`core/remediation/skill_relay.py` 只维护本地整改投递状态。`workflow_contract`、`developer_handoff`、`skill_relay_bridge` 和 `finalization_summary` 可以作为未来外部集成的概念，但不属于当前稳定 API。这样，安全结果进入下一轮修改时仍保留风险链、证据链、整改链和复测链，同时明确自动桥接尚未交付。

对真实开发而言，这个机制解决了“改不顺”的深层问题。很多 AI 生成页面的问题并不难描述，难的是让修补动作始终带着边界：身份问题要改为服务端会话事实，不能只隐藏前端字段；输出渲染问题要在写入点前消毒，不能只过滤某个字符串；工具调用问题要在执行前门禁，不能只在提示词里提醒模型；多租户问题要在服务端收口工作区、所有者和角色，不能只让页面不显示按钮。平台把这些边界写进 `patch_constraints` 和 `acceptance_criteria`，再由技能回送给 AI 编程助手，使后续修改更接近可验收工程任务。

这一点也提升了作品的现实吸引力。面向课程系统、中小团队原型、智能表单、内部运营后台和轻量智能体页面，开发者真正需要的是“快速生成之后如何放心交付”。嫘祖鉴丝给出的答案是：继续保持一句话生成和一句话修改的效率，但在每轮关键交付前插入可调用、可验证、可回送、可复测的安全门禁。

### 5.7 受控智能体协作

第七项创新，是把多智能体协作纳入控制平面治理。平台为不同角色设定输入范围、输出结构、预算和证据策略。运行面角色负责整理目标边界，审查角色负责提出风险线索，监控角色负责检查证据覆盖和过度声称，风险链角色负责建模路径，验证计划角色负责选择可执行步骤，执行协调角色负责进入受控验证，证据复核角色负责判断结论是否成立，整改角色负责生成修补和复测材料。每个角色的输出都回到任务对象链中，不以自由对话作为最终交付。

这种协作方式降低了 AI 安全审查中的两个风险。第一，模型容易过度自信，平台通过监控摘要、证据覆盖、人工复核候选和推理门禁约束结论；第二，多角色容易失控，平台通过阶段记录、角色记录、审批票据和指标摘要保留控制面状态。最终形成的是可治理的智能体协作。对于面向评审的系统展示，这一点能够体现平台对 AI 审查过程本身的工程约束。

受控智能体协作还使系统具备扩展性。将来如果加入新的风险家族，例如浏览器代理误操作、MCP 工具投毒、跨应用身份委托、外部知识库污染等，只需要在运行面、风险链、验证模板和整改模板中补充相应对象，不需要推翻整体架构。控制平面会继续记录哪些角色参与、哪些证据进入、哪些审批发生、哪些结果被回送。这样的可扩展性，是平台从课程样例走向真实应用生态的重要条件。

### 5.8 创新点之间的协同关系

本章前面列出的创新点围绕同一条闭环互相支撑。复合运行面建模解决“对象看不全”的问题，链式风险解释解决“风险讲不清”的问题，会话化验证和证据包解决“结论证不实”的问题，整改回送与技能化门禁解决“结果改不顺”的问题，多目标回归和公告漂移治理解决“下一轮还会不会复发、公告是否可信”的问题，受控智能体协作则贯穿前面所有环节，保证模型参与过程可治理。

这组创新的核心价值，是把安全能力从一次性检查变成可持续工作流。传统扫描器往往停在“发现疑似问题”，人工渗透测试往往停在“证明问题存在”，普通报告往往停在“建议修复”。嫘祖鉴丝将这些动作串成对象链：发现项必须进入风险链，风险链必须进入验证会话，确认风险必须生成整改包，整改包必须带复测计划，复测通过后才能沉淀回归。每个环节都留下结构化对象，形成可查询、可恢复、可回送、可复用的安全流程。

对 vibe coding 场景而言，这种协同关系尤其重要。AI 编程助手可以快速生成大量功能，也可以快速改写已有代码；如果安全系统不能同样保持会话化和回送能力，审查结论很快会和最新代码脱节。平台把送检合同、运行面、风险链、证据包、整改包和复测基线连在一起，使每次 AI 修改都能在同一条任务链上继续推进。这样，速度优势被保留，安全门禁也不再游离于开发流程之外。

从技术深度看，平台的创新不依赖单个模型或单个规则库，而体现在对象体系和控制流程上。模型可以替换，规则可以扩展，浏览器执行器可以增加新动作，风险模板可以覆盖新漏洞族，但主链路仍然稳定：先建模边界，再解释风险，再受控验证，再证据复核，再整改回送，再复测归档。这种架构稳定性，使系统能够从当前的课程页面、轻量智能体和 AI 工作流样本继续扩展到更多生成式应用。

## 六、系统能力验证与实验结果分析

### 当前实现核对：当前系统总结

嫘祖鉴丝 Vibe Sec Platform 的最终形态，是一个把 Vibe Coding 安全问题工程化的闭环系统。它以 Skill 进入编码 Agent，以 RunSession 保持会话和状态，以 VRTM 描绘数据、指令、权限和能力共同组成的运行面，以静态和语义审查发现候选，以 LLM 进行证据阅读和风险解释，以 Harness 在授权条件下完成服务、浏览器或沙箱验证，以 evidence bundle 约束结论，以 remediation package 回送整改，以 approval gate 控制高权限修改，以 retest 和 VRTM 演化决定是否关闭。

这个系统的核心不是“模型是否聪明”，而是模型在一套可信工程边界内能否持续完成以下动作：只读取它被允许读取的证据；只调用被允许的工具；在证据不足时保留不确定；在终态协议失败时不伪造完成；把风险解释成开发者能理解的链路；把整改变成带约束的 Agent 输入；在修复后通过反向控制和合法控制重新证明安全属性；把所有过程保存成下一次审查可以复用的 RunSession、VRTM snapshot 和 evidence artifact。

因此，当前版本可以被定位为“面向 Vibe Coding 的本地、证据驱动、Skill 化安全审查验证平台”。它已经具备工程闭环和多靶场验证基础，但仍应以 `needs_evidence`、覆盖未知、LLM 波动和动态授权边界为产品事实，继续通过人工 Ground Truth、更多真实项目和可重复的 Docker/Runner 部署提高成熟度。





### 当前实现核对：后续演进路线

#### 短期：稳定当前闭环

短期目标是把当前已验证的链路稳定为日常工作流：完善 Docker 依赖缓存和国内镜像配置、补齐 Docker 镜像构建 CI、增加真实项目的 LLM acceptance 基线、把四轮终态成功率作为指标、继续优化运行面去重和前端聚焦路径、增加项目级认证和多用户审计日志。

#### 中期：提高 Agent 修复可信度

中期目标是把整改回送从“提示词 + 计划”推进到“受限 patch + 机器验收”：解析 Agent 变更范围、自动检查 patch 是否覆盖验证谓词、对高权限文件启用签名批准、运行最小负向/合法控制、比较 VRTM security change analysis，并生成可供代码评审的 diff evidence。

#### 长期：多项目、基准集与回归网络

长期目标是建立带人工 Ground Truth 的 Vibe Coding 安全基准集，分别统计静态候选、LLM 排序、验证确认、误报、漏报、整改成功率和回归阻断率；增加 Java/Go/PHP/Rust 等语义适配器；将项目运行面和历史 Finding 形成风险族回归网络；支持多节点 Runner，但继续保持控制面、证据面和高权限执行面的分离。

#### 评价指标

未来评价不只使用“发现数量”，而是至少包括 Candidate precision、Candidate recall、Evidence completeness、LLM terminal completion、Verification support rate、Remediation acceptance rate、Retest closure rate、VRTM unknown reduction、False closure rate 和 Artifact reproducibility。指标必须按项目类型、风险族、语言、是否使用 LLM、是否动态验证和证据面分层统计，不能只给一个混合平均数。

#### 实验结论与能力边界

已经被当前实现和测试支持的结论包括：平台可以跨 Python/Flask、OpenAPI/Connexion、JavaScript/TypeScript/Node 和 Agent/MCP 代码形成统一审查对象；VRTM 可以把数据、指令、权限和 artifact 投影为可聚焦的运行面图；LLM 可以在有预算、工具审计、证据绑定和终态合同的前提下辅助审查；Harness 可以使用授权、漏洞态、修复态、合法控制和清理记录支持验证与整改验收；Remediation Package、RunSession、approval gate 和 CLI/Python retest 将编码 Agent 的修改纳入可追踪流程；Docker Compose、Skill 安装器和审计 API 打通了本地交付主链路。前端动态验证、外部 Agent 回调和 UI 复测闭环仍未完成。

尚未被当前数据证明的结论包括：Juice Shop 全量精确率和召回率；所有 DeepSeek ReAct 会话在固定四轮内稳定完成；大规模多用户并发、分布式 ArtifactStore 和生产级 SQLite 替换能力；未授权外部目标的安全性；通过模型自然语言自动生成可信修复的成功率。

当前测试没有覆盖真实浏览器端到端验证提交、前端复测启动与状态回写、规划中的多 Agent 控制面 API、双 Skill 桥接或外部 Agent 自动派发。因此测试通过只能证明核心 Python/CLI/契约和部分 API 行为，不能证明前端完整工作流或生产级多用户交付已经完成。








### 6.1 实验目标与现实问题映射

第六部分验证的核心问题，是嫘祖鉴丝能否在 AI 生成应用的真实边界上形成可信闭环。自然语言生成开发与智能应用搭建平台改变了网页应用的交付方式：页面、接口、模型提示词、外部上下文、工作流节点、文件工具和浏览器渲染路径常常被快速拼接出来，开发者首先看到的是功能已经跑通，却很难同步判断认证、权限、输出、工具、文件和网络边界是否可靠。嫘祖鉴丝的实验因此不只考察“能不能发现一个漏洞”，更考察四个连续能力：能不能看见复合运行面，能不能把风险解释成链路，能不能用真实会话或运行复现实验证实风险，能不能把结论转化为整改、复测与回归输入。

实验目标对应第一章提出的四类断点。针对“看不全”，实验要求系统在真实目标和复现目标中识别页面入口、接口、提示词、工具能力、对象归属和运行状态；针对“讲不清”，实验要求每个高价值问题都能落入风险链，说明入口、前提、失效边界、触发动作和业务影响；针对“证不实”，实验要求正式漏洞复现实验具备漏洞态、修复态、合法控制三态，真实目标具备验证会话和确认/不确定判定；针对“改不顺”，实验要求每类确认风险都能对应到整改包、修补提示词、复测计划和回归基线，使安全结果可以进入 AI 编程助手下一轮修改。

#### 上一版历史实验矩阵（仅历史基线）

正式复现采用三态实验方法。漏洞态要求危险路径真实触发，并在 HTTP 状态、对象状态、文件内容、浏览器执行、工具输出或函数返回中留下可观察信号；修复态要求同一路径的恶意输入被阻断，阻断信号可以是 `400/403/404/422/500` 等预期响应，也可以是验证器、策略门禁、权限门禁、工作区范围校验、所有者/管理员校验、真实路径保护、DOMPurify、MIME 校验、Host Header 校验或服务端身份字段保持；合法控制要求正常功能仍然保留，证明修复没有把业务能力粗暴关闭。三态同时成立，实验才被视为完整验证。

证据面同样分层。`62` 条复现实验采用接口/服务级运行验证，覆盖工作流平台、对象权限、认证、文件访问、服务端请求伪造、配置暴露和缓存污染等行为；`3` 条采用浏览器和页面行为证据，覆盖富文本、文件预览和前后端收窄运行链路中的脚本执行；`5` 条采用函数级验证，覆盖 LangChain Core 的提示词、模板、路径和序列化边界。运行证据保留总量为 `148.7MiB`，平均单实验 `2.1MiB`，最大保留实验为 `praisonai-platform-label-idor-0.1.3-replay-lab`，保留 `5.7MiB`。这说明实验既保留了复核所需材料，也控制了长期证据体量。

> 图 6-1（文字指标）：验证授权、正向控制、负向控制、证据绑定和清理状态共同决定 `verified/needs_evidence`，不是单一模型判断。

图 6-1 把三态验证的关键门禁压缩为一组质量指标：修复态对照、运行确认、修复态阻断和清理后记录均达到 `70/70`，说明实验同时验证了漏洞态存在、修复是否生效、正常控制是否保留、记录是否可长期复核。`67/70` 的证明差异和 `65/70` 的强运行确认，也说明平台能够在大多数样本上取得足够清晰的前后对比。对实际使用而言，这组指标支撑的是“证实”和“可验收”，解决了安全结果停留在疑似清单的问题。

正式复现的三态方法是本章最重要的实验方法。漏洞态回答“风险能不能触发”；修复态回答“恶意路径是否被阻断”；合法控制回答“业务能力是否仍然存在”。三者缺一不可。只有漏洞态，没有修复态，就只能说明风险存在，不能说明平台能支持整改；只有修复态，没有合法控制，可能只是把功能关掉；只有接口返回，没有清理记录，后续复核就缺少长期材料。嫘祖鉴丝用同一套三态标准约束 70 条实验，使不同产品、不同风险族、不同证据面之间可以被放在同一张质量表里比较。

实验材料体量也受到控制。`148.7MiB` 的长期保留材料覆盖 70 条正式复现，平均每条 `2.1MiB`，说明平台没有用无限制材料堆积换取“证据充分”的表面效果。对真实团队而言，证据既要能复核，也要能长期保存和检索；如果每条实验都产生大量不可管理文件，平台很难进入持续回归。当前材料规模说明系统在证据完整性和存储可管理性之间做了平衡。

从实验方法上看，三态验证同时控制了三个常见误区。第一个误区是只证明漏洞态可触发，却没有证明修复路径，因此无法支持整改验收；第二个误区是只证明恶意输入失败，却没有证明正常业务仍可用，容易把“修复”变成“关掉功能”；第三个误区是只保存最终结论，没有保留足够材料，导致后续版本无法复核。嫘祖鉴丝将漏洞态、修复态、合法控制和清理后记录同时纳入指标，正是为了让实验结果可以服务真实交付。

`70/70` 修复态对照和 `70/70` 运行确认说明每条正式复现实验都至少完成了“风险可达”和“修复可验”的基本门槛。`65/70` 强运行确认说明绝大多数实验不仅有状态码或文本信号，还具备更强的运行行为证据，例如对象变化、文件访问、浏览器执行、工具到达或函数返回。`67/70` 证明差异说明大部分实验能清楚展示漏洞态和修复态之间的行为差异。少数没有达到强差异的样本仍保留在正式清单中，是因为它们满足三态验证的最低证据门槛，但报告没有把它们包装成更强结论。

这种指标解释对读者很重要。安全实验不能简单追求“全部满分”，还要说明每个数字代表什么证据强度、能支撑什么结论、不能支撑什么结论。嫘祖鉴丝在报告中把正式复现、真实目标、语义样本和漂移探针分开，就是为了让读者能够区分“已运行确认”“结构映射”“公告边界待复核”三种不同材料。这样的边界意识，比单纯堆叠案例数量更能体现平台可信度。

图 6-4 解释了为什么报告把证据面分开讨论。接口/服务级证据占主体，适合认证、权限、对象、文件和网络边界；浏览器和页面行为证据数量较少但价值很高，适合证明脚本是否真正执行；函数级证据用于底层库和模板函数，避免为函数级边界强行搭建完整产品环境。三类证据共同说明，平台会根据风险所在位置选择验证方式，用分层证据解释不同类型的问题。

产品族分布也反映出 AI 生成应用的现实风险重心。Flowise 与 n8n 体现“自然语言编排工具和文件/网络能力”的风险；Open-WebUI 体现“用户内容进入聊天界面和浏览器渲染面”的风险；PraisonAI 体现“智能应用搭建平台自动生成团队协作后台后，对象归属与角色边界失效”的风险；LangChain Core 体现“底层提示词和模板工具在函数级输入中暴露路径、属性和序列化风险”的问题。嫘祖鉴丝没有把这些样本拆成互不相关的漏洞清单，而是统一放入运行面、风险链和三态验证框架中处理。

从产品族角度看，实验覆盖了 AI 应用的三条主线。第一条是“工具编排线”，包括 Flowise、Langflow、n8n、AgenticMail 和 MCP SDK，重点是工具、文件、网络和协议边界；第二条是“页面交互线”，包括 Open-WebUI 和 Gradio，重点是聊天界面、富文本、文件预览、缓存和浏览器执行；第三条是“应用对象线”，包括 PraisonAI Platform，重点是工作区、项目、议题、成员、标签和智能体对象的归属边界。三条主线共同对应 vibe coding 的真实结果：开发者生成的通常不止一个页面，还包括工具、对象和工作流。

从证据面角度看，接口/服务级验证占主体，说明多数 AI 应用风险最终落在认证、权限、对象、文件和网络边界上；浏览器和页面行为证据数量较少但价值高，专门用于证明脚本执行和页面渲染；函数级验证则用于底层库和模板函数，避免为了函数边界强行搭建完整系统。这样的分层使实验更加务实：风险在哪里，就在哪里验证。

从复现结果看，70 条实验还证明平台具备“公告到验证”的转化能力。公开漏洞描述通常只给出影响版本、风险类型、触发条件和修复建议，不能直接变成可运行实验。平台需要先把公告内容转化为目标画像，再抽取入口、参数、权限前提和预期信号；随后构造漏洞态、修复态和合法控制，最后记录清理和长期材料。这个过程本身就是系统能力的一部分，因为真实开发团队拿到的也往往是公告、依赖版本和少量描述，而不是完整的测试脚本。

不同产品族之间的差异也检验了架构的泛化能力。Flowise 和 Langflow 更接近工作流工具，风险常落在节点配置、代码执行和文件/网络能力；Open-WebUI 更接近聊天界面，风险常落在富文本、文件预览、工具权限和缓存；PraisonAI 更接近智能应用后台，风险常落在工作区、对象归属和角色边界；LangChain Core 更接近底层库，风险常落在函数参数、模板和序列化。平台用同一套对象链处理这些差异，说明运行面和风险链抽象具有跨产品适用性。

这组结果也能反向说明为什么只做静态扫描不足。工具执行、服务端请求伪造、对象越权、缓存脚本执行、符号链接文件读取和模板路径穿越分别需要不同证据面；有些需要浏览器，有些需要接口，有些只需要函数级探针。嫘祖鉴丝的验证层允许按风险位置选择证据面，避免把所有问题都强行塞进同一种测试方法。

### 6.5 按现实风险族分析系统能力

**认证与会话边界。** AI 生成页面通常能很快生成登录、重置密码、临时 token、API key 和工具接口，但服务端会话校验、一次性凭据约束和默认认证策略常常滞后。Flowise resetPassword 证明了重置链中无效临时 token 应被服务端拒绝；Langflow validate/code 证明执行类接口必须先经过认证；AgenticMail MCP HTTP auth 与 PraisonAI call server auth default 证明智能体工具路由不能默认开放。嫘祖鉴丝在这一族风险上证明的能力，是从 `RuntimeSurface` 中定位认证前提，再通过运行复现观察未认证调用、无效 token 或默认开放接口是否可达，最后把服务端会话校验、token 绑定、默认拒绝和有效控制路径写入整改包。

**权限、租户和对象边界。** 智能应用搭建平台和团队协作后台常自动生成 workspace、project、issue、member、label、agent 等对象页面，后端如果继续信任客户端传入的对象 id、owner、role 或 workspace，就会形成跨租户读改删。PraisonAI Platform 0.1.3 系列集中展示了这一问题：workspace、issue、activity、comment、project、dependency、member、label 和 agent 均出现跨空间读写、删除、链接、解除链接或角色提升路径；Open-WebUI folder owner injection 与 feedback mass assignment 也证明身份字段和归属字段不能由客户端覆盖；Flowise dataset/documentstore/evaluation takeover 进一步说明对象创建和更新中的 protected fields 必须剥离。嫘祖鉴丝对这一族风险使用对象 id、角色、空间、动作和响应差异建立 `RiskChain`，并用工作区范围、所有者/管理员门禁、issue 范围校验、服务端派生身份字段等修复态信号证明边界已收紧。

**工具调用与代码执行边界。** 自然语言生成开发的高风险点之一，是页面节点、插件、MCP、OpenAPI、Python/JS 工具被自然语言输入直接驱动。Flowise Airtable 与 CSV Agent 证明生成代码可以进入 pyodide；Flowise CustomMCP、MCP、Node Custom Function 和 Langflow custom component 证明配置解析、命令初始化和自定义组件可能跨入执行环境；Open-WebUI tool update 证明工具内容更新需要工作区权限门控。嫘祖鉴丝在这一族风险上关注三个信号：危险输入是否进入执行环境，修复态是否在执行前由验证器、策略门禁或权限门禁阻断，正常工具或安全数据处理路径是否仍保留。这个能力直接服务于 AI 工作流平台，因为开发者最容易忽略的正是“能跑的工具节点”背后是否已经形成执行边界。

**输出渲染与页面结构边界。** AI 生成内容、Markdown、富文本、文件预览、SVG、音频缓存、聊天消息和 profile 图片进入浏览器后，风险从后端字符串变成真实页面行为。Open-WebUI RichText、FilePreview、Audio Cache、Webhook Profile SVG 和 OAuth Picture SVG 覆盖了这一类风险。嫘祖鉴丝的浏览器和页面结构证据证明脚本是否真的执行，而服务级证据证明 MIME、附件响应头、头像校验、扩展名限制和安全渲染控制是否生效。与只看响应内容的检查相比，浏览器证据的价值在于能判断危险内容是否到达执行点、是否被浏览器执行、修复后安全 Markdown 或合法图片是否还能正常使用。

**文件访问与路径边界。** AI 工作流和智能体工具经常需要读写文件、上传文件、读取模板、加载图片或解析符号链接。Gradio arbitrary file read、n8n read/write file symlink、Flowise read/write file/get upload file、LangChain path traversal 和 image path read 共同覆盖这一族风险。嫘祖鉴丝在验证中关注文件内容是否真实返回、路径是否越过允许目录、符号链接是否在检查前被解析、上传引用是否可被伪造、模板路径是否允许相对穿越。修复态通常体现为真实路径保护、工作目录限制、路径校验、MIME 允许列表和安全模板加载。合法控制则证明同工作区、同 HTTP 文件边界或安全字符串仍可使用。

**网络与服务访问边界。** AI 应用为联网、OpenAPI 加载、RAG 搜索、MCP 工具和 webhook 自动开放外部请求能力，常把服务端请求伪造、Host Header、DNS rebinding 和私有网段访问带入系统。Flowise Execute Flow 与 OpenAPI Toolkit SSRF、Open-WebUI RAG Web Search SSRF、MCP SDK DNS rebinding、n8n webhook IP whitelist 共同覆盖这一族风险。嫘祖鉴丝通过 loopback、私有网段、mapped IPv6、Host Header、IP 比较和公开控制样本验证边界是否收紧。整改输出对应拒绝列表、允许列表、主机校验、严格 IP 比较、私有网段阻断和规范主机名校验。

六类风险族共同覆盖了 AI 生成应用的主要失效方式。认证与会话边界决定“谁能进入”；权限与对象边界决定“能操作谁的数据”；工具与代码执行边界决定“用户输入能不能变成系统动作”；输出渲染边界决定“模型或用户内容能不能进入浏览器执行面”；文件路径边界决定“工具能不能越过工作区”；网络访问边界决定“系统能不能被诱导访问内部或伪造目标”。这些风险族共同构成平台的核心审查范围，也解释了为什么单一静态检查难以覆盖 vibe coding 应用。

每一类风险族都对应明确整改模板。认证问题回到服务端会话、令牌绑定和默认拒绝；权限问题回到工作区、角色、所有者和对象范围；工具执行问题回到执行前验证器、策略门禁和最小权限；渲染问题回到消毒、编码、内容类型和安全组件；文件问题回到真实路径、工作目录和允许列表；网络问题回到主机校验、私有网段阻断和严格比较。实验不仅证明平台能发现这些风险，也证明平台能把风险转成可执行修补要求。

| 风险族 | 典型入口 | 关键证据 | 整改回送重点 |
| --- | --- | --- | --- |
| 认证与会话 | 登录、重置密码、工具接口、临时令牌 | 未认证调用、无效令牌写入、默认开放路由 | 服务端会话校验、令牌绑定、默认拒绝、一次性凭据 |

表 6-3 将风险族、证据和整改回送关系放在一起，是为了说明平台并没有把实验结论停留在漏洞名称层面。每一类风险都必须能够回答三个问题：从哪里进入，怎样证明，应该怎么改。只有这三个问题都能回答，风险才适合进入 AI 编程助手的下一轮修改。如果缺少入口，AI 修改容易找错位置；如果缺少证据，开发者难以判断优先级；如果缺少整改重点，模型可能生成表面修复。

这些风险族也反映了平台对现实痛点的覆盖。课程型 AI 页面重点落在认证、会话、权限和提示词边界；轻量智能体页面重点落在提示词、输出、工具和上下文清理；AI 工作流平台重点落在工具执行、文件和网络边界；智能应用搭建平台重点落在对象归属和角色权限。通过同一套风险族归纳，报告把多个看似分散的案例重新收束为读者能理解的安全问题地图。

Flowise Airtable Agent 3.0.13 复现对应 `CVE-2026-41265`，代表工具调用与代码执行边界。实验入口为 `/api/v1/prediction/demo-chatflow`。漏洞态中，危险输入被工作流节点转化为生成代码，并到达 pyodide 执行路径，HTTP 状态为 `200`，说明风险已经超出静态字符串命中，输入真实进入执行环境。修复态中，验证器在执行前拒绝恶意载荷，HTTP 状态为 `422`。合法控制中，安全的数据表控制样本仍能进入 pyodide，证明修复保留了正常数据处理能力。该案例说明，嫘祖鉴丝可以把“AI 工作流工具会不会执行用户输入”拆成入口、执行信号、修复阻断和正常控制四个可验证条件。

n8n Read/Write File Symlink 1.105.0 复现对应 `CVE-2025-57749`，代表文件访问与路径边界。漏洞态中，符号链接穿越导致文件访问被观察到；修复态中，系统先解析真实路径，再做允许路径检查，从而阻断符号链接逃逸；合法控制保留同 HTTP 文件边界内的读写能力。该案例说明，文件类风险不能只看路径字符串是否包含 `../`，还必须验证符号链接解析顺序、真实文件系统位置和业务允许目录之间的关系。嫘祖鉴丝的 `RiskChain` 在这里表达了从用户可控文件引用到真实文件访问的完整路径。

Open-WebUI 0.6.34 RichText 复现对应 `CVE-2025-64495`，代表输出渲染与页面结构边界。漏洞态中，浏览器观测到脚本执行，并取得可视化证明；修复态中，DOMPurify 在进入渲染点前完成消毒；合法控制中，同一 `innerHTML` 渲染点仍保留安全 Markdown 渲染。该案例展示了浏览器和页面结构证据的核心价值：系统不仅知道 HTML 里存在危险片段，还能证明脚本是否真实执行，并证明修复后安全 Markdown 仍可正常渲染。

PraisonAI Platform Issue IDOR 0.1.3 复现对应 `CVE-2026-47415`，代表权限、租户和对象边界。漏洞态中，系统观测到跨工作区读取、更新和删除；修复态中，工作区范围校验对跨空间 issue 返回 `404`；合法控制中，同工作区 issue 操作被保留。该案例对应智能应用搭建平台生成后台最常见的现实风险：页面自动生成了对象管理能力，但后端没有把 workspace、role、owner 和 issue scope 作为服务端事实。嫘祖鉴丝通过跨空间对象、同空间控制和修复响应差异，证明权限边界是否真正回到服务端。

Flowise resetPassword 3.0.13 复现对应 `CVE-2026-41276`，代表认证与会话边界。漏洞态中，系统观察到重置密码写入，说明重置链允许危险写入；修复态中，无效临时 token 被拒绝；合法控制中，同一路由下的有效临时 token 重置能力被保留。该案例的重点在于，重置密码不能只以路由存在与否作为判断，必须验证临时 token 与用户、时效和重置动作的绑定关系。嫘祖鉴丝的整改输出因此要求服务端 token 校验、一次性使用、有效期、绑定对象和复测路径同时成立。

Open-WebUI 0.9.4 Feedback Mass Assignment 复现对应 `CVE-2026-45396`，代表身份字段和对象归属边界。漏洞态中，反馈记录被写入到伪造的受害者身份下；修复态中，服务端派生的身份字段被保留；合法控制中，同一路由的反馈创建能力仍然可用。该案例说明，AI 生成应用中常见的表单和反馈入口如果允许客户端提交身份字段，就会把“可编辑 JSON”变成真实业务身份覆盖。嫘祖鉴丝在这里验证了服务端派生身份字段是否压过客户端输入，并把修复要求写成可回送给 AI 编程助手的修改约束。

这些代表性案例的共同点，是都包含“漏洞态、修复态、合法控制”三种信号。Flowise Airtable 证明危险输入能进入代码执行环境，也证明验证器能在执行前拒绝，并保留安全数据处理能力；n8n 符号链接证明路径风险不仅是字符串问题，还要验证真实路径解析顺序；Open-WebUI 富文本证明浏览器执行证据比响应文本更有说服力；PraisonAI IDOR 证明对象归属必须回到服务端工作区范围；Flowise 重置密码证明临时凭据必须绑定用户、时效和动作；Open-WebUI 批量赋值证明客户端身份字段不能覆盖服务端事实。它们分别对应平台的六类风险族，也共同支撑“发现、证实、整改、复测”闭环。

对评审而言，这些案例还展示了平台跨漏洞类型工作的能力。代码执行、路径穿越、浏览器脚本、越权访问、认证缺陷、身份覆盖分别落在不同技术层面，但都能被平台转化为运行面、风险链和验证会话。这种跨风险族的一致处理能力，是系统架构有效性的直接体现。

### 6.7 真实事件语义样本

现实事件语义样本用于把公开事件中的风险结构转化为稳定回归场景，结论范围限定为风险语义映射。AXIS Camera Station Pro 样本映射的是认证边界失守语义，对应公开事件中未授权访问高价值监控资源的风险结构。系统将其抽象为登录、bootstrap、live view、recordings、smart search、dashboard、users 和 devices 等运行面入口，用来验证“认证前提缺失如何影响高价值资源访问”这一类问题。该样本的价值在于把公开事件中的认证失效结构转化为可复用的运行面和回归条件。

AI Form Builder 样本映射的是生成内容进入预览渲染面的存储型 XSS 语义，对应 `CVE-2026-0996` 的公开记录。嫘祖鉴丝将其抽象为 builder、preview 和 submissions 等入口，关注不可信生成内容如何进入浏览器渲染面，如何通过消毒、输出编码和安全组件进行整改。Base44 Private App 样本映射的是私有应用认证绕过语义，将 register、verify-otp、private-app 和 members 等路径组织为认证边界回归目标。Lovable Data Permission 样本映射生成页面身份与后端数据权限脱钩的风险，参考 `CVE-2025-48757` 的 disputed 公开记录，只表达行级安全策略不足可能带来的数据权限问题。

这四类样本共同说明，嫘祖鉴丝面向的是现实世界已经出现的风险结构：认证边界、数据权限、输出渲染和生成页面默认发布链。它们为报告提供现实贴合度，也为系统提供可复用的语义回归目标；同时，报告严格区分语义映射与正式公开漏洞复现，语义样本只承担风险结构映射和回归目标构造作用。

### 6.8 公告边界漂移分析

公告边界漂移探针用于处理公开公告、版本声明、发布包和运行行为之间的不一致。实验中共有 `4` 条漂移探针，人工复核通过 `4/4`，运行探针确认 `4/4`，已发布修复版本仍触发的漂移为 `1/4`，已发布受影响版本未按公告表现的漂移为 `1/4`，涉及 `4` 个不同 CVE 和 `8` 条公告引用。它们不并入 `70` 条正式复现成绩；漂移探针的目标是判断公告边界是否与运行行为一致。

Flowise TTS Credential 3.0.13 公告漂移探针对应 `CVE-2026-41279`。运行探针显示触发版本包括 `3.0.13`、`3.1.0`、`3.1.1` 和 `3.1.2`，其中 `3.1.0`、`3.1.1`、`3.1.2` 属于公告称已修复但仍触发风险信号的版本。嫘祖鉴丝因此将其归入公告固定边界漂移。n8n Expression Escape `CVE-2026-25049`、n8n Git Pre-Commit Hook `CVE-2025-62726` 和 Langflow Shareable Playground 1.9.1 也作为漂移探针单独记录，用于提示开发者不要把公告版本文字直接等同于运行时安全状态。

这一机制对 AI 生成应用安全治理很关键。开发者在 AI 编程助手中修复依赖或升级版本时，经常会根据公告文字让模型“升级到安全版本”，但真实发布包、依赖范围、默认配置和运行行为可能仍存在差异。嫘祖鉴丝把公告漂移探针独立出来，可以让报告同时呈现“正式复现实验已经证明的内容”和“公告边界仍需复核的内容”，避免把证据边界不清的结果写成确定修复。

### 6.9 实验结果对系统创新点的支撑

上一版历史实验材料为前文提出的五项创新提供了方法依据，而不是当前版本新增成绩。历史真实目标将页面状态、学习进度接口、外部页面结构、vendor contexts 和提示词边界放入同一运行面；历史多产品复现则覆盖工具、对象、文件、网络和浏览器渲染。历史案例展示了如何把表层信号延展为入口、前提、失效边界、触发动作、证据条件和影响结果；当前代码与多靶场结果仍需独立评估。

历史材料中的 `10` 个真实目标验证会话和 `70` 条三态复现展示了会话化验证、证据包、整改提示和复测条件的组织方式。它们说明历史实验如何把认证、权限、渲染、文件和网络问题转成修补约束；不表示当前前端已经提供自动验证、外部回调或批量回归。`85` 个目标、`4` 条语义样本和 `4` 条漂移探针也均属于历史基线，当前版本结果必须引用独立的 2026-08-02 测试记录。

从效果看，嫘祖鉴丝已经把安全审查从“发现疑似问题”推进到“证实、解释、整改回送、复测支撑”。这正是 AI 生成应用场景最需要的能力：开发者不只需要知道某处可能有漏洞，还需要知道为什么成立、证据在哪里、该如何改、改完怎样验收，以及同类问题以后如何回归。

### 6.10 实验边界、历史基线结论与 70 条公开漏洞复现实验清单

历史基线结论是：上一版实验在其已验证样本和风险家族上形成了可复核的发现、验证、解释、整改提示和复测材料链。3 个历史真实目标形成 `10` 个验证会话并确认 `7` 个风险；70 条历史公开漏洞复现实验覆盖 `63` 个 CVE、`133` 条公告引用和 `9` 个 AI 应用生态产品族，并记录 `70/70` 修复态阻断、`70/70` 清理后材料、`67/70` 证明差异，长期材料为 `148.7MiB`。这些数字用于说明方法和实验资产，不作为 2026-08-02 当前版本的检测率或前端闭环证明。
