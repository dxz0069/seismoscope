# 核心可信链完善进度 0723

## 1. 本轮目标

本轮不是增加更多扫描器，而是修复会影响产品结论可信度的基础契约：

1. Verification、Finding 状态、Regression 与最终结果必须一致；
2. VRTM 的证据来源、控制语义、模型身份与变化门禁必须不可伪造；
3. Skill 返回必须适合编程助手消费，动态验证授权必须来自仓库外的可信入口。

详细设计见 `CORE_TRUST_AND_PRODUCT_HARDENING_PLAN.md`。

## 2. 已完成能力

### 2.1 Finding 最终状态

每个候选 Finding 最终只能进入以下一个状态：

- `verified`
- `rejected`
- `needs_evidence`
- `not_reviewed`

编排器会校验候选总数守恒，不再把已拒绝候选通过回退逻辑重新发布为普通 Finding。未知验证类型、工具不可用、实验失败、超时和控制无效均按 fail-closed 处理。

### 2.2 可信动态验证授权

已实现 `vibe-sec.verification-authorization.v1`：

- 授权文件必须位于被审计仓库之外；
- 使用本地 Harness 密钥进行 HMAC-SHA256 完整性保护；
- 绑定项目根目录、有效期、非生产环境、网络和服务启动权限及执行预算；
- 篡改、过期、项目不匹配、生产环境或仓库内授权均被拒绝；
- CLI 提供 `authorize-verification` 和 `--authorization`，无效授权返回受控错误，不产生 traceback。

### 2.3 PoC v2 与 Harness-owned Oracle

`vibe-sec.poc-plan.v2` 绑定：

- Finding ID 与漏洞类型；
- 项目内相对文件路径；
- Finding 行号范围；
- 当前源码 SHA-256；
- 正向和负向控制；
- Harness-owned Oracle ID；
- 授权和资源预算。

模型不再提交或持久化 `target_code`。Harness 自己读取目标源码；代码变化后旧计划因哈希不一致而失效。

当前已实现 `python.command-sink-differential.v1`。它只记录由绑定目标代码对象触发的命令 Sink，控制脚本自行设置 `VIBE_SEC_VERIFIED=True` 不会得到 verified。其他尚无可信 Oracle 的 Python 漏洞类型返回 `needs_evidence`，不得宣称已自动复现。

### 2.4 Regression 隔离

初次审计不再执行伪修复回归。Regression 仅在修复后通过 `retest` 运行，并要求：

- 修复状态和正、负控制证据；
- Artifact 或 ToolExecution 等证据来源；
- 修改文件范围符合整改包；
- 项目测试通过受限 DockerExecutor 执行；
- 默认无网络、只读工作区和资源限制；
- Docker 不可用时返回 skipped/partial，不回退到宿主机执行项目代码。

### 2.5 VRTM 证据信任

VRTMService 现在有两个 Observation 通道：

- `observations`：外部/API/CLI 输入，强制标记为 external；
- `trusted_observations`：仅供内部编排器使用，标记为 harness 并绑定 run provenance。

外部输入不能声明 verified，也不能把 Hypothesis 改成 supported、refuted 或 mitigated。

### 2.6 控制与威胁适用性

检测到控制后不再删除适用威胁。每个 Hypothesis 分开表达：

- `applicability`
- `control_state`
- `residual_status`
- `control_gaps`

控制状态为 `expected / declared / static_observed / runtime_observed / verified`。只有证据强度影响剩余风险，控制存在本身不改变威胁是否适用。

### 2.7 双指纹与变化门禁

VRTM 现在使用：

- `graph_fingerprint`：节点、边和安全属性；
- `model_fingerprint`：图指纹、声明范围、假设、排除项、声明摘要、方法版本和 Technique Catalog 版本。

快照按 model fingerprint 寻址。即使图结构不变，声明安全含义变化也会产生新模型身份。

变化门禁已覆盖授权移除、审批移除、通配权限、信任跨越、Authority Plane、新身份权限、环境晋升、数据分类降级和控制证据降级，并返回稳定 reason code 与 before/after。

零提取覆盖、零有效实体和不支持的提取结果现在为 `degraded`，不会标记为 `complete`。

### 2.8 Skill v2

默认协议为 `vibe-sec.skill-result.v2`：

- stdout 只返回触发结果、汇总、紧凑整改包和 Artifact 引用；
- 完整审计、Finding 证据和大图存入外部 ArtifactStore；
- `--full-result` 仅供明确需要完整对象的调用方；
- 真实完整审计夹具的默认 JSON 已通过小于 100 KiB 的自动化门禁。

## 3. 验证结果

```text
python -m compileall -q main.py api core agents tests
passed

python -m pytest -q
157 passed, 7 skipped
```

7 个跳过项均为当前主机缺少固定容器镜像：focused scanner、offline Trivy、Nuclei/Python fixture、CodeQL 和 Python service fixture。契约、隔离和适配器测试通过，但这些真实镜像集成路径本轮未执行。

## 4. 当前能力边界

本轮可以证明机制更加可靠，不能证明漏洞发现能力已经超过 AutoCVE，也不能证明 VRTM 方法有效性已经经过行业数据验证。

尚未完成：

- 命令注入以外漏洞家族的 Harness-owned Oracle；
- Regression 自动重新执行原始 PoC，而不是消费外部提供的 retest evidence；
- 真实镜像环境中的全工具集成回归；
- 漏洞 Recall、Precision、错误确认率、PoC 成功率和重复运行一致性测评；
- VRTM 节点、边、风险路径和 Hypothesis 的标注数据集；
- 正式 OCI 发布、签名、SBOM、离线包和升级回滚；
- Web UI。

## 5. 下一步计划

1. 建立 Verification Predicate/Oracle Registry，优先覆盖路径穿越、SQL 注入、SSRF、浏览器 XSS、提示注入和 MCP 越权。
2. 让整改包保存原始可执行验证计划，`retest` 在修复后自动重放正负控制并绑定新源码哈希。
3. 建立传统漏洞、AI/MCP/Workflow 风险和 VRTM 图抽取的统一测评集。
4. 在具备固定镜像的环境运行全部容器集成测试并记录镜像 digest。
5. 根据测评结果再决定继续加深智能体漏洞发现能力，还是扩展 VRTM 运行时 Observation 适配器。
