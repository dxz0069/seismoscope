# 运行面建模开发进度 0722

> 日期：2026-07-22  
> 模块：VRTM（Vibe Runtime Threat Modeling）  
> 范围：方法论、四平面图、风险分析、智能体证据回填、持续建模、CLI/Skill/API 和版本存储

## 1. 当前结论

运行面建模已经从早期的 Runtime Surface 静态投影推进为可独立调用的 VRTM 产品模块：

- 可以从源码和结构化配置生成确定性基础图；
- 可以通过项目声明补充源码无法观察的身份、服务、记忆、检索、凭据和部署事实；
- 可以在同一图中表达传统 Web、Agent、MCP、Workflow 和供应链风险；
- Audit 和 Verification Agent 可以把新证据受控回填到图中；
- 可以比较相邻模型，识别风险变化、权限扩大、边界变化和控制退化；
- 可以通过 CLI、Skill 和本地 API 使用，并持久化不可变快照；
- 不依赖 LLM、Docker 或传统扫描器即可完成基础建模和确定性风险分析。

当前应准确描述为：

> VRTM 的产品机制和工程闭环已经完成；抽取准确率、风险路径有效率和对最终漏洞发现率的提升仍需要正式测评。

## 2. 方法论结构

VRTM 使用四个可重叠平面：

| 平面 | 关注对象 | 主要问题 |
| --- | --- | --- |
| Data | 输入、处理、存储、输出 | 数据如何进入、传播和泄露 |
| Instruction | Prompt、Context、Memory、Retriever | 内容如何改变模型和自动化决策 |
| Authority | 身份、Tool、MCP、Token、Approval | 权限如何委托和扩大 |
| Artifact | 源码、配置、记忆、构建物、部署物 | 产物如何持久化并进入运行环境 |

建模流程已经实现为：

```text
Scope
  -> Discover
  -> Model
  -> Analyze
  -> Investigate
  -> Verify
  -> Evolve
```

图不是最终结论。风险分析输出的是带路径、控制缺口、假设和验证谓词的 Risk Hypothesis。

### 3.3 证据等级

- `declared`；
- `static_observed`；
- `inferred`；
- `runtime_observed`；
- `verified`；
- `unknown`。

证据等级和 Confidence 分开表达。较低等级的新 Observation 可以进入审计历史，但不能覆盖较高等级事实。

## 5. 风险假设实现

每条 Risk Hypothesis 当前包含：

- Source、Boundary 和 Target；
- 完整 Attack Path；
- Flow Planes；
- Impact 和 Severity；
- Evidence Confidence；
- Control Strength；
- Control Gaps；
- Evidence Predicates；
- External Mappings；
- `open`、`supported`、`refuted`、`mitigated` 状态。

没有生成单一安全分数。Severity、可利用性、证据置信度和控制强度保持独立，避免制造看似精确的结论。

## 6. 智能体持续建模

Surface Agent 先生成基础图。Audit 和 Verification 阶段随后执行：

```text
Finding / Verification Result
  -> 绑定当前稳定节点
  -> 生成 RuntimeGraphObservation
  -> 校验 Agent、Tool、Evidence Reference 和 Predicate
  -> 应用证据与有限安全事实
  -> 重算 Coverage 和 Threat Model
  -> 输出 VRTM Evolution
```

已经实现：

- Audit Finding 到图节点和 Hypothesis 的确定性绑定；
- Verification 结果回填 `verified` 或反证状态；
- Observation 重复 ID 拒绝；
- 未知目标拒绝；
- `verified` 必须来自 Verification Agent 并包含 Verification Predicate；
- 节点类型级事实白名单；
- Audit 和 Verification 各自产生图 diff、风险 diff 和演化事件；
- 最终审计结果输出全部 Observation 和更新后的模型。

## 7. 证据连续性

Observation 应用前会计算不含动态证据的 `base_fingerprint`：

- 基础图不变：上一版本证据可以沿用；
- 基础图变化：旧证据失效并进入 `stale_observations_invalidated` 诊断；
- 新验证必须重新绑定当前图；
- 最终 Graph Fingerprint 包含证据状态。

该机制防止代码修改后继续沿用已经过期的验证结论。

## 8. 持续变化分析

当前可以输出：

- Added / Removed / Changed Nodes；
- Added / Removed / Changed Edges；
- New / Resolved / Changed Hypotheses；
- Hypothesis Status Changes；
- Authority Expansion；
- New Boundary Crossings；
- New Privileged Assets；

`vibe-sec model --fail-on-review` 在出现权限扩大、边界变化、新特权资产或控制退化时返回退出码 `2`，用于 CI 或发布前人工审查门禁。

## 9. 项目声明

默认声明文件：

```text
.vibe-sec/vrtm.yaml
```

Schema：`vibe-sec.vrtm.declaration.v1`。

支持 Scope、Nodes、Edges、Assumptions 和 Exclusions。严格解析器会拒绝：

- 重复 YAML Key；
- 未知节点和关系；
- 重复稳定 Key；
- 非法 Flow Plane；
- 不包含规范平面的关系；
- 越界 Confidence；
- 非法对象结构。

未解析边引用会使模型成为 `invalid`，无效模型不会覆盖有效快照。

## 10. 产品入口

### CLI

```powershell
vibe-sec model-init <project-path>
vibe-sec model <project-path> --format json
vibe-sec model <project-path> --format markdown --output vrtm.md
vibe-sec model <project-path> --format dot --output vrtm.dot
vibe-sec model <project-path> --list-snapshots
vibe-sec model <project-path> --fail-on-review
```

### Skill

`skill-audit` 自动保存带 Audit 和 Verification 证据的最终模型。`retest` 在整改应用后重新建模并与最新基线比较。

### API

- `POST /api/vrtm/models`；
- `GET /api/vrtm/models/latest`；
- `GET /api/vrtm/models`。

API 只接受已注册 Project ID，声明路径不得逃逸项目目录。默认监听 Loopback，默认 CORS 只允许本地开发源。

## 12. 质量和持久化

质量状态：

- `complete`：图完整且无当前诊断；
- `degraded`：模型可用，但存在 Unknown、解析失败或过期证据；
- `invalid`：图完整性错误，禁止持久化。

快照目录：

```text
.vibe-sec/vrtm/latest.json
.vibe-sec/vrtm/snapshots/<fingerprint-prefix>.json
```

快照按内容指纹寻址，使用临时文件和 `os.replace` 原子写入。损坏的 Latest 不会阻塞重新建模，但会产生明确诊断。
