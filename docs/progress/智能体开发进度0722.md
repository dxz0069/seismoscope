# Vibe Sec 智能体开发进度 0722

> 基线日期：2026-07-22  
> 范围：本地 Skill/CLI 智能体核心、运行面建模、工具接入、受控验证、整改回送和源码包部署。  
> 不包含：Web UI、企业多用户服务、正式能力对比测评。

## 1. 当前结论

Vibe Sec 当前已经形成一套可运行的安全智能体系统，而不再只是若干扫描脚本或单轮 LLM Prompt。核心流程已经贯通：

```text
Skill / CLI Trigger
        ↓
Recon → Runtime Surface → Audit → Verification → Remediation → Regression
                              ↓
                  Evidence / Artifact / Finding
```

当前状态应准确描述为：

- 智能体编排和安全 Harness 机制已经基本完整；
- 源码审查、运行面建模和验证能力已经具有可执行实现；
- Skill 驱动的源码包安装和调用路径已经建立；
- 漏洞发现能力尚未进行正式基准测评，不能宣称超过 AutoCVE；
- 运行面安全建模是当前最有差异化潜力、同时也最需要验证的方法；
- Web UI 暂缓，当前产品主入口是 Skill 和 CLI。

## 2. 产品定位

Vibe Sec 面向独立开发者、小团队、企业安全团队和使用 AI 编程助手的 Vibe Coding 用户。产品不是传统扫描器的替代品，也不只是一个扫描工具集合。

产品定位为：

> 成熟智能体审计引擎 + 运行面安全建模方法 + 开发流程 Security Harness。

核心目标是把安全变成编程助手能够自动触发和执行的确定性开发流程：

```text
开发变更
  → 安全触发判断
  → 自动审查
  → 收集和补充证据
  → 受控验证
  → 结构化整改回送
  → 编程助手修复
  → 修复后复测
```

用户不应被要求理解扫描器参数、漏洞报告格式或复杂安全术语。智能体负责调查、解释、验证和将结果翻译为可执行的整改任务。

## 3. 当前运行架构

### 3.1 控制面

以下组件运行在宿主机 Python 进程中：

- Claude Code Skill 和 CLI 接口；
- Orchestrator；
- Agent 状态机和多轮 ReAct Runtime；
- Recon、Surface、Audit、Verification、Remediation、Regression Agent；
- Runtime Surface Graph 和 Runtime Threat Model；
- Tool Gateway、权限策略、证据和会话状态；
- 本地源码读取、搜索、AST 和 Tree-sitter 分析工具。

LLM 启用时，由宿主机调用 DeepSeek API。API Key 只从环境变量读取，不进入扫描器容器、报告和安装状态。

### 3.2 工具执行面

传统安全工具通过临时 Docker 容器执行：

```text
Tool Gateway
  → docker run --rm
  → 固定镜像和参数
  → 只读项目目录
  → 收集 stdout/stderr
  → 生成 ToolExecution、ToolSignal、ArtifactRef
  → 销毁容器
```

每次工具调用使用独立的短生命周期容器。多个工具可以并行执行，但不会共享一个长期高权限工具容器。

### 3.3 验证环境

需要复现应用时，可以启动临时的多服务 Docker 环境：

```text
临时内部网络
├── app
├── database / redis / 其他依赖
└── verifier / nuclei
```

内部复现环境默认无外网、无宿主机端口，服务有依赖顺序、健康检查、资源限制、日志收集和强制清理。

## 4. 智能体角色与上下文

### 4.1 Orchestrator

负责固定阶段调度、阶段门禁、失败处理、检查点、暂停恢复、并发和 Agent 间结构化交接。Orchestrator 决定流程，不让 LLM 任意跳过主要阶段。

### 4.2 ReconAgent

上下文包括项目路径、变更文件和审计请求。负责项目结构、语言、框架、依赖、入口点和启动方式识别，并产生后续阶段需要的项目画像。

### 4.3 SurfaceAgent

消费 Recon 结果和源码结构，抽取：

- 外部入口；
- Prompt 和模型调用；
- Tool 和 MCP Capability；
- 权限和信任边界；
- 外部内容；
- 浏览器 Sink；
- 存储和敏感资产；
- 工作流节点；
- 关键代码块。

输出 Runtime Surface、图结构、可视化数据和威胁假设。

### 4.4 AuditAgent

按以下 Lane 执行审查：

- `web_audit`：传统 Web/API 漏洞和业务信任问题；
- `agent_audit`：提示注入、过度代理、危险工具使用；
- `mcp_audit`：MCP 描述注入、授权和能力边界；
- `secrets_audit`：密钥、凭据和敏感文件；
- `workflow_audit`：工作流输入、代码执行、凭据和部署权限。

每条 Lane 可以拆分为多个目标任务并行运行。确定性候选、运行面风险假设和 LLM 源码探索最终进入同一个候选和 Finding 模型。

### 4.5 Finding Reviewer

对一个候选问题执行真正的多轮循环：

```text
观察候选和风险假设
  → 调用源码/语义/图查询工具
  → 获取工具结果
  → 补充支持或反证
  → 识别证据缺口
  → FinalizeFinding
```

模型不能用普通自然语言结束任务。`FinalizeFinding` 要求问题身份、位置、类型、严重性、结论和证据包。

### 4.6 VerificationAgent

消费 Finding、Evidence Bundle、运行面路径和授权策略，选择静态谓词、动态执行、Fuzz、浏览器或多服务环境验证。

最终结论由 Harness 根据验证谓词、正向控制、负向控制和实际工具结果生成。工具可用、容器启动成功或模型声称成功，都不能单独确认漏洞。

### 4.7 RemediationAgent

为已验证或仍需补证的问题生成 RemediationBundle，包括：

- `ai_patch_prompt`；
- 修改范围；
- 修复约束；
- 验收标准；
- 正向和负向复测；
- 预期运行面变化；
- 受影响文件和位置。

RemediationAgent 不直接修改用户项目，而是将结构化整改任务返回当前编程上下文。

### 4.8 RegressionAgent

在编码助手完成修改后，对比变更树，执行漏洞复测、行为控制和项目测试。只有修复证据和复测条件满足时，问题才可以进入关闭状态。

## 7. Tool Gateway 和证据机制

所有 Agent 工具调用统一经过 Tool Gateway：

- 工具注册和能力 Schema；
- 项目根目录范围检查；
- 网络目标和域名白名单；
- 只读、扫描、主动和修改型风险分类；
- 超时、CPU、内存、PID 和输出限制；
- 敏感信息脱敏；
- 工具执行审计；
- 不可变 Artifact 和 SHA-256；
- ToolSignal 标准化；
- 失败和超时证据保留。

镜像在注册前执行 capability、版本和工具版本预检。不存在或标签不匹配的镜像不会出现在智能体工具 Schema 中。

智能体默认没有通用 Shell、任意命令执行和项目写入工具。

## 11. 相对传统工具的当前优势

传统工具在单次规则扫描速度和确定性上更强。Vibe Sec 不应以“替代传统扫描器”作为竞争叙事。

当前设计优势是：

- Skill 接入和编程助手自动搭建；
- 不要求用户具备安全基础；
- 自动理解项目和变更上下文；
- 将规则信号扩展为跨文件和跨组件调查；
- 能处理 AI、MCP、工具权限和工作流风险；
- 将多个信号统一为证据化 Finding；
- 提供验证、整改回送和修复后复测；
- 用户不需要学习多个工具的参数和报告格式。

这里的“快速”主要指从安装、审查到整改闭环的总体效率，不代表 LLM 单次扫描速度快于传统工具。

## 12. 相对 AutoCVE 的机制差异

AutoCVE 类源码探索和验证能力是 Vibe Sec 必须具备的底座。当前设计上的扩展包括：

1. 从触发到复测的完整开发生命周期，而不只是一轮源码审计；
2. Runtime Surface Graph 和可执行风险假设；
3. 传统漏洞与 Prompt、MCP、Tool、Workflow 风险的统一表达；
4. Harness 掌握最终验证结论；
5. Finding 级任务状态、并行、检查点和恢复；
6. 安全信封、正反控制和隔离多服务 PoC；
7. 扫描器作为可选证据源，而不是独立产品流程；
8. Skill 驱动的安装、触发、整改回送和复测。

这些是机制和产品范围上的优势，不是测评结论。当前不能宣称源码漏洞发现率、PoC 成功率或总体能力已经超过 AutoCVE。

## 14. 距离成熟产品的主要差距

### 14.1 缺少正式测评

这是当前最大的能力缺口。尚未建立传统漏洞、跨文件漏洞、AI/MCP 风险、负样本、PoC 和整改的统一基准。

### 14.2 源码分析深度不均

Python、JavaScript 和 TypeScript 是当前主要语义语言。Java、Go 和其他语言的框架路径仍以有限语义和来源关联为主，不是通用跨过程污点分析。

### 14.3 运行面方法论未经过验证

需要测量图抽取准确率、风险路径有效率、假设误报率，以及运行面图对最终发现率的实际增益。

### 14.4 多轮智能体稳定性未量化

需要测量重复运行一致性、无效循环、提前终止、证据错误引用、模型漂移、时间和 Token 成本。

### 14.5 验证和整改覆盖不足

协议已经建立，但不同漏洞类型的可复现率、修复成功率、回归率和闭环成功率尚不清楚。

### 14.6 发行和生产运行能力不足

缺少 OCI 正式发行、签名、离线包、事务回滚、长期任务队列、集中监控、多用户权限和企业策略管理。

## 15. 下一阶段建议

下一阶段应优先建立测评体系，而不是继续堆叠扫描器。

建议使用同一模型和同一数据集运行以下模式：

1. 传统工具单独运行；
2. Vibe Sec 确定性分析，不使用 LLM；
3. Vibe Sec LLM 源码审查，不使用运行面图；
4. Vibe Sec 完整运行面审查；
5. Vibe Sec 完整能力加传统工具信号；
6. AutoCVE 对照运行。

核心指标包括：

- 候选和最终 Finding 召回率；
- 误报率和错误确认率；
- 证据完整率；
- 跨文件漏洞发现率；
- AI/MCP/Workflow 风险发现率；
- 重复运行一致性；
- 平均时间、Token 和工具调用次数；
- PoC 复现成功率；
- 整改后复测成功率。

在测评完成前，对外应宣称“机制覆盖更完整、接入更轻、流程闭环更强”，不应宣称“漏洞发现能力已经超过 AutoCVE”。

## 16. 0722 基线定义

0722 版本的核心成果不是增加了若干安全工具，而是已经把以下对象连接成一个系统：

```text
Skill Trigger
  + Deterministic Orchestrator
  + Multi-turn Audit Agent
  + Runtime Surface Graph
  + Permissioned Tool Gateway
  + Evidence-bound Verification
  + Remediation Return
  + Regression Retest
  + Source-package Setup
```

下一步工作的判断标准应从“功能是否存在”切换为“能力是否经过测量、结果是否稳定、用户是否能低成本获得可靠结论”。
