# Vibe Sec Platform 当前项目状态

> 状态快照：2026-08-01
>
> 结论范围：本机代码、正在运行的本地服务、持久化任务数据、完整自动化回归和已有靶场报告。本文刻意区分了“已实现”“已实测”“候选风险”和“尚未具备”，不将设计目标或静态发现表述为已验证漏洞。

---

## 1. 执行结论

Vibe Sec Platform 已经是一个**可在本机对源码目录发起审计、保存任务历史、查看发现与整改建议、生成运行面威胁模型的工程验证版平台**。它不是远程源码托管或远程审查服务；靶场服务器只用于受控验证，本机项目路径仍是审查对象和状态存放位置。

当前可以用于以下工作：

1. 从前端创建本地项目和审计任务，选择是否启用已配置的 LLM。
2. 查看项目维度的任务历史、最新任务的去重审查队列、证据摘要与整改包。
3. 为项目生成和保存 VRTM（Versioned Runtime Threat Model），在前端查看中文化的运行面风险概览，并切换到智能面、数据面、权限面和源码追溯视图。
4. 通过 CLI、Python API 或 FastAPI 调用确定性审计流程；对部分漏洞类别产生静态或受控验证证据，并生成复测计划。

当前还不能将它当作成熟的生产安全门禁或自动修复系统。最重要的原因是：真实项目召回率和误报率尚无完整量化基准；LLM 审查的深度验证仍不稳定；前端有一批遗留页面会回退到演示数据；任务执行依赖 FastAPI 进程内后台任务，服务重启会中断运行中的审计；模型密钥当前虽不返回给浏览器，但本地存储尚未加密。

**成熟度判断：工程验证版 / 本地单人使用 Beta，而非可对外宣称完整闭环的成熟产品。**

## 2. 定位、边界和可信结论

### 2.1 产品定位

平台面向 AI 辅助开发（Vibe Coding）的本地源码审查。设计工作流为：

```text
计划 -> 侦察 -> 运行面提取 -> 多审计通道 -> 合并去重
-> 受控验证 -> 整改包 -> 返回开发上下文 -> 定向复测
```

它覆盖传统 Web/API 风险、密钥泄露、AI Agent 与 MCP 风险、工作流/工具权限风险，并使用运行面模型把输入、指令、权限、数据和敏感操作放在同一风险语境中。

### 2.2 结论分级

平台和使用者必须遵守以下边界：

| 结论类型 | 含义 | 是否可直接称为漏洞 |
|---|---|---|
| 静态候选 | 规则、语义分析或 LLM 发现的可疑点 | 否 |
| 运行面假设 | 基于已提取节点、边界和攻击路径的待证伪风险路径 | 否 |
| `needs_evidence` / `not_reviewed` | 证据不足或尚未排入验证预算 | 否 |
| `verified` | 满足 Harness 控制的验证谓词，并有结构化证据 | 可以称为已验证发现，但仍须结合业务影响复核 |
| `rejected` | 负向对照或证据否定了候选 | 不应继续按活动风险展示 |

运行面图中的红色路径表示“当前待验证、与风险假设相关”，而不是“已经成功利用”。已反证或已缓解路径保留在历史中，但不应继续被当作活动红色风险。

### 5.4 历史靶场结果如何解读

`docs/progress/VAMPI_TEST_REPORT.md` 是 2026-07-29 的历史 no-LLM 基线：当时仅召回 6 个已知漏洞中的 1 个（17%），原因包括 OpenAPI/Connexion 路由未提取、弱密钥/业务逻辑/IDOR 检测不足。之后代码和回归测试已加入 OpenAPI 路由提取，当前 VAmPI VRTM 也已产生 14 个风险假设；但是**尚未对这份更新后的代码重新执行并人工标注 VAmPI 六个已知漏洞的完整召回率复测**。因此，17% 是历史问题证据，不应被说成当前准确率；当前提升也不能在复测前被说成已证实。

Juice Shop 已经跑通本地源码审计，但没有完成对 CVE/官方挑战的人工 ground truth 标注。一次较早任务产生 1,076 个发现，后续结果降为 131 个，说明去噪已有进展；在没有精确率、召回率和每条已验证证据复核前，仍只能把这些结果视为审查队列。

## 7. 当前检测与验证能力边界

### 7.1 相对可靠的能力

1. 已知模式和有明确静态谓词的密钥、部分命令执行、工作流、MCP 配置、危险输入到汇等问题。
2. Python、JavaScript/TypeScript 和 YAML 的部分结构提取，以及 Python/JS/TS 的受限跨文件语义追踪。
3. 带正负对照的 Harness 受控验证。验证记录包含谓词、证据等级、候选用例、正向/负向对照和产物引用。
4. VRTM 的节点/边稳定标识、模型快照、声明和运行观察、差异检测，以及风险假设的排序与去重。

### 7.2 当前弱项或未证明能力

1. **复杂业务授权**：IDOR、管理员自赋值、多租户隔离、角色组合等需要跨层数据流和业务语义，不能依赖现有规则结论。
2. **OpenAPI/Connexion 等框架**：路由提取已进入代码和回归，但真实 VAmPI 基准尚未复测，不能声称召回已经达标。
3. **LLM 深度审查**：历史上 ReAct 完成率从 26% 提升到 74%，但 LLM 结果的验证率仍显著低于 no-LLM 路径，尤其是没有可执行 PoC 的新风险类型。
4. **大型 JS/TS 项目**：Juice Shop 的 467 个未知安全事实说明模型覆盖尚不足；1,918 个节点的源码图即使被语义投影隐藏，底层关联质量仍需提高。
5. **动态验证广度**：动态、容器和浏览器验证框架存在，但需要明确授权、受控环境、可执行计划和每类漏洞的 Harness 谓词；不能对任意候选自动验证。
6. **准确率指标**：尚未完成多靶场的 TP/FP/FN 标注、按漏洞类别的 Precision/Recall/F1、运行时长和资源消耗基线。

## 8. 主要成熟度差距与优先级

### P0：应先完成，才能作为稳定本地产品推广

1. **移除前端演示数据混入真实工作区的问题。** 对未实现接口显示“未接通”，不要静默回退；收敛前端到已实现的本地审计链路。
2. **任务可靠性。** 把 FastAPI `BackgroundTasks` 迁移为可恢复的本地任务执行器/队列，至少支持任务心跳、取消、重试、启动后恢复或明确重跑。现有 6 次失败已证明进程内任务不够可靠。
3. **本地密钥保护。** 当前 API 响应会脱敏，但 `ApiStateStore` 直接持久化模型配置。应改用操作系统凭据库或加密存储，支持迁移、轮换和删除，并在报告中只显示“已配置”。
4. **前端复测与验证写回。** 提供受权限约束的验证启动/结果提交和 `retest` API，完整展示证据、对照和状态转移。
5. **真实基准复测。** 重新运行 VAmPI，并以六个已知漏洞为 ground truth 标注 TP/FP/FN；同样为 Juice Shop 建立固定版本、挑战/CVE 映射和人工复核表。

### P1：提高检测价值和可解释性

1. 对入口按认证中间件、路由组和实际敏感操作聚类，进一步压低“未保护入口”类假设的重复量。
2. 把前端临时的风险归并下沉为后端显式 `risk_groups` 合约，保证 CLI、API 和 UI 统计一致。
3. 增加跨文件调用图、导入图和有限污点传播，优先覆盖 Controller -> Service -> DAO -> 数据库的常见路径。

## 9. 当前推荐使用方式

### 9.1 用前端测试一个新本地项目

1. 启动本地 API 与前端，确认 API 健康状态正常。
2. 在工作区新建项目，填写**本机源码绝对路径**；平台读取源码，不需要把代码传到靶场服务器。
3. 第一轮优先使用 no-LLM 审计，建立可重复的静态/结构基线；随后在模型设置确认已激活聊天模型后，再创建 LLM 增强任务。
4. 等待任务状态进入 `completed`。若是 `failed`，读取具体错误并新建任务；不要把中断任务当作完成结果。
5. 在“风险发现”中按验证状态优先处理 `verified`，其次是高优先级 `needs_evidence`；`not_reviewed` 是待审队列，不是确认问题。
6. 查看整改包中的约束、验收标准与复测计划。当前从 UI 应把它作为人工修复依据；真正复测仍建议通过 CLI/Python 工作流执行并保留证据。
7. 打开“运行时威胁模型”，先看“风险概览”和中文路径说明；需要定位源码时再切到“源码追溯”。

### 9.2 适合的测试目标

优先从范围小、已知答案明确的项目开始：fixture、VAmPI 的固定 commit、Juice Shop 的固定 commit，以及一份允许审查的本地业务项目。每次应保存：项目版本/commit、配置、审计时间、候选数、去重数、验证状态分布、人工 TP/FP/FN 判定和复测证据。

不建议在当前阶段将任何一次输出作为自动阻断发布、自动提交补丁或对外漏洞披露的唯一依据。
